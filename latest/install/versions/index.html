Requirements and tested versions¶

What Muster needs, which versions it was checked against, how its own versions are numbered, and how to verify that a release you download is the one the project built. "Tested" means different things for different rows, so each row says which.

  • CI means an automated job that runs on the project's pull requests or nightly, and fails the build.
  • Development stand means a person ran the behaviour against a real server of that version and recorded what it did, but no job repeats it. These facts are the ground the messenger and Alertmanager features rest on; the fake servers that CI uses imitate them.

Requirements¶

PostgreSQL
14 or newer, directly or or through a pooler whose session connection is session-capable. Nothing else stateful: no Redis, no queue. See The database.
Where Muster runs
Binaries and container images for Linux; binaries also for macOS; both on amd64 and arm64. The container image is linux/amd64 and linux/arm64. The Quick start needs Docker with the Compose plugin.
Kubernetes
1.30 or newer, for the Helm chart.
A browser
For the web UI, one that keeps a Secure cookie: over HTTPS, or on localhost. See Sign-in needs HTTPS or localhost.

Tested versions¶

PostgreSQL
14 and 17 in CI: make test-integration runs the integration tests on both, in containers, on every pull request. The compose example and the development database run PostgreSQL 17.
Kubernetes and Helm
Kubernetes 1.33.0 in CI: make helm-check lints the chart, renders it with the values files of the repository and validates the result strictly against the schemas of 1.33.0. Helm v4.3.0 does the rendering, and also packages the chart for a release. Nothing is run in a cluster by CI, and other versions from 1.30 are not checked.
Alertmanager
v0.34.1 on a development stand, with Prometheus v3.15.0 and vmalert v1.153.0: how it repeats, groups, restarts and truncates is measured there. Other versions of Alertmanager send the same webhook; if one behaves differently, the Snapshot semantics page and the Heartbeat are how you notice.
Grafana
OSS 13.2.4 on a development stand, as one instance on SQLite and as a pair of replicas on PostgreSQL 17, through the webhook contact point of its built-in Alertmanager. See Connect Grafana.
Mattermost
11.2.2, a test server on the development stand, through REST API v4 with a bot account. CI runs the same behaviour against a fake Mattermost server. See Mattermost.
Slack
Slack's cloud Web API and Socket Mode, on a development stand: a free workspace with a test app and a test channel. CI runs against a fake. See Slack.
Telegram
The cloud Bot API 10.3, on a development stand, with a test bot and a test channel. CI runs against a fake. See Telegram.
The web UI
Its component tests and its end-to-end tests run in Chromium in CI. Other browsers are not tested.

Version numbers¶

Muster's versions are 0.N.x, and 1.0 is a long way off.

  • 0.N is layer N of the roadmap. L1, Alert Groups in messengers, is 0.1.x; L2, on-call, is 0.2.x; L3 will be 0.3.x, and so on. Layer N+1 starts with the release 0.(N+1).0, which the maintainers set with release-please's release-as.
  • 0.N.x releases bring fixes and small changes, and nothing that breaks an installation: settings, the API under /api/v1 and the database keep working without a change on your side.
  • Breaking changes come only with the next layer's minor version, and its release notes say what to change before you upgrade. See Upgrades for how to upgrade.

Upgrade notes¶

After a recovery from a failed migration below, run muster doctor: its schema line is WARN while migrations remain, OK once muster migrate or a replica's start has applied them, and FAIL while the schema is still dirty.

0.2.0

0.1.x can crash-loop on a Route with a line template. On 0.1.4 and earlier, Muster panics when it re-renders the Root message of an Alert Group that has no Alerts to list on a Route with a line template, for example at the end of a Grace period after a person resolved an Alert Group whose Alerts still fired. The timer fires again at every start, so the replica crash-loops. 0.2.0 fixes it: upgrade. Until you can, remove the line template from such Routes.

The route.urgent setting of a Route and the Organization's "critical is Urgent" (organization.critical_is_urgent) no longer act: an Alert Group is Urgent exactly when its Severity level is critical, and a Route raises the level of its Alert Groups with its Minimum severity.

  • Routes marked urgent got the Minimum severity critical, which also makes their Alert Groups critical, also for Severity conditions.
  • An Organization that had turned "critical is Urgent" off now sees its critical Alert Groups as Urgent: a rise to critical ends their Snoozes and, where route.urgent_rise_removes_ack is on, their acknowledgements.
  • Migration 0021 computes the Severity level and the urgency of the open Alert Groups and of their deliveries once, by the new rule: without lifecycle events or Mentions, without ending a Snooze or an acknowledgement, and without publishing anywhere new.
  • Urgency is read from the Severity level of every Alert Group, resolved ones included, while migration 0021 computes the level only of the open ones. A resolved Alert Group whose Route was marked urgent now reads urgent: false unless its level is critical, and a resolved critical one of an Organization that had turned "critical is Urgent" off now reads urgent: true, so the urgent filter and the statistics over a period before the upgrade give other results than on 0.1.
  • urgent in the input of a Route and critical_is_urgent in the input of the Organization are optional. A Route request with urgent: true and no minimum_severity, as a 0.1 client sends it, sets the Minimum severity critical; urgent: false, urgent beside minimum_severity, and critical_is_urgent change nothing. Reads keep both until 0.3.0 removes them: urgent is true exactly when the Minimum severity is critical, and critical_is_urgent is always true.
  • Migration 0022 adds Teams and the Organization's Working hours: Monday to Friday, from the start of the working day to its end, 18:00. The end must be later than the start on the same day, so an Organization whose working day started at 18:00 or later gets the end 23:59 — and one that started at 23:59, the latest time with no later end, the start 23:58. Check the Organization's settings after the upgrade if yours did.
  • Migration 0023 adds the button sets: the Organization's shows every button, and every Destination follows it, so the Root messages show the buttons they showed before.
  • Migration 0024 adds the Team label and Team matchers. The Team label is team by default, and no Team exists after the upgrade: each Alert Group whose Alerts start firing with the label team after the upgrade records one Quiet unknown_team_value per value in its Timeline, and outgoing webhooks in events mode receive one extra event for each. Create the Teams, or change the Team label, to avoid it.
  • Migration 0025 adds Schedules and the Permissions schedules:read, schedules:write and schedule-overrides:write. Roles get them at once; a Personal access token keeps the Permissions it was issued with, so issue a new one to reach Schedules with a token.
  • Migration 0026 adds the personal iCal feeds; no User has one after the upgrade.
  • Migration 0027 adds the evaluation of the open Alert Groups when a Team or the Team label is saved: creating a Team for a value of the Team label, or changing a Team's slug or Team matchers, or the Team label, adds the Team to the open Alert Groups whose firing Alerts it now picks, with a Quiet team_joined. It only adds, so the Alert Groups of Alerts that fired before the upgrade get their Teams the first time a Team is created, its slug or Team matchers change, or the Team label changes.

  • Migration 0028 adds the gap alert of each Schedule, by_default: the main Schedule of each Team raises the Internal alert MusterScheduleGap for a gap now or within 7 days.

  • The Root messages have a new layout for every Route, in Mattermost, Slack, Telegram and the body of a bridge: the title with the status as a word, the fields Severity, Route, Teams and Started, the summary and the description, one line of Labels in the message, the Alerts by the label that tells them apart, then the notices, the footer, the buttons and the links. The label sections and the expandable quote of 0.1 are gone; every other label stays on the Alert Group page. An open Alert Group's message changes to the new layout at its next edit. A Route with its own Root message template keeps its body, now under the title, the fields and the links; its built-in source, which "Custom" fills the editor with, changed too.

  • Migration 0029 adds "Labels in the message" of a Route, routes.message_labels, computed by default from the Group key without alertname and the severity label, then the Team label and namespace, and the description of an Alert Group, alert_groups.description, set once like its summary. An Alert Group created before the upgrade, or by a 0.1 replica during it, has none until a new Alert with a description joins it on 0.2.0, which sets it; until then its Root messages show no description.
  • Migration 0030 adds the claim of every entry of the Role mapping, with subtrees, and the identity provider entries of Teams. The Role mapping reads as before: every entry reads the groups claim, and an entry ending in /* now matches its subtree.
  • Migration 0031 lets a change of the Organization's severity label, Team label, Instance labels, time zone, start of the working day or first day of the week, and a rename of a Team, reach the open Alert Groups: their Root messages are edited once, Quietly, to show the new labels, start time, Snooze presets or name, instead of at each Alert Group's next change.
  • Migration 0032 adds the Severity conditions of the Destinations of Routes and Teams, "Also to the Teams from the label" of a Route, off, and the Destinations of the Teams, none. Every Destination of a Route has the condition any, so a Route delivers as before. Routes take and read destination_entries; destination_ids stays, derived from destination_entries, until 0.3.0 removes it: a request with only destination_ids keeps the condition of each Destination it keeps and gives a new one any. Outgoing webhooks in events mode may receive the new event destination_joined.
  • Migration 0033 adds the contacts at Notification gateways and their confirmation codes; no data is migrated. It is expand only: a 0.1 replica, or one of a development image without it, reads and writes nothing of the new tables.
  • Migration 0034 adds the queue of calls through Notification gateways, the Timeline kind escalation with its events, the Mention paged and the Transport gateway; no data is migrated. It is expand only: a 0.1 replica, or one of a development image without it, writes none of the new tables and columns, and every row it writes satisfies the widened CHECKs. Outgoing webhooks in events mode may receive the new event page_not_delivered.
  • Migration 0035 keeps the signed action data of a call through a Notification gateway, with the id of the key that signed it, from its first attempt; no data is migrated. It is expand only: a 0.1 replica, or one of a development image without it, writes neither column and signs each attempt of a call with the active key, as before.
  • Migration 0036 adds the Broken state of Notification gateways to the Connections; no data is migrated, and no gateway starts Broken. It is expand only: a 0.1 replica, or one of a development image without it, writes none of the new columns; one of such an image sends the calls of a Broken gateway, which then fail and end Not delivered as before.
  • Migration 0037 adds the Notification rules: the Organization's default rules, which every existing Organization takes — normal a Mention, important a Mention, a wait of 5 minutes and a Mention — and the rules of each User, none at first, so that every User follows the Organization's. It is expand only: a 0.1 replica, or one of a development image without it, reads and writes nothing of either, and an Organization it creates gets the default rules.
  • Migration 0038 marks the edits of open Root messages that a change of configuration alone made — a new button set, new message settings, a renamed Team, the re-render after a key rotation — so that delivery sends them after the Publications of new Alert Groups and the edits of Root messages that Alerts and Commands made, of the same urgency, and those of Alert Groups that are not Urgent also after the Thread replies and the events of outgoing webhooks; no data is migrated, and a re-render still pending at the upgrade keeps its place. It is expand only: a 0.1 replica, or one of a development image without it, claims in its own order and never writes the mark, so an edit, a final edit or a republication it queues for a Root message whose re-render a 0.2.0 replica queued — still pending, or already delivered by the older replica — waits behind the work that goes before configuration edits of its urgency until it is delivered; a delivery by a 0.2.0 replica clears the mark.
  • Migration 0039 lets a change of a Route's language, Snooze durations, Root message template or line template, and a change of a Link rule or a Lookup table, reach the open Alert Groups: their Root messages are edited once, Quietly, to show the new texts, Snooze buttons, body or links, instead of at each Alert Group's next change; no data is migrated.
  • Migration 0040 does the same for the user a footer names: a new display name of a User, a new, changed or removed Account link of a User, and a new name of a Service account edit, once and Quietly, the open Root messages whose footer names them as the Owner or as who snoozed; no data is migrated. Whether a Root message needs an edit is now decided by the footer of its Destination's identity space alone, so after the upgrade an open Root message whose footer names a User with an Account link in any other identity space — a User with only a Telegram link, for a Mattermost Destination — gets one Quiet edit, with no visible change, at its next re-render.
  • Migration 0041 does the same for a Destination moved to a Mattermost, Slack or Bridge Connection of another identity space: each open Root message whose footer then reads otherwise — a User with an Account link in either Connection — is edited once, Quietly, at the re-render of the move, so that the footer names the user as the new Connection's messenger knows them; the others are not edited. No data is migrated. Such an edit goes through the new Connection to a message published through the old one, as any edit after a move always did, now at the move instead of at the Alert Group's next change: a message the new Connection cannot find (a 404, as from another Mattermost server) is published again once, Quietly, as a deleted Root message is, and a Mention in its footer may notify; a message the new Connection may not edit (a 403, as from another Connection of the same Mattermost server) makes the Destination Broken. A repair of a Root message that a send after a move may have shown wrong stores a repair hash in deliveries.desired_hash; a replica without 0041, during a rolling update, takes it as a changed Desired state and edits each such Root message once more, Quietly, with no visible change.
  • Migration 0042 adds the Team mentions, none after the upgrade, and what the check of a Connection finds of its groups: whether a Slack bot token has usergroups:read and whether a Mattermost bot may read the groups, unknown until the Connection's next check. It is expand only: a 0.1 replica, or one of a development image without it, reads and writes neither; a Team or a Connection it deletes keeps its Team mentions, which no read shows and the Team's next save of its Team mentions replaces, and a new bot token or server URL it saves keeps what the last check found of the old bot's groups until the Connection is checked again on 0.2.0.
  • Migration 0043 turns the Mention settings of every Destination into Mention entries with the same effect: each target chosen for a kind of Loud event becomes one entry for those kinds, and an entry for new_alert_group also applies to the start of a Storm, as the Storm summary of 0.1 mentioned. A Destination that mentioned nobody has no entries, and a Destination of a Team gets the entry "Team {Team}", Telegram excepted. Until 0.3.0 the API still returns the Mention settings as the deprecated field mentions, computed from the entries — the same Users and groups for each kind, listed in the order of the first kind that lists each — and a request with mentions and without mention_entries is still converted, replacing only the entries that 0.1 could express; 0.3.0 removes the field. The migration keeps destinations.mentions as it found it and 0.2.0 no longer writes it, except that a Destination created on 0.2.0 stores nobody there. It is expand only, and its down migration drops the entries and restores the settings as the column kept them.
  • Migration 0044 adds what the Destination check of a Telegram Destination sees of the members of its discussion group, for the warnings about unreachable On-calls: nothing is known after the upgrade, so no On-call is warned about a discussion group until each Telegram Destination is saved or checked again. It is expand only: a 0.1 replica, or one of a development image without it, reads and writes neither column, and a check it runs leaves what the last check on 0.2.0 saw. A Telegram Destination that such a replica moves to another channel or discussion group during a rolling update keeps the absences seen in the old group until its next check: select Check on it once every replica runs 0.2.0.
  • Migration 0045 records who made the first acknowledgement of each Alert Group, for the statistics by people. For the Alert Groups acknowledged before its fill starts it fills it from the earliest acknowledged entry of their Timeline, but only where the Timeline is still whole, its created entry kept (retention.alert_details); the older Alert Groups name nobody, and the statistics by people count them in the row "Unknown". It is expand only: a 0.1 replica neither reads nor writes the column and leaves it as it is. The fill sees the Alert Groups as they were when it started: a first acknowledgement that a 0.1 replica records before then is filled with the others; one it records after the fill started, while the rollout lasts, names nobody and counts as "Unknown" too. A change that a 0.1 replica makes to an Alert Group the fill is writing waits until the fill commits; should the two ever deadlock, PostgreSQL ends one of them, and a failed fill is recovered as described below. Their time to acknowledge is kept as before.
  • Migration 0046 adds the Escalation chains, their steps and the chains that Routes and Teams name, none after the upgrade, and the Permissions escalation-chains:read, which every Role gets, and escalation-chains:write, which Admins get. Roles get them at once; a Personal access token keeps the Permissions it was issued with, so issue a new one to reach the Escalation chains. It is expand only: a replica without it reads and writes none of them.
  • Migration 0047 adds the runs of the Escalation chains on Alert Groups, the steps they made and skipped, and the timers of their steps, which name the run rather than the Alert Group, none after the upgrade: chains start at the next point that starts them, such as a first Publication or an Unacknowledge, never on the upgrade. It is expand only: a replica without it never claims the timers of runs, as it claims only the kinds it knows, and keeps setting the ack timeout, Reminder and Snooze timers of Alert Groups as before, and never marks the release of a held Alert Group by a raised Minimum severity, whose first Publication then starts chains. Such a replica starts no chain on the Alert Groups it changes, and a chain whose Alert Group it acknowledges, snoozes or resolves stops at its next step, without making it; let the rollout finish before relying on chains.
  • Migration 0048 adds the delivery events of undelivered Mentions, mention_not_delivered and mention_delivered, and an index on them, none after the upgrade: the warnings of the Destinations start with the next Loud message that leaves someone out. It is expand only: a replica without it records neither, so the Loud messages it delivers during the rollout warn of nothing and clear no warning, its Destination reads have no mention_warnings, and its Timeline lists both kinds, mention_delivered included, as delivery events of a kind it does not know, which its web UI shows as "Delivery event in {Destination}".
  • Migration 0049 adds the Pages by Mention of the Escalation chains, the people they name, the runs of the Notification rules and the timers of their waits, which name the rule run rather than the Alert Group, and the Thread replies of Pages, none after the upgrade: the chains Page from their next step on. It is expand only: a replica without it makes no Page — its steps that Page are made without a Thread reply, as before — never claims the timers of rule runs, and stops no rule run when it acknowledges, snoozes or resolves an Alert Group, whose rule runs then stop at their next action, without making it; let the rollout finish before relying on Pages.
  • Migration 0050 adds the Assignees of Alert Groups, the Assignees after each change in the Timeline, and the run step of each Page and run of a Notification rule, none after the upgrade: an Alert Group gets Assignees from the next delivered Page. It is expand only: a replica without it makes no Assignee and never clears them when it acknowledges, snoozes or resolves an Alert Group — the reads show only the Assignees of firing Alert Groups, so such rows never show — and its Pages and rule runs carry no run step, so a reach by them only adds to a chain without Assignees; let the rollout finish before relying on Assignees.
  • Migration 0051 adds the Pages through Notification gateways: the Page, the run of the chain and the rule run that queued each Alert Group of a call, and the gateway and the call of a Page of the kind call, none after the upgrade. It is expand only: a 0.1 replica, or one of a development image without it, writes none of the new columns, so the calls it queues have no stop check of a chain or a rule, and a call it sends ends without settling its Pages, which stay pending and make no Assignee. Its delivery worker also settles the Pages of the calls of a 0.2.0 replica as Pages by Mention within a round: it ends them not_delivered, records a wrong page_not_delivered, and an accepted call then makes no Assignee. Do not rely on Pages through gateways until every replica runs 0.2.0.
  • Migrations 0052 to 0055 add one index each, on thread_replies (the Page replies still to be sent), alert_groups (the open Alert Groups and those in their Grace period) and twice on deliveries (the pending deliveries of Alert Groups, and those no worker has to send, by their last change), which the delivery worker, the walks of a change of configuration and the retention of deliveries read. They are expand only and a replica without them works as before, only slower on a large database. Each builds its index inside a transaction, so while it builds, writes to that table wait: ingestion and Alert Group changes for alert_groups and deliveries, Thread replies for thread_replies. Each runs under a lock_timeout of 5 seconds and a statement_timeout of 5 minutes.
  • Migration 0056 adds managed_by, the name of the tool that keeps an object as code, such as the Terraform provider, to Integrations, Routes, Teams, Schedules, Escalation chains, Lookup tables, Link rules, Connections, Destinations, the Organization's settings, the Outbound address policy and the OIDC settings, null on every object after the upgrade. It is a mark only and changes nothing else. It is expand only: a replica without it neither reads nor writes the mark, and keeps it on the objects it saves.

Breaking changes in 0.2.0. Four changes can break an installation or a client that worked on 0.1; check them before you upgrade:

  • The Route profile id on_call is now paging. A client that types the enum of listRouteProfiles or looks up on_call must use paging. Nothing stored changes. See "The Route profile On-call is now Paging" below.
  • A Helm image.repository without a registry host is prefixed with ghcr.io. A path such as myorg/muster that you pulled from Docker Hub now points at ghcr.io/myorg/muster: set image.registry: docker.io or write the full path; a local image for kind or minikube needs image.registry: "". See "Helm chart" below.
  • A Role mapping entry that ends in /* is a subtree. platform/* matched only that exact group name on 0.1; it now matches platform and every group below it, so it can give a Role to people it did not before. Review each entry that ends in /* before the upgrade. An entry with * anywhere else is refused with 422 when you save the OIDC settings. See "Role mapping entries with *" below.
  • Marking a Route urgent and "critical is Urgent" stop acting. An Alert Group is Urgent exactly when its Severity level is critical, and a Route raises the level with its Minimum severity. Routes marked urgent got the Minimum severity critical; an Organization that had turned "critical is Urgent" off now has Urgent critical Alert Groups, and no setting keeps the old behaviour. Check the Minimum severity of your Routes after the upgrade. A client that sends urgent or critical_is_urgent keeps working, as the notes above describe.

Slack apps get an optional scope. Team mentions in Slack need the bot scope usergroups:read, which the manifest now has. A Slack app installed before 0.2.0 keeps working without it, without Team mentions. To add it, add the scope to the app and reinstall the app in the workspace, as Slack asks: the reinstall keeps the bot token, so the Connection needs no change; check it again and it records the scope (Add usergroups:read to an installed app).

The Route for Muster's own alerts groups by more labels. An installation that accepted the suggestion "Send Muster's own alerts to a Destination" in 0.1 has a Route "Muster internal alerts" whose Group key is alertname, integration, destination and route. Add to it the labels that 0.2.0 suggests after route — schedule, then connection — so that each Schedule's gaps get an Alert Group of their own, which belongs to that Schedule's Team, and each Broken Notification gateway one of its own; without them, the gaps of every Schedule share one Alert Group, which collects the Teams of all of them, and so do the Broken gateways. When the Routes can deliver to the Teams of their Alert Groups, the suggestion turns that on too, so that each gap reaches its own Team; turn it on for a Route accepted before.

Helm chart. ingress.app.annotations and ingress.ingest.annotations set the annotations of one Ingress, over the shared ingress.annotations, so an installation that turned the chart's Ingress off to get different annotations can turn it on again. The image is now image.registry and image.repository, with global.imageRegistry over the registry. An image.repository with the full path keeps working, but it ignores both registry values; move its host to image.registry to use global.imageRegistry. A host without a dot or a colon, such as registry/muster, now counts as a path under image.registry.

  • An image.repository without a registry host, such as the Docker Hub path myorg/muster or a bare local muster for kind or minikube, is now prefixed with ghcr.io. To keep pulling it from Docker Hub, set image.registry: docker.io; or write the full path, such as docker.io/myorg/muster. A local image for kind or minikube needs image.registry: "".
  • A global.imageRegistry inherited from an umbrella chart now applies to Muster. To keep pulling Muster from GitHub, set image.repository to the full ghcr.io/muster-io/muster, which ignores both registry values.
  • httpRoute.app.annotations and httpRoute.ingest.annotations set the annotations of one HTTPRoute, over the shared httpRoute.annotations, as the Ingress ones do.
  • Three alert rules are new and on by default, so an installation that renders the rules gets them on upgrade: MusterIngestSnapshotFailed (alerting.rules.MusterIngestSnapshotFailed.enabled), MusterScheduleGap (alerting.rules.MusterScheduleGap.enabled) and MusterNotificationGatewayBroken (alerting.rules.MusterNotificationGatewayBroken.enabled). Set the key to false to leave one out.

The Route profile On-call is now Paging. route-profiles (listRouteProfiles) returns the id paging, named Paging, instead of on_call, which breaks clients that type the enum of the profile ids or look up on_call; during a rolling update a 0.1 replica still answers on_call, and a page of the 0.1 web UI names both profiles Informational, and its first card fills in the Paging values, so reload the web UI after the rollout. Profiles only fill in a new Route and are not stored, so nothing stored changes.

Rolling upgrade from 0.1. Every migration of 0.2.0 applies when the first 0.2.0 replica starts, while 0.1 replicas still run until the rollout ends. A 0.1 replica keeps running on the new schema, but one that starts or restarts after the first 0.2.0 replica has migrated (after a crash or an OOM kill, on a node drain, a scale-up or docker compose restart) exits with schema_too_new and does not come back, so the capacity drops to the 0.2.0 replicas: finish the rollout promptly. A 0.1 replica ignores the Minimum severity: it stores a lower Severity level on the Alert Groups it changes, with urgent true, since 0.2.0 writes routes.urgent. Until a later change of their Alerts or of the Route's Minimum severity computes the level again, the API and the list show such an Alert Group as not Urgent, while its messages and outgoing webhooks treat it as Urgent. Do not edit Routes or "critical is Urgent" until every replica runs 0.2.0: a 0.1 replica writes routes.urgent and the switch, which 0.2.0 reads differently. Migration 0045 runs in three transactions: the first adds alert_groups.first_acknowledged_by_user_id with its foreign key and alert_groups_first_acknowledged_by_check, both NOT VALID; the second validates them; the third fills the column in one UPDATE. The fill reads the created entries of the Timeline that is kept and, for each acknowledged Alert Group among them, its earliest acknowledged entry on timeline_entries_group_idx, and writes only the Alert Groups acknowledged within retention.alert_details. On a test machine (8 vCPU, PostgreSQL 17) it took 7 seconds for 200,000 Alert Groups, of which it filled 76,000, and 40 seconds for 1,000,000 Alert Groups with 3.3 million kept Timeline entries, of which it filled 380,000: about 100 seconds per million filled Alert Groups, nearly all of it writing the rows.     ALTER TABLE alert_groups VALIDATE CONSTRAINT alert_groups_first_acknowledged_by_user_id_fkey;
ALTER TABLE alert_groups VALIDATE CONSTRAINT alert_groups_first_acknowledged_by_check;
SET statement_timeout = 0;
UPDATE alert_groups g
SET first_acknowledged_by_user_id = f.actor_user_id
FROM (
    SELECT s.org_id, s.id, a.actor_user_id
    FROM alert_groups s
    CROSS JOIN LATERAL (
        SELECT e.actor_user_id
        FROM timeline_entries e
        WHERE e.org_id = s.org_id AND e.alert_group_id = s.id AND e.event = 'acknowledged'
        ORDER BY e.at, e.id

    (org_id, alert_group_id)
    WHERE state = 'pending' AND alert_group_id IS NOT NULL;
-- 0055

Going back to 0.1. Nothing runs down migrations in an installation: muster migrate takes no arguments, and the "Going back below 00NN" sentences above describe what the down migrations drop, which only Muster's tests run; they are not a supported way back. A 0.1.x binary on the 0.2.0 schema stops at start with the log event schema_too_new, naming the schema version of 0.2.0 and the one it knows ("database schema version N is newer than this binary knows (20)" on 0.1.4), and its muster migrate exits with 1. Going back to 0.1 means restoring the database backup taken before the upgrade together with the master keys of that time, and running 0.1 on it, as Upgrades describes; everything written since the upgrade is lost.

Image tags¶

The images are ghcr.io/muster-io/muster and the tags are:

  • vX.Y.Z: a release. Use it, so that an upgrade is a decision you make.
  • latest: the newest release that is not a prerelease. A prerelease tag, such as v1.4.0-rc.1, never moves it.
  • edge: the newest commit on master, a development image.
  • sha-<7 hex digits>: the development image of one commit.

Verify a release¶

A release is built by the workflow release.yml of the repository, on a tag vX.Y.Z. It signs the container image and the Helm chart with cosign, keyless, with the identity of that workflow run, so a valid signature proves that the image or the chart was built by that workflow on that tag. The development images, edge and sha-…, are not signed and carry no SBOM attestation: the workflow that builds them skips signing. Install cosign v3 or newer (the release signs with v3.1.3, in the new signature format), then verify the image:

VERSION=vX.Y.Z
cosign verify ghcr.io/muster-io/muster:$VERSION \
  --certificate-identity "https://github.com/muster-io/muster/.github/workflows/release.yml@refs/tags/$VERSION" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

It prints the verified signature and exits 0. To accept any release tag, replace --certificate-identity with --certificate-identity-regexp '^https://github\.com/muster-io/muster/\.github/workflows/release\.yml@refs/tags/v'. The signature covers the multi-architecture index and the image of each platform. To pin what you run, deploy the digest you verified, ghcr.io/muster-io/muster@sha256:…, rather than the tag.

The Helm chart is signed the same way, by the same workflow run. Its tag is the version without the v:

VERSION=vX.Y.Z
cosign verify ghcr.io/muster-io/charts/muster:${VERSION#v} \
  --certificate-identity "https://github.com/muster-io/muster/.github/workflows/release.yml@refs/tags/$VERSION" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

To install exactly the chart you verified, verify it by its digest and install by the same digest. helm pull prints the digest as Digest: sha256:…:

helm pull oci://ghcr.io/muster-io/charts/muster --version ${VERSION#v}
cosign verify ghcr.io/muster-io/charts/muster@sha256:… \
  --certificate-identity "https://github.com/muster-io/muster/.github/workflows/release.yml@refs/tags/$VERSION" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
helm install muster oci://ghcr.io/muster-io/charts/muster@sha256:… \
  --namespace muster --create-namespace -f values.yaml

The SBOM of the image is an attestation that BuildKit attaches when the image is pushed, not a cosign attestation. Read it with Docker:

docker buildx imagetools inspect ghcr.io/muster-io/muster:$VERSION --format '{{ json .SBOM }}'

It prints the software bill of materials, one per platform.

The archives are attached to the GitHub release: muster_<version>_<os>_<arch>.tar.gz for Linux and macOS on amd64 and arm64, checksums.txt with their SHA-256 sums, and one SPDX JSON software bill of materials per archive. Download the archive and checksums.txt into one directory and check it:

sha256sum --ignore-missing -c checksums.txt

On macOS use shasum -a 256 -c checksums.txt --ignore-missing. checksums.txt is not signed: it finds a broken or swapped download from the same release, not a swapped release. For that, verify the image.
