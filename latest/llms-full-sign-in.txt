# Sign-in

Everything in the web UI and the API works only after sign-in. No page and no read of the API is open to someone who has
not signed in. What is open is a short list of endpoints that cannot ask for a session:

- the sign-in itself: the list of sign-in methods, the password sign-in, the OpenID Connect redirect and its callback,
  and the page where a person sets a password from a setup link;
- [ingestion](https://muster-io.github.io/muster/latest/integrations/alertmanager.md) and the [Heartbeat](https://muster-io.github.io/muster/latest/integrations/heartbeat.md), which take an
  Integration token;
- the callbacks that Mattermost, Slack, Telegram and a [Bridge](https://muster-io.github.io/muster/latest/messengers/bridge.md) send to Muster, which each
  carry a secret or a signature of their own;
- the served API specification;
- the health checks and `/metrics`, on the internal listener, which is not meant to be reachable from outside the
  cluster.

Everything else answers `401` without a session or a token.

## Roles

Each User and Service account has one of three Roles, each a fixed set of Permissions:

| Role | May |
|---|---|
| Admin | everything: also configures Integrations, Routes, Connections and Destinations, manages Users, the OIDC settings, Service accounts, the Organization's settings, and reads the Audit log and the System status |
| Responder | what a Viewer reads, and acts on Alert Groups: acknowledges and takes over, resolves, snoozes, adds Notes and answers Reminders |
| Viewer | reads Alert Groups, Alerts, Integrations, Routes, Connections, Destinations, Link rules and Lookup tables, with secret values masked |

Every signed-in person also manages their own profile: password, TOTP, Account links and Personal access tokens. Every operation in the [API reference](https://muster-io.github.io/muster/latest/reference/api.md) names the Permission it needs.

## Ways to sign in

- **Local users.** An Admin creates a user with a login, and Muster returns a single-use link, valid for 24 hours
  (`auth.password_setup_link_ttl`), where the person sets a password of at least 12 characters
  (`auth.password_min_length`). Muster sends no email; the Admin hands the link over. The first Admin comes from
  `MUSTER_BOOTSTRAP_ADMIN_EMAIL` and its password at the first start, as the [Quick start](https://muster-io.github.io/muster/latest/quick-start.md) shows.
- **OpenID Connect.** People sign in at your identity provider, and a mapping from the groups in their token to Roles
  decides what they may do. [Sign-in with Keycloak](https://muster-io.github.io/muster/latest/sign-in/oidc-keycloak.md) and [Sign-in with GitLab](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md) are
  complete walkthroughs.
- **TOTP.** A second step with a one-time code from an authenticator app, for local and OIDC users alike; the
  Organization can require it. See [TOTP](https://muster-io.github.io/muster/latest/sign-in/totp.md).
- **Personal access tokens.** A person creates them in the profile for scripts. A token acts as its User, with at most
  that User's Permissions, and can be narrowed to fewer. It can expire (`token.expiry`; a token has no expiry unless
  you set one, and the page warns about that), and the Audit log names the token with the person. The API limits each
  token (`api.rate_limit`). See [API tokens and automation](https://muster-io.github.io/muster/latest/configure/api-tokens.md).
- **Service accounts.** An identity that is not a person, for automation such as a pipeline. It has a Role and any number
  of tokens, cannot sign in to the web UI, and cannot become the Owner of an Alert Group.

Operations that change one's own account, such as the password, TOTP, tokens and Account links, need the web session; a
token is refused there.

A web session ends after 12 hours without a request (`auth.session_idle_timeout`), or 7 days after sign-in
(`auth.session_lifetime`). Both are built in. A session of an OIDC user whose identity provider granted no offline
token — or, as GitLab, offers none — ends 12 hours after sign-in (`auth.oidc_fallback_session_lifetime`), and a
background re-check asks the identity provider about every OIDC user who has an offline token and a live session or a
usable Personal access token, every 15 minutes (`auth.oidc_recheck_interval`).

When the identity provider is in a network that Muster cannot reach, see [Closed networks](https://muster-io.github.io/muster/latest/sign-in/closed-networks.md).

## Add a User

An Admin adds a local user; a person who signs in through OpenID Connect gets their User at their first sign-in.

1. Open **Access → Users** and select **Create user**. Enter the **Name**, the **Login** and, if you like, the
   **Email (optional)**, and choose the [Role](https://muster-io.github.io/muster/latest/sign-in/index.md#roles). Select **Create**.

    ![The dialog Create user: the name Dana Lee, the login dana, an email and the Role Responder](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/index/01-create-user.png){ .screenshot }

2. Muster shows the **Password setup link** once. Copy it with **Copy** and hand it to the person yourself: Muster sends
   no email. The link works once, until the time the dialog names. In the screenshot it starts with
   `http://localhost:8080`, the address of a development installation; yours starts with your `MUSTER_PUBLIC_URL`.

    ![The dialog Password setup link: the link with Copy, until when it works, and that it is shown once](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/index/02-setup-link.png){ .screenshot }

3. The **Users** list shows the new User with the Role, the source, the sign-in method, the last sign-in, TOTP and the
   status. If the link is lost or expires, open the User and select **New password setup link**.

    ![The Users list: admin and Dana Lee, a local Responder who has not signed in yet](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/index/03-users.png){ .screenshot }

4. The person opens the link, sets a password, and signs in on **Sign in to Muster** with the login and the password.
   With OpenID Connect on, the page also offers **Sign in with {name}**.

    ![The sign-in page with the login dana and a password, and Sign in with the identity provider below](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/index/04-sign-in.png){ .screenshot }

## Your profile

Every signed-in person opens their own profile from the user menu, their name at the top right: **Profile**.

1. Under **Details**, change your **Name** and select **Save**. Under **Language and time zone**, choose the
   **Language** and the **Time zone** of the web UI; they apply at once. The time zone also sets when the Snooze
   presets you press in messengers end.

    ![The profile of Dana Lee: Details with the name, Language and time zone, Sign-in method and Password](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/index/05-profile.png){ .screenshot }

2. Under **Password**, enter the **Current password** and the new one twice, and select **Change password**; your other
   sessions are signed out. **Sessions** lists where you are signed in, and **Sign out everywhere** ends them all, this
   one too.

    ![The profile further down: Password, Two-factor authentication (TOTP) off, and Sessions with one active session](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/index/06-password-and-sessions.png){ .screenshot }

The profile also holds [TOTP](https://muster-io.github.io/muster/latest/sign-in/totp.md#enrol), the [messenger accounts](https://muster-io.github.io/muster/latest/messengers/account-links.md) and the
[Personal access tokens](https://muster-io.github.io/muster/latest/configure/api-tokens.md#create-a-personal-access-token).

## Sign-in needs HTTPS or localhost

The session cookie is `Secure`, so browsers keep it only on a page served over HTTPS or from the browser's own machine:
`localhost`, a name under `.localhost`, `127.0.0.1` or `[::1]`. On plain `http://` to any other address, such as
`http://192.0.2.10:8080`, the browser drops the cookie and every sign-in returns to the sign-in page. Muster says so in
two places:

- the sign-in page shows "Sign-in needs HTTPS or localhost" above the form when the browser does not treat the page as
  secure;
- the server logs [`public_url_insecure`](https://muster-io.github.io/muster/latest/reference/log-events.md#public_url_insecure) at WARN when it starts with
  `MUSTER_PUBLIC_URL` set to an `http://` address on any other host.

There are two ways out:

- **HTTPS.** Put a reverse proxy or an [Ingress](https://muster-io.github.io/muster/latest/install/helm.md#ingress) with a certificate in front of the app
  port 8080, set `MUSTER_PUBLIC_URL` to its `https://` address and restart Muster.
- **An SSH tunnel to localhost**, to try Muster on another machine without a certificate. On your own machine, run
  `ssh -L 8080:localhost:8080 <host>`, keep it open and browse to `http://localhost:8080`, with `MUSTER_PUBLIC_URL`
  set to `http://localhost:8080`. Safari may drop the cookie on `localhost` too: if sign-in still returns to the
  sign-in page there, use HTTPS or another browser.

## Link your messenger accounts

A button in Mattermost, Slack or Telegram acts as a Muster User only if the person who presses it has linked their
messenger account to their User. People do it themselves, from their profile, as [Link your messenger
accounts](https://muster-io.github.io/muster/latest/messengers/account-links.md) describes. Admins cannot do it for them: they see the links of every User and
can remove them, but they cannot create one for someone else. A press from an unlinked account changes nothing, and the
person is answered privately with a link to their profile.

# Sign-in with Keycloak

This page sets up sign-in through [Keycloak](https://www.keycloak.org/) with OpenID Connect (OIDC). Other identity
providers work the same way: Muster needs a confidential client with the authorization code flow, a claim that lists
the person's groups, and, for the background re-checks, the scope `offline_access` where the provider offers it.
[Sign-in with GitLab](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md) covers a provider that does not.

Muster talks to Keycloak over the **back channel**: it fetches the provider metadata (discovery) and the signing keys,
and exchanges the authorization code for tokens itself. Muster must therefore reach Keycloak over the network, directly
or through the proxy of the OIDC settings. If it cannot — Keycloak sits in a closed network and Muster outside it — use
[local users with TOTP](https://muster-io.github.io/muster/latest/sign-in/oidc-keycloak.md#when-muster-cannot-reach-the-identity-provider) instead.

In the examples, Keycloak runs at `https://keycloak.example.org` with the realm `ops`, and `MUSTER_PUBLIC_URL` is
`https://muster.example.org`.

## 1. Create the client

In the Keycloak admin console, open the realm, then **Clients → Create client**:

<!-- tablecheck: allow the names fit; the long values are URLs to copy, longer than a phone line in any layout -->

| Setting | Value |
|---|---|
| Client type | OpenID Connect |
| Client ID | `muster` |
| Client authentication | On (a confidential client with a client secret) |
| Authentication flow | **Standard flow** only; switch off Direct access grants, Implicit flow and Service accounts |
| Valid redirect URIs | `https://muster.example.org/api/v1/sessions/oidc/callback` and `https://muster.example.org/api/v1/me/oidc-identity/callback` |
| Web origins | leave empty: the browser never calls Keycloak from Muster's pages |

Both redirect URIs are `MUSTER_PUBLIC_URL` followed by a path: `/api/v1/sessions/oidc/callback` ends a sign-in, and
`/api/v1/me/oidc-identity/callback` ends linking an existing account to Keycloak from its profile. Register both, with
exactly the scheme, host and port of `MUSTER_PUBLIC_URL`.

Under **Advanced → Advanced settings**, set **Proof Key for Code Exchange Code Challenge Method** to `S256`. Muster
always sends a PKCE challenge, so this only makes Keycloak insist on it.

Then open **Credentials** and copy the **Client secret**. Note when it expires, if your realm rotates client secrets:
Muster warns two weeks before the date you enter (`oidc.secret_expiry_lead`).

## 2. Add the groups claim

Muster gives each person a Role from their groups. Keycloak puts groups into tokens only through a mapper:

1. Open the client → **Client scopes** → `muster-dedicated` → **Add mapper → By configuration → Group Membership**.
2. Set **Name** to `groups` and **Token Claim Name** to `groups`.
3. Switch **Full group path** off, so that the claim carries `oncall` rather than `/oncall`.
4. Switch on **Add to ID token** and **Add to userinfo**.

Muster reads the groups from the ID token, and from the userinfo endpoint when the ID token lacks the claim; the
userinfo answer must be plain JSON, not a signed JWT. The name of the claim is the **Groups claim** of the OIDC
settings; it is `groups` unless you change both.

An entry of the mapping may also read **another claim**, named in the entry, such as a claim of client roles added
by another mapper; Muster reads it the same way, from the ID token and then from userinfo. Without a claim, an entry
reads the groups claim. A group in an entry is matched exactly, or as a subtree `a/b/*`, which matches `a/b` and every
group below it at `/` boundaries — useful with **Full group path** on, where `/platform/*` matches `/platform` and
`/platform/sre`.

## 3. Allow `offline_access`

Muster asks for the scope `offline_access` at every sign-in, besides the scopes of the settings, from every identity
provider whose discovery lists it in `scopes_supported` or lists no scopes at all; Keycloak lists it. With it, Keycloak
returns an offline token, which Muster keeps encrypted and uses to **re-check every OIDC user in the background**
every 15 minutes (`auth.oidc_recheck_interval`): a person disabled or removed in Keycloak loses their Muster sessions
at the next re-check, without waiting for them to end.

Another identity provider may support `offline_access` without listing it in its discovery. Add `offline_access` to
the **Scopes** of the settings for it, and Muster requests it too. Never do so for GitLab, which offers no
`offline_access` and refuses such a sign-in with `invalid_scope` ([Sign-in with GitLab](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md)).

To allow it in Keycloak:

1. Make sure the realm role `offline_access` is a default role of the realm (**Realm settings → User registration →
   Default roles**), which it is in a new realm, or give it to the groups that use Muster.
2. Open the client → **Client scopes** and check that the client scope `offline_access` is assigned as **Optional**.

### Without `offline_access`

Sign-in still works when Keycloak does not grant `offline_access`, but Muster cannot re-check the person in the
background:

- there are no background re-checks for them;
- each of their OIDC sessions ends `auth.oidc_fallback_session_lifetime` (12 hours) after sign-in, even while in use,
  so that a person disabled in Keycloak is signed out within that time;
- their Personal access tokens work only while their last OIDC sign-in is within `auth.oidc_token_grace` (7 days);
  after that, the tokens are refused until they sign in through OIDC again.

## 4. Configure Muster

Sign in to Muster as an Admin and open **OIDC settings**, or use `PUT /api/v1/oidc-settings`:

<!-- tablecheck: allow the names fit; the long values are URLs to copy, longer than a phone line in any layout -->

| Setting | Value |
|---|---|
| Issuer URL | `https://keycloak.example.org/realms/ops` — the `issuer` of `https://keycloak.example.org/realms/ops/.well-known/openid-configuration`. Use `https`: over `http` the client secret and the tokens cross the network in clear text |
| Client ID | `muster` |
| Client secret | the secret of step 1; it is write-only: Muster shows only whether it is set and when it changed |
| Client secret expires on | the expiry date of the secret, if it has one |
| Display name | the name on the button "Sign in with {name}"; by default the host of the issuer URL |
| Scopes | `profile email`; `openid` is always added, and `offline_access` because Keycloak offers it |
| Groups claim | `groups` |
| Group mapping | for example `muster-admins` → Admin, `oncall` → Responder; each entry reads the groups claim unless it names another claim; when the entries map a person to several Roles, the highest wins |
| Role for users without a matching group | none (the default) refuses their sign-in; Viewer or Responder lets them in |
| Sync Role at sign-in | on (the default): Keycloak decides the Role at every sign-in and re-check; off: the mapping applies only when the user is created. A re-check reads the refreshed ID token: once a refreshed ID token has carried a claim, one that lacks it counts as no groups, so a person removed from every group is refused; a claim no refreshed ID token has carried yet is not decided then |
| Skip TOTP when the IdP asserted MFA | off by default; on skips Muster's own TOTP step when the ID token's `amr` claim says that Keycloak used multi-factor authentication. Keycloak sends `amr` only when the client has an *Authentication Method Reference (AMR)* mapper |
| Proxy | the HTTP, HTTPS or SOCKS5 proxy through which Muster reaches Keycloak, if it needs one |

The settings behind the three rows above Proxy are `oidc.unmatched_role` (none: sign-in is refused), `oidc.sync_role`
(on) and
`oidc.skip_totp_with_idp_mfa` (off).

In the web UI:

1. Open **Access → OIDC**. Under **Identity provider**, turn on **Allow sign-in through OIDC** and fill in the **Issuer
   URL**, the **Provider name** (the display name), the **Client ID**, the **Client secret** — **Set a value**, or
   **Replace** once one is set —, **Client secret expires on** and the **Scopes**.

    ![The OIDC settings: the issuer https://sso.example.org/realms/muster, the provider name Keycloak, the client muster and the scopes profile email](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/oidc-keycloak/01-identity-provider.png){ .screenshot }

2. Under **Roles**, enter the **Groups claim** and map each group with **Add IdP group**: the group's name and its
   Role. Choose the **Role for users without a matching group**, and whether to **Sync the Role at every sign-in** and
   to **Skip TOTP when the identity provider confirmed multi-factor authentication**. Set the proxy below if Muster
   needs one, and select **Save**.

    ![The Roles of the OIDC settings: the groups claim groups, muster-admins mapped to Admin and oncall to Responder](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/oidc-keycloak/02-roles.png){ .screenshot }

The screenshots show the form filled in, before **Save**.

Then press **Check connection**. The check fetches discovery through the saved settings and proxy and shows how the
request travelled (`direct` or `proxy`), how long it took, the endpoints Keycloak announced, the **Requested scopes**
of a sign-in (`openid offline_access profile email`) and that **Offline access** is offered. When the outbound
address policy blocks Keycloak or the proxy, the error names the rule.

Keycloak lists only standard claims in `claims_supported`, so until the first sign-in the check shows the warning *No
sign-in has carried the groups claim ‘groups’ yet, so group mappings have not matched anyone yet*
(`groups_claim_missing`) although the mapper of step 2 exists. The warning goes away at the first sign-in whose ID
token or userinfo carries the groups claim, and later checks no longer raise it; changing the groups claim, the issuer,
the client ID or the scopes starts over. A sign-in without the claim changes nothing: Keycloak leaves it out for a user
in no group. If the warning stays after a sign-in of a user in a group, the mapper is missing or not added to the ID
token. A mapper removed after it worked raises no warning: you notice it through refused sign-ins, whose Audit log
entry `session.oidc_refused` lists no groups; it lists the values of every claim the mapping read.

An entry that names another claim gets the same warning for its claim, which names it, until a sign-in carries that
claim. The check also keeps the claims Keycloak lists, for the editor to suggest.

The **Roles** section shows the claim of each entry under its group, read-only, by a short name with the full claim in
a tooltip; set an entry of another claim through `PUT /api/v1/oidc-settings`, as
`{"claim": "…", "group": "…", "role": "…"}` in `group_mappings`. A save on the page keeps the claim of every entry.

The settings also warn when the mapping is empty and users without a matching group get no Role
(`nobody_can_sign_in`), and two weeks before the client secret expires.

## 5. Sign in

Open Muster and press **Sign in with {display name}**. The first sign-in of a person creates their Muster user with
the Role of their groups. The login is Keycloak's `preferred_username`, else the email, else the subject. Muster never
merges accounts by login or email: when a local user already has the login, the sign-in is refused with "An account
with this login already exists. Sign in with it and link OIDC in your profile."

A person whose groups map to no Role is refused with "You have no access to Muster. Contact your administrator.", and
the Audit log entry `session.oidc_refused` lists the groups their token carried. A user with TOTP gives the code after
Keycloak, unless Keycloak asserted multi-factor authentication and the setting above skips it.

Other errors on the sign-in page: `account_disabled` (the Muster user is disabled or deleted), `oidc_disabled` (OIDC
was switched off), `invalid_request` (the sign-in took longer than 10 minutes, `oidc.auth_request_ttl`, or was
started in another browser) and `idp_error` (Keycloak reported an error, could not be reached, or answered with a
token that did not verify; the log event `oidc_sign_in_failed` says which).

## When Muster cannot reach the identity provider

OIDC needs the back channel from Muster to Keycloak. When Keycloak is inside a closed network that Muster cannot
reach, even through a proxy, use local users instead:

- an Admin creates each user and hands over the one-time password setup link (**Users → Create**);
- set **Organization → Security → TOTP required** to *everyone*, so that every user enrols TOTP at their first sign-in.

Local sign-in is always available, also next to OIDC, and the bootstrap Admin or `muster admin reset-password --actor
<name>` lets an operator in when the OIDC settings are broken.

# Sign-in with GitLab

This page sets up sign-in through GitLab with OpenID Connect (OIDC), on `https://gitlab.com` or on GitLab
self-managed. GitLab is an OIDC provider for its own users: a person signs in to Muster with their GitLab account, and
the groups they belong to in GitLab, and their role in them, decide their Role.

GitLab differs from [Keycloak](https://muster-io.github.io/muster/latest/sign-in/oidc-keycloak.md) in two ways that matter here:

- it puts group **paths** such as `platform/sre` into its claims: two groups claims, `groups` and `groups_direct`,
  and one claim per GitLab role — Owner, Maintainer and Developer;
- it does not offer the scope `offline_access`, so Muster cannot
  [re-check its users in the background](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md#no-offline-access).

Muster talks to GitLab over the **back channel**: it fetches the provider metadata (discovery) and the signing keys,
and exchanges the authorization code for tokens itself. Muster must therefore reach GitLab over the network, directly
or through the proxy of the OIDC settings. If it cannot, use
[local users with TOTP](https://muster-io.github.io/muster/latest/sign-in/oidc-keycloak.md#when-muster-cannot-reach-the-identity-provider) instead.

In the examples, GitLab self-managed runs at `https://gitlab.example.org`, and `MUSTER_PUBLIC_URL` is
`https://muster.example.org`. On `https://gitlab.com`, replace the first with `https://gitlab.com`.

## 1. Create the application

Muster is an OAuth application in GitLab. Create it where it suits you; in recent GitLab versions the pages are:

- **instance-wide**, on GitLab self-managed: **Admin → Applications → New application**;
- **for a group**: the group's **Settings → Applications → Add new application**;
- **for a user**: **Edit profile → Access → Applications → Add new application**.

Whoever owns the application, every user of that GitLab can authorize it; the Role mapping of
[step 3](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md#3-map-groups-to-roles) decides who gets in.

!!! warning "Every GitLab account can reach the sign-in"
    On `https://gitlab.com`, any gitlab.com account can authorize Muster's application. Keep **Role for users without
    a matching group** at **None** and map only groups of your own, so that a stranger's sign-in is refused. On GitLab
    self-managed the same applies to every user of the instance.

Fill in the form:

<!-- tablecheck: allow the names fit; the long values are URLs to copy, longer than a phone line in any layout -->

| Setting | Value |
|---|---|
| Name | `Muster` — GitLab shows it when it asks a person to authorize the application |
| Redirect URI | `https://muster.example.org/api/v1/sessions/oidc/callback` and `https://muster.example.org/api/v1/me/oidc-identity/callback`, one per line |
| Confidential | checked: Muster keeps the secret on the server |
| Trusted | optional, in the Admin area only: checked skips the screen where a person authorizes Muster at their first sign-in |
| Scopes | `openid`, `profile` and `email` |

Both redirect URIs are `MUSTER_PUBLIC_URL` followed by a path: `/api/v1/sessions/oidc/callback` ends a sign-in, and
`/api/v1/me/oidc-identity/callback` ends linking an existing account to GitLab from its profile. Register both, with
exactly the scheme, host and port of `MUSTER_PUBLIC_URL`.

Select **Save application**, then copy the **Application ID** and the **Secret**. GitLab shows the secret in full only
now; **Renew secret** makes a new one later.

## 2. Configure Muster

Sign in to Muster as an Admin and open **Access → OIDC**, or use `PUT /api/v1/oidc-settings`:

<!-- tablecheck: allow the names fit; the values are short or URLs to copy -->

| Setting | Value |
|---|---|
| Issuer URL | `https://gitlab.example.org`: the base URL of GitLab, including its relative URL path if it has one (for example `https://example.org/gitlab`), or `https://gitlab.com` |
| Client ID | the **Application ID** of step 1 |
| Client secret | the **Secret** of step 1; it is write-only: Muster shows only whether it is set and when it changed |
| Display name | the name on the button "Sign in with {name}", for example `GitLab`; by default the host of the issuer URL |
| Scopes | `profile email`; `openid` is always added, and `offline_access` is not, because GitLab does not offer it |
| Groups claim | `groups` or `groups_direct`, see [step 3](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md#3-map-groups-to-roles) |
| Group mapping | group paths, each of a claim, to Roles, see [step 3](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md#3-map-groups-to-roles) |

Every scope in the list must be one of the application's scopes: GitLab refuses a sign-in that asks for any other
scope with `invalid_scope`, so never add `offline_access` to the list for GitLab. The **Role for users without a
matching group** stays **None**, as the warning in [step 1](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md#1-create-the-application) says. The other settings — Role
sync, skipping TOTP and the proxy — work as on the [Keycloak page](https://muster-io.github.io/muster/latest/sign-in/oidc-keycloak.md#4-configure-muster).

## 3. Map groups to Roles

GitLab names each group by its full path, such as `platform` or `platform/sre`, and offers these claims:

`groups`
:   The paths of every group the person is a member of, directly or through an ancestor group: a member of
    `platform` is listed with `platform` and with each of its subgroups, such as `platform/sre`, but a member of
    `platform/sre` alone is not listed with `platform`: the groups above a person's own never appear. GitLab puts it
    in the userinfo answer, not in the ID token, and Muster reads it from there.

`groups_direct`
:   The paths of the groups the person is a direct member of, without the subgroups they reach through an ancestor.
    GitLab puts it in the ID token.

`https://gitlab.org/claims/groups/owner`, `…/maintainer` and `…/developer`
:   The role claims: each lists the groups where the person holds that GitLab role **directly** — never the subgroups
    they reach through an ancestor — and a person has only the claims of the roles they hold, so an Owner of
    `platform` has the owner claim `["platform"]` and no maintainer claim. GitLab lists all three in discovery and puts
    them in the userinfo answer, where Muster reads them.

Every entry of the mapping names a group and, optionally, the claim it reads; without a claim it reads the **Groups
claim** of the settings. A group is matched exactly, letter case included, so copy it from the group's URL, except a
**subtree** `a/b/*`, which matches `a/b` and every group below it at `/` boundaries: `platform/*` matches `platform`
and `platform/sre`, never `platformx`. There are no other wildcards. When the entries map a person to several Roles,
the highest wins.

For Admin, map the owner claim to your top group **exactly**. For example, to make the Owners of the group `corp`
Admins and everyone else in it a Responder:

`groups` `corp/*`
:   Responder: every member of `corp` or of any group below it. `groups` lists the groups a person is a member of
    and those below them, never the groups above, so a Developer of `corp/team-a` alone has `groups`
    `["corp/team-a"]`, which `corp/*` matches.

`https://gitlab.org/claims/groups/owner` `corp`
:   Admin: the people who hold Owner on `corp` itself.

A Developer of `corp/team-a` alone is a Responder, and a person outside `corp` matches no entry and is refused while
**Role for users without a matching group** is **None**.

!!! danger "A subtree entry of a role claim also matches the Owners of new subgroups"
    A role claim lists the groups where the person holds the role directly, and GitLab makes whoever creates a
    subgroup its direct Owner. A subtree entry such as the owner claim `corp/*` → Admin therefore makes an Admin of
    everyone allowed to create a subgroup below `corp` — by default its Maintainers too — once they create one. Map
    the owner claim, and the other role claims, to exact groups for Roles; if you do use a subtree entry, restrict
    **Roles allowed to create subgroups** in the settings of the top group (**Settings → General → Permissions and
    group features**) to Owners. An exact entry `corp/sre` does not match an Owner of `corp`, who holds that role in
    `corp/sre` only through its parent: add an entry for each group whose Owners should have the Role.

    Subtree entries are harmless in the identity provider entries of a Team: a Team grants no Permission and no Role
    ([Teams](https://muster-io.github.io/muster/latest/concepts/teams.md#membership-from-the-identity-provider)).

The OIDC page of Muster shows the claim of each entry under its group, read-only, by a short name such as `owner`
with the full claim in a tooltip, and keeps it when you save there; to add or change an entry of another claim, use
`PUT /api/v1/oidc-settings`:

```json
"group_mappings": [
  {"group": "corp/*", "role": "responder"},
  {"claim": "https://gitlab.org/claims/groups/owner", "group": "corp", "role": "admin"}
]
```

With only the groups claims, choose `groups` when membership of a parent group should count for its subgroups, as it
does in GitLab itself, and `groups_direct` when a Role should follow only the groups a person was added to by name.
For example, with the groups claim `groups`:

| IdP group | Role |
|---|---|
| `platform/muster-admins` | Admin |
| `platform/sre` | Responder |
| `platform` | Viewer |

Every member of `platform` is a Viewer at least, and also a member of `platform/sre` through it, so a Responder. To keep
`platform` members Viewers, use `groups_direct`: then only the people added to `platform/sre` itself are Responders.

Teams take their people from GitLab the same way: see
[Membership from the identity provider](https://muster-io.github.io/muster/latest/concepts/teams.md#membership-from-the-identity-provider).

## 4. Check the connection

Press **Check connection**. The check fetches discovery through the saved settings and proxy and shows how the
request travelled, how long it took, the endpoints GitLab announced, the **Requested scopes** of a sign-in
(`openid profile email` with the scopes above) and that **Offline access** is not offered. That is expected for GitLab
and is not a problem: it only means the rules of [No offline access](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md#no-offline-access) apply. The check also keeps
the claims GitLab lists, the role claims among them, and warns about each claim of the mapping that GitLab does not
list, until a sign-in carries it.

## 5. Sign in

Open Muster and press **Sign in with {display name}**. GitLab asks the person to authorize Muster once, unless the
application is trusted, and the first sign-in creates their Muster user with the Role of their groups. The login is
GitLab's username (`preferred_username`). As with any provider, Muster never merges accounts by login or email, and
a person whom no entry matches is refused; the [Keycloak page](https://muster-io.github.io/muster/latest/sign-in/oidc-keycloak.md#5-sign-in) lists the errors of
the sign-in page.

## No offline access

GitLab's discovery does not list `offline_access` in `scopes_supported`, so Muster does not request it. GitLab still
returns a refresh token, but without `offline_access` Muster does not keep it. Sign-in works, and for every person who
signs in through GitLab:

- there are no background re-checks;
- each OIDC session ends `auth.oidc_fallback_session_lifetime` (12 hours) after sign-in, even while in use, so that a
  person blocked or removed in GitLab is signed out within that time;
- their Personal access tokens work only while their last OIDC sign-in is within `auth.oidc_token_grace` (7 days);
  after that, the tokens are refused until they sign in through GitLab again.

The [Keycloak page](https://muster-io.github.io/muster/latest/sign-in/oidc-keycloak.md#without-offline_access) describes the same rules; see also
[Ways to sign in](https://muster-io.github.io/muster/latest/sign-in/index.md#ways-to-sign-in).

## Troubleshooting

`idp_error` with `invalid_scope` in the log event `oidc_sign_in_failed`
:   GitLab refused a scope Muster asked for: a scope in Muster's **Scopes** that the application does not have, or
    `offline_access` typed into that list. Remove it from the list, or add it to the application in GitLab.

The Role is not the one you expect
:   Check the claim of each entry: with `groups_direct`, membership through a parent group does not count, and a role
    claim lists only the groups where the role is held directly, so an exact entry of a subgroup does not match an
    Owner of its parent: add an exact entry for the parent rather than a subtree entry, which would also match the
    Owner of any new subgroup (see [step 3](https://muster-io.github.io/muster/latest/sign-in/oidc-gitlab.md#3-map-groups-to-roles)). The Audit log entry `session.oidc_refused` of a
    refused sign-in lists the values GitLab sent for every claim the mapping read.

# TOTP

TOTP is a second step in the sign-in: a six-digit code from an authenticator app, which changes every 30 seconds
([RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)). Every User, local or from OpenID Connect, can enrol it. It adds
protection to a password that leaks, and it is the second factor of installations that cannot use an identity provider:
see [Closed networks](https://muster-io.github.io/muster/latest/sign-in/closed-networks.md).

## Enrol

People enrol from their **profile**: they scan a QR code with the authenticator app and confirm with the first code.
Enrolment gives the person **10 recovery codes** (`auth.totp_recovery_codes`), each of ten characters and usable once. They are shown **once**:
save them somewhere safe. In the profile a person can generate new recovery codes, which replace the unused ones, and
remove TOTP. Removing it needs the current password (a local user) or a current code or recovery code.

1. Open your **Profile** and, under **Two-factor authentication (TOTP)**, select **Set up TOTP**.
2. Scan the QR code with your authenticator app, or enter the **Secret** by hand. Enter the code the app shows in
   **Code from the app** and select **Confirm**.

    ![Set up TOTP: the QR code and the secret, covered here, and the field Code from the app](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/totp/01-set-up.png){ .screenshot }

3. Muster shows the recovery codes once: **Copy codes**, keep them somewhere safe, and select **Continue**.

    ![Save these recovery codes: the ten codes, covered here, with Copy codes and Continue](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/totp/02-recovery-codes.png){ .screenshot }

4. The profile says since when TOTP is on and how many recovery codes are left, with **Regenerate recovery codes** and
   **Remove TOTP**.

    ![TOTP on: since when, 10 recovery codes left, and the buttons to regenerate the codes and to remove TOTP](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/totp/03-totp-on.png){ .screenshot }

A User has one enrolment. From then on, every sign-in asks for a code after the password, or after the redirect from the
identity provider: **Two-factor authentication** asks for the **Code**, and **Use a recovery code instead** takes a
recovery code.

![The sign-in step Two-factor authentication: the field Code, Continue, Use a recovery code instead and Sign out](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/totp/04-code-prompt.png){ .screenshot }

A recovery code is accepted in place of a code, and is then used up. Until the code is given, the session can only read
itself, sign out and give the code.

A wrong password or code counts as a failure, and failures slow the next attempts down per account and per source
address: after 3 in a row, each attempt waits twice as long as the one before, from 1 second up to 60 seconds.

## The policy

The Organization's policy **TOTP required** (`organization.totp_required`), under Organization → Security, has three
values:

| Value | Who must have TOTP |
|---|---|
| nobody (the default) | no one; everyone may enrol if they want |
| local users | every account that has a password |
| everyone | every account, local or from OpenID Connect |

1. Open **Organization → Security**.
2. Under **Two-factor authentication**, choose **TOTP required**: **Nobody**, **Local users** or **Everyone**. Select
   **Save**.

    ![Organization → Security with TOTP required set to Local users, saved](https://muster-io.github.io/muster/latest/assets/screenshots/sign-in/totp/05-policy.png){ .screenshot }

A person who falls under the policy and has no TOTP yet must enrol right after sign-in, before they can do anything
else. An account that signs in through OpenID Connect, whether created by it or linked to it, does not count as a local
user for this policy.

## OpenID Connect and the identity provider's multi-factor authentication

An identity provider may already ask for a second factor. When the OIDC setting `oidc.skip_totp_with_idp_mfa` (skip TOTP when the identity provider
asserted multi-factor authentication; off by default) is on, Muster skips its own code
for a sign-in where the provider's token says so in its `amr` claim. With the setting off, Muster asks for its own code
whenever the User has TOTP. See [Sign-in with Keycloak](https://muster-io.github.io/muster/latest/sign-in/oidc-keycloak.md).

## A lost authenticator

A person who lost both the device and the recovery codes needs a reset.

- **An Admin** resets it under **Access** → **Users**: **Reset TOTP**.
- **From the command line**, when no Admin can sign in:

  ```sh
  muster admin reset-totp --actor ops-alice alice
  ```

  `--actor` names the person who runs the command, and is required; the last argument is the login of the account. The
  command works on the database, with the same settings as the server.

A reset removes the TOTP and its recovery codes and ends the account's sessions. Under a policy that covers the account,
the person enrols again at the next sign-in. Without the policy, they can enrol again from the profile.

## What the Audit log records

The Audit log, under Organization → Audit log, records TOTP enrolled, removed and reset, with the User, who did it, and
the Transport (`cli` for the command). It never records a code. Failed sign-ins, with a wrong code too, are counted in
the metric `muster_login_failures_total` with the method `totp`; the chart rule `MusterLoginFailures` watches it.

# Closed networks

OpenID Connect needs a **back channel**: Muster itself calls the identity provider, to read its configuration and keys,
to exchange the code for tokens, and to check the sessions again later. Where Muster is outside the network of the
identity provider and cannot reach it, OpenID Connect cannot work, even though the people's browsers can. Typical cases
are an identity provider inside a company network and Muster in a cloud or a different site.

If a proxy can bring Muster to the provider, set it in the OIDC settings first: see [Proxies](https://muster-io.github.io/muster/latest/messengers/proxies.md).
When it cannot, use **local users with TOTP**. The [Keycloak page](https://muster-io.github.io/muster/latest/sign-in/oidc-keycloak.md#when-muster-cannot-reach-the-identity-provider)
describes the symptoms of an unreachable provider and does not repeat them here.

## Set it up

1. Sign in as the bootstrap Admin, whose email and password come from `MUSTER_BOOTSTRAP_ADMIN_EMAIL` and its password
   variable at the first start.
2. Under **Access** → **Users**, create a user for each person, with a login and a Role.
3. Hand each person the one-time setup link that Muster shows. It is valid for 24 hours and works once. Muster sends no
   email, so you pass it on yourself. The person sets a password of at least 12 characters.
4. Under Organization → Security, set **TOTP required** to **local users**, or to **everyone**. With the policy, the
   person enrols [TOTP](https://muster-io.github.io/muster/latest/sign-in/totp.md) right after the first sign-in and saves the 10 recovery codes. Without it, the policy
   would only be a wish: enrolment would be each person's choice.
5. Add [Personal access tokens](https://muster-io.github.io/muster/latest/sign-in/index.md#ways-to-sign-in) for scripts and Service accounts for automation. They do not
   depend on the identity provider.

Take care of the way back: keep at least two Admins, and keep the recovery codes of each. If the last Admin loses the
second factor, `muster admin reset-totp --actor <name> <login>` resets it from the command line, and
`muster admin reset-password --actor <name> <login>` sets a new password.

Local sign-in and OpenID Connect can run side by side. If the provider becomes reachable later, configure OIDC and let
people link it from their profile; their TOTP stays.
