# Messengers

Muster delivers Alert Groups to **Destinations**. A Destination is a place where Alert Groups arrive: a channel of a
messenger, or an outgoing webhook. There are five types:

- **Mattermost**, through a bot account on your Mattermost server;
- **Slack**, through the bot of a Slack app, to a channel the bot is a member of;
- **Telegram**, through a bot, to a channel with comments;
- **Bridge**, for any other messenger: a small service that you or someone else writes speaks the Bridge protocol with
  Muster and talks to the messenger;
- **Outgoing webhook**, which sends the lifecycle events of Alert Groups, or requests you build from templates, to any HTTP
  endpoint.

A **Connection** holds the credentials Muster uses to reach one messenger: a bot on a Mattermost server, the bot of a
Slack app, a Telegram bot, or a Bridge. Many Destinations can share a Connection. An outgoing webhook has no Connection;
the Destination carries its own address, Secrets and proxy.

To start, create the Connection, check it, create a Destination for a channel, and add the Destination to a Route. A Route
decides which Alert Groups reach which Destinations; see [Routes and Group keys](https://muster-io.github.io/muster/latest/concepts/routes-and-group-keys.md).

## What each Destination type can do

Every entry is true for this release. An entry that depends on the bridge says "if the bridge declares it": a Bridge
offers only what its `info` announces, and Muster adapts to the rest. [Write a bridge](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md) lists the
features.

Needs a Connection
:   - Mattermost — yes
    - Slack — yes
    - Telegram — yes
    - Bridge — yes
    - Outgoing webhook, events mode — no
    - Outgoing webhook, template mode — no

One message per Alert Group, kept up to date
:   - Mattermost — yes
    - Slack — yes
    - Telegram — yes
    - Bridge — yes
    - Outgoing webhook, events mode — no: one request per event
    - Outgoing webhook, template mode — yes, through your requests

Edits of the Root message
:   - Mattermost — yes
    - Slack — yes, no window known
    - Telegram — yes
    - Bridge — yes, until the bridge's edit window
    - Outgoing webhook, events mode — no
    - Outgoing webhook, template mode — yes, through the `update` request

Buttons
:   - Mattermost — yes
    - Slack — yes, with the Snooze menu
    - Telegram — yes
    - Bridge — if the bridge declares `buttons`
    - Outgoing webhook, events mode — no
    - Outgoing webhook, template mode — no

Without buttons
:   - Mattermost — the web UI and the API
    - Slack — the web UI and the API
    - Telegram — the web UI and the API
    - Bridge — [Text commands](https://muster-io.github.io/muster/latest/concepts/statuses-and-commands.md#text-commands) in the Thread if the bridge declares
      `thread_messages`; otherwise the web UI and the API
    - Outgoing webhook, events mode — the web UI and the API
    - Outgoing webhook, template mode — the web UI and the API

Thread
:   - Mattermost — replies under the Root message
    - Slack — replies under the Root message
    - Telegram — the comments of the Root message, in the channel's discussion group
    - Bridge — replies under the Root message
    - Outgoing webhook, events mode — no: each event is separate
    - Outgoing webhook, template mode — optional `reply_in_thread`, with an optional `open_thread`

Loud
:   - Mattermost — a new post with Mentions
    - Slack — a new message with Mentions
    - Telegram — a new message
    - Bridge — a new message that the bridge posts with `notify`
    - Outgoing webhook, events mode — `notify` is true
    - Outgoing webhook, template mode — `.Notify` is true

Quiet
:   - Mattermost — an edit, or a post without a Mention
    - Slack — an edit, or a message without a Mention
    - Telegram — an edit, or a message sent with `disable_notification`
    - Bridge — an edit, or a message without a notification if the bridge declares `quiet_messages`
    - Outgoing webhook, events mode — `notify` is false
    - Outgoing webhook, template mode — `.Notify` is false

Mentions
:   - Mattermost — nobody, `@channel` `@all` `@here`, users, Mattermost groups
    - Slack — nobody, `@channel` `@here`, users
    - Telegram — nobody, users
    - Bridge — nobody, users
    - Outgoing webhook, events mode — nobody, everyone, users, groups, as data
    - Outgoing webhook, template mode — the same, as data

Account links
:   - Mattermost — yes: a code the bot sends by direct message
    - Slack — yes: a code the bot sends by direct message
    - Telegram — yes: a link that opens the bot
    - Bridge — yes: a token sent to the bot, and a code if the bridge can find people and send direct messages
    - Outgoing webhook, events mode — not needed: no one presses anything
    - Outgoing webhook, template mode — not needed

Rate limits
:   - Mattermost — Connection 5 requests/s; Destination the same by default
    - Slack — Connection 50 requests/min; Destination 30 requests/min, sends and edits together
    - Telegram — Connection 15 messages/s; Destination 10 requests/min, sends and edits together
    - Bridge — Connection 10 requests/s, Destination 30 requests/min, or half of what the bridge's info declares
    - Outgoing webhook, events mode — Destination 5 requests/s
    - Outgoing webhook, template mode — Destination 5 requests/s

Edit window
:   - Mattermost — none by default; the server setting `PostEditTimeLimit` is unlimited, so keep it
    - Slack — none known for a bot's messages
    - Telegram — none for the bot's own messages
    - Bridge — the bridge declares it, or none; Muster publishes a new Root message past it
    - Outgoing webhook, events mode — not applicable
    - Outgoing webhook, template mode — the chat's own; Muster does not know it

Storms
:   - Mattermost — one Storm summary per Route
    - Slack — one Storm summary per Route
    - Telegram — one Storm summary per Route
    - Bridge — one Storm summary per Route
    - Outgoing webhook, events mode — every event is sent, no summary
    - Outgoing webhook, template mode — one Storm summary

Proxy
:   - Mattermost — on the Connection
    - Slack — on the Connection
    - Telegram — on the Connection
    - Bridge — on the Connection
    - Outgoing webhook, events mode — on the Destination
    - Outgoing webhook, template mode — on the Destination

Destination check
:   - Mattermost — yes
    - Slack — yes, `conversations.info`
    - Telegram — yes
    - Bridge — yes, `checkChannel`, which posts nothing
    - Outgoing webhook, events mode — no
    - Outgoing webhook, template mode — no

Test message and preview
:   - Mattermost — yes
    - Slack — yes, the test message cannot press its own button
    - Telegram — yes
    - Bridge — yes
    - Outgoing webhook, events mode — yes, sends the event `test`
    - Outgoing webhook, template mode — yes, sends the `create` request

Notes on the entries:

- **Rate limits.** These are the defaults of the limiters, and you can change them. Mattermost's own rate limit is off
  by default; when an administrator turns it on, it allows 10 requests per second per client address, so keep the
  limiters of all Connections to one server below that together. Slack limits each method per app and workspace, and
  about one message per second per channel; its Connection limiter is 50 requests a minute and its Destination limiter
  30. A Telegram chat takes about 20 messages and edits per minute, which is why its Destination limiter is half of
  that. A bridge says its own limits in its info, and its `rate_limited` answers always win. A `429` from a messenger
  holds the Destinations that share it, for as long as it asks.
- **Slack and Quiet.** Slack cannot send a message without a notification, so Quiet means "without a Mention"; an edit
  carries no Mention. See [Connect Slack](https://muster-io.github.io/muster/latest/messengers/slack.md#who-gets-notified).
- **Account links.** Pressing a button as a Muster user, and being Mentioned, need an Account link. See [Link your
  messenger accounts](https://muster-io.github.io/muster/latest/messengers/account-links.md).
- **Loud and Quiet.** Edits never notify anybody, so every Loud change is a new message. See [Loud and
  Quiet](https://muster-io.github.io/muster/latest/concepts/loud-and-quiet.md).
- **Edit windows.** See [Broken Destinations](https://muster-io.github.io/muster/latest/concepts/broken-destinations.md#republishing-past-an-edit-window).
- **Destination check.** It asks the messenger whether the bot can still post, without posting. Muster runs it when you save
  a Destination, from **Check**, and as the probe of a [Broken Destination](https://muster-io.github.io/muster/latest/concepts/broken-destinations.md) when nothing
  waits. An outgoing webhook has no Destination check, so a Broken one is probed by its next delivery.

# Connect Mattermost

Muster posts to Mattermost through the REST API with a **bot account**: one post per Alert Group, the **Root
message**, which Muster edits as the Alert Group changes, and replies in its **Thread** for what happens later. People
act on the Alert Group with the buttons of the post. Muster uses no incoming webhook and no plugin.

In the examples, `MUSTER_PUBLIC_URL` is `https://muster.example.org`, `MUSTER_INGEST_URL` is
`https://ingest.muster.example.org` and the Mattermost server is `https://chat.example.org`.

## Create the bot account

1. In the System Console, under **Integrations → Bot Accounts**, turn on **Enable Bot Account Creation**.
2. In **Integrations → Bot Accounts**, add a bot, for example `muster`. Give it the role **Member**: Muster needs no
   system admin role and no **post:all** or **post:channels** permission, because it posts only to channels the bot
   is a member of. With the role Member, the answers to button presses show in the Thread of the Root message; see
   [Where answers to presses show](https://muster-io.github.io/muster/latest/messengers/mattermost.md#where-answers-to-presses-show). The role Member is also enough to read the
   server's custom groups, which Muster lists so that a Team can be mentioned by its group; it needs no permission
   added for that ([Team mentions](https://muster-io.github.io/muster/latest/concepts/teams.md#team-mentions)). This was checked on Mattermost 11.2.2 with the
   Entry licence (F-122); groups synced from LDAP were not checked (F-121).
3. Copy the bot's access token. Mattermost shows it once.
4. Add the bot to the team, and to every channel a Destination posts to. A public channel is enough; a private channel
   works the same once the bot is a member.

The bot token works even when **Enable Personal Access Tokens** is off, its default.

## Create the Connection

1. In Muster, open **Connections**, select **Create connection** and choose **Mattermost**.
2. Enter a **Name** and the **Server URL**, the address people open Mattermost at, such as `https://chat.example.org`.
   Select **Set a value** next to **Bot token** and paste the bot's access token.

    ![The form of a new Mattermost Connection: the name, the server URL https://chat.example.org and the bot token](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/mattermost/01-new-connection.png){ .screenshot }

3. Select **Check connection**, below the form. The check reads the bot's own user with the token and shows the
   bot's name. When the bot may not make ephemeral posts, it passes with a warning: see
   [Where answers to presses show](https://muster-io.github.io/muster/latest/messengers/mattermost.md#where-answers-to-presses-show).

    ![The Connection check: connected as the bot, with the warning that answers to presses show in the Thread](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/mattermost/02-check-connection.png){ .screenshot }

4. Select **Save**. The saved Connection shows its **callback address**, which Mattermost calls when someone presses
   a button: `MUSTER_INGEST_URL` followed by `/api/v1/callbacks/mattermost/CN…`. In the screenshot it is
   `http://localhost:8081`, the ingest address of a development installation; yours starts with your
   `MUSTER_INGEST_URL`. [Let button presses reach Muster](https://muster-io.github.io/muster/latest/messengers/mattermost.md#let-button-presses-reach-muster) says what the server
   needs to call it.

    ![The card Button presses of the saved Connection: the callback address and the hint to allow its host in AllowedUntrustedInternalConnections](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/mattermost/03-saved-connection.png){ .screenshot }

## Check before saving

**Check connection** checks the values in the form, before anything is saved: in the form of a new Connection, as
above, and on the page of a saved one while the form holds changes. It saves nothing: no bot name is recorded and the
Audit log gets no entry.

- With the bot token typed in the form, the check reads the bot's own user at the server URL in the form, through the
  proxy in the form, and shows the bot's name.
- Without a token typed, the page of a saved Connection uses its stored token only when the server URL and the proxy
  are the saved ones: the stored token is sent only to the saved address, through the saved proxy. After a change of
  the server URL or of the proxy, the check makes only a dry probe: `GET <server>/api/v4/system/ping` without a token,
  which a Mattermost server answers to anyone with `200` and `"status":"OK"`. It tells a wrong address, a wrong path
  prefix (`404`) and a server that is not Mattermost apart, and the step **Token** asks you to type the bot token again
  to check the new address or proxy, or to save first. A new Connection without a token gets the dry probe alone too.

The check is `POST /api/v1/connections/checks`, which needs `connections:write`; with a Personal access token of an
Admin in `MUSTER_TOKEN`:

```sh
curl -X POST https://muster.example.org/api/v1/connections/checks \
  -H "Authorization: Bearer $MUSTER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"type":"mattermost","server_url":"https://chat.example.org","bot_token":"the-bot-token"}'
```

Add `"connection_id":"CN…"` to check the changes of a saved Connection, whose stored token the rule above may use.

## Add a Destination

A Mattermost Destination is one channel of one team that the bot is a member of.

1. Open **Destinations**, select **Create destination** and choose **Mattermost**.
2. Choose the **Connection**, the **Team** and the **Channel**. The list shows the channels the bot is a member of:
   add the bot to a channel to send there. The **Name** takes the channel's name; change it if you like.

    ![The form of a new Mattermost Destination: the Connection, the team dev and the channel alerts](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/mattermost/04-new-destination.png){ .screenshot }

3. Select **Save**. Saving runs the **Destination check**: the bot is a member of the channel, which belongs to the
   team and is not archived. A Destination that fails the check is not saved, and the check names what failed.

    ![The saved Destination alerts: Mattermost, Healthy](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/mattermost/05-saved-destination.png){ .screenshot }

4. Under **Test and preview**, on the tab **Test**, select **Send test message**. Muster posts a message marked 🧪;
   the result shows the request it sent and Mattermost's answer. Links in the screenshot start with
   `http://localhost:8080`, the address of a development installation; yours start with your `MUSTER_PUBLIC_URL`.

    ![The result of the test message: Test passed, Message: Sent, with the request to the Mattermost server](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/mattermost/06-test-message.png){ .screenshot }

    Muster then presses the message's first button through the bot. The step **Button press** says whether the press
    reached Muster at the callback address; when it did not, read
    [Let button presses reach Muster](https://muster-io.github.io/muster/latest/messengers/mattermost.md#let-button-presses-reach-muster).

    ![The step Button press of the test: Button presses reach Muster](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/mattermost/07-button-press.png){ .screenshot }

**Check** on the Destination page runs the Destination check at any time.

## Direct messages

Account links send a person a direct message from the bot: the bot opens the direct channel with the person's user id
and posts there. Make sure your server lets the bot open direct messages with the people who link their accounts — for
example, if **Enable users to open Direct Message channels with** is restricted to members of a team, add the bot to
the teams of those people.

## Let button presses reach Muster

A press on a button makes the Mattermost server call Muster at the Connection's callback address, which the Connection
page shows:

```text
https://ingest.muster.example.org/api/v1/callbacks/mattermost/CN…
```

When that address resolves to a private or otherwise reserved address — the usual case inside one network — the
Mattermost server refuses to call it unless the host is listed in **ServiceSettings.AllowedUntrustedInternalConnections**
(**Environment → Developer → Allow untrusted internal connections to** in the System Console). Add the host of
`MUSTER_INGEST_URL`, for example:

```json
"ServiceSettings": {
  "AllowedUntrustedInternalConnections": "ingest.muster.example.org"
}
```

Without it, a person who presses a button sees only a generic **Action integration error**; only the Mattermost server
log says why ("address forbidden … in a reserved range and not in AllowedUntrustedInternalConnections"). The test
message of a Destination presses its own button through the bot and tells you whether the press reached Muster.

Whatever the person who pressed must read — that the press was refused, that their Mattermost account is not linked
to Muster yet, or that the button could not be verified — arrives as a message only they can see. A press from an
account without an Account link changes nothing. A request that does not come from a button of a Muster post in one of
the Connection's channels gets no answer at all.

### How Muster knows a press came from Mattermost

Mattermost does not sign the requests it sends to Muster. Each button therefore carries, in its integration data, a
callback secret of its own: Muster derives it from the [master key](https://muster-io.github.io/muster/latest/operations/key-rotation.md) that signed the
button, the Connection and the button, and never stores it. The Mattermost server keeps the integration data to
itself, removes it from the posts it sends to apps and browsers, and returns it with a press. Muster checks the secret
before anything acts on the press, so a press made up from what a Telegram or Slack message, a bridge or the
[Request log](https://muster-io.github.io/muster/latest/operations/request-log.md) shows changes nothing and is answered "This button could not be verified;
nothing was changed." A [key rotation](https://muster-io.github.io/muster/latest/operations/key-rotation.md) gives the buttons of open Root messages new
secrets when it signs them again.

Root messages posted by a version of Muster that did not check callback secrets yet carry buttons without one. The first press on one of them
changes nothing: the person reads "These buttons are out of date and are being updated; nothing was changed. Press again
in a moment.", and Muster edits that Root message so that its buttons carry their secrets. The next press works. Any
change of the Alert Group edits its Root message the same way. Buttons in Thread replies, such as a Reminder's, are
never edited; an older Reminder's buttons stay refused, and the buttons on the Root message work.

### Where answers to presses show

Muster first sends the answer as an ephemeral message, which shows in the channel, marked "(Only visible to you)".
Mattermost allows that only with the `create_post_ephemeral` permission, which by default only the system admin role
has. Without it, Mattermost refuses the ephemeral message, and Muster returns the same text in its answer to the press:
Mattermost then shows it from **System** in the **Thread** of the Root message. With collapsed reply threads,
Mattermost's default, it is not shown in the channel view; the person opens the Thread to read it. Either way the answer
is never lost.

**Check connection** tells you which applies: when the bot's roles do not grant `create_post_ephemeral`, the check
passes with a warning that answers will show in the Thread of the Root message, and `muster doctor` prints the
Connection as a `WARN` line. The warning names the bot whose token the Connection holds, as `@username`, and the roles
Muster read for it, for example `system_user`, so you can see which account the token belongs to. To show answers in
the channel, give the bot that permission, for example the system admin role. Otherwise keep the role Member and let
people read the answers in the Thread.

Promote the bot account itself, not the person who owns it, and check that it is the bot the warning names: a bot of
another Connection, or an older token of another bot, keeps its own roles. As a system admin, open **Integrations →
Bot Accounts** from the product menu, select **Edit** on the bot, set **Role** to **System Admin** and select
**Update**; or run `mmctl roles system-admin <bot-username>`. Then run **Check connection** again: the warning is gone
once the bot's roles grant the permission.

## Rate limit

Mattermost's rate limit is off by default. When an admin turns it on (`RateLimitSettings.Enable`, which takes a server
restart), it allows 10 requests per second, with a burst of 100, **per client address**. All Connections of one Muster
installation to the same Mattermost server usually come from one address and share that bucket, so keep their limiters
together below it. The default limiter of a Connection is 5 requests per second. A `429` from Mattermost holds every
request of the Connection, to any of its Destinations, for the seconds of its `Retry-After`.

## Keep posts editable

Muster edits a Root message for as long as its Alert Group is open, which can be days. Keep
**ServiceSettings.PostEditTimeLimit** at `-1`, its default, so that posts can be edited at any age.

## What Muster posts

A Root message is one post with no text of its own and one attachment in the colour of its status. The attachment's
title is `#N` and the Alert Group's title, linked to the Alert Group page, with the status as a word; the Severity,
Route, Teams and Started are its short fields; the summary, the description, the key labels, the Alerts, the notices
and the footer are its text, with the links as its last line; and the buttons come under it. The labels, the Alerts and
the text of the Route's message are chosen on the Route: see
[Messages and templates](https://muster-io.github.io/muster/latest/configure/messages-and-templates.md#the-default-message), which shows the attachment, and
[Labels in the message](https://muster-io.github.io/muster/latest/configure/messages-and-templates.md#labels-in-the-message). A post is at most 16,383
characters; a long one drops its description first, then its Alerts, its summary and its key labels.

## Who gets notified

- **Edits notify nobody**, even an edit that adds a Mention. That is why every Loud event is a new post: a new Root
  message, or a reply in the Thread.
- **Thread replies notify the Thread's followers** by their own notification settings, and a Mention makes the person
  mentioned a follower of the Thread. "Quiet" therefore means "without a Mention", not "nobody notified".
- A Loud Root message carries its Mentions — `@channel`, `@here`, `@all`, a Mattermost group, or a person's
  `@username` through their Account link — as one line at the top of the attachment, directly under its title. There a
  person's `@username`, `@channel`, `@here` and `@all` notify as they do anywhere in a post (F-124), and so does a
  custom group's `@payments_team`, whose members are mentioned in an attachment and in a Thread reply alike; a custom
  group's setting to allow references cannot be turned off, so it can always be mentioned (F-123). The Mentions are
  those of the Destination's [Mention entries](https://muster-io.github.io/muster/latest/concepts/mentions.md); a person whom an entry names without an
  Account link is left out of the message. The post's own text is empty: everything is in the attachment, so
  the post shows its title once. What a notification shows follows from that: an email notification shows no content;
  a push notification, when the server's **PushNotificationContents** is `full`, and a desktop notification show the
  attachment's summary line — the status, `#N` and the title — which Muster sets as its `fallback` and the channel does
  not show; a push notification under `generic` shows a fixed text such as "… notified the channel." An edit removes
  the line of Mentions. A reply in the
  Thread carries its Mentions in its own text. A `{{ mention "channel" }}` in a Route's template shows in the post as
  text and, on a Loud Root message or Thread reply, adds its Mention to the line of Mentions.
- Alert data never mention anyone: an `@` in a label or annotation is shown as text and notifies nobody.
- The footer of a Root message — "Acknowledged by", "Snoozed by", "Resolved by" — writes a person with an Account link
  for the Connection as `@username`, so that Mattermost shows their name with their profile; a person without one is
  their Muster name as text. An edit notifies nobody, but a new post with the footer, after a republish, may notify that
  person.

## Check from the command line

`muster doctor` prints one line per Mattermost Connection and per Mattermost Destination with the same checks, without
sending anything.

# Connect Telegram

Muster posts to a Telegram **channel** through the Bot API with a **bot**: one channel post per Alert Group, the
**Root message**, which Muster edits as the Alert Group changes. Everything that happens later goes to the channel's
**discussion group**, the group that Telegram creates when comments are enabled on the channel. People act on the Alert
Group with the buttons under the post.

In the examples, `MUSTER_INGEST_URL` is `https://ingest.muster.example.org` and the bot is `@muster_alerts_bot`.

## Create the bot

1. In Telegram, open [@BotFather](https://t.me/BotFather) and send `/newbot`. Give the bot a name and a username, for
   example `@muster_alerts_bot`.
2. Copy the bot token that BotFather sends, such as `123456789:AA…`. Anyone with the token controls the bot; Muster
   stores it encrypted and never shows it again.
3. Leave the bot's privacy mode on, the default. Muster needs no other setting in BotFather.

## Create the Connection

1. In Muster, open **Connections**, select **Create connection** and choose **Telegram**.
2. Enter a **Name**, select **Set a value** next to **Bot token** and paste the bot token. Keep the **Bot API base
   URL** `https://api.telegram.org` unless Telegram is blocked in your network; for a proxy or another address, see
   [Telegram in restricted networks](https://muster-io.github.io/muster/latest/messengers/telegram-restricted-networks.md). Keep the **Update mode** **Long polling** unless
   Telegram can reach Muster: see [Long polling or webhook](https://muster-io.github.io/muster/latest/messengers/telegram.md#long-polling-or-webhook).

    ![The form of a new Telegram Connection: the name, the bot token, the default Bot API base URL and long polling](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/telegram/01-new-connection.png){ .screenshot }

3. Select **Check connection**, below the form. The check runs in steps and shows the latency of each and whether it
   went through the proxy:

    1. a dry probe, `GET <base>/bot0:x/getMe` without your token, which only a Bot API answers with `401` and JSON — it
       tells a wrong address, a wrong path prefix, a proxy that refuses or a web server that is not a Bot API apart
       before your token goes anywhere;
    2. `getMe` with your token, which names the bot;
    3. `getWebhookInfo`, which says whether a webhook is set and how many updates wait.

    ![The Connection check: the dry probe, getMe and getWebhookInfo passed, connected as the bot](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/telegram/02-check-connection.png){ .screenshot }

4. Select **Save**. On the saved Connection, **Check connection** records the bot, which the page then names.

    ![The saved Connection Telegram with its bot, the stored token and the default Bot API base URL](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/telegram/03-saved-connection.png){ .screenshot }

## Check before saving

**Check connection** checks the values in the form, before anything is saved: in the form of a new Connection, as
above, and on the page of a saved one while the form holds changes. It saves nothing: no bot name is recorded and the
Audit log gets no entry.

- With the bot token typed in the form, the check runs its three steps against the base URL in the form, through the
  proxy in the form, with that token.
- Without a token typed, the page of a saved Connection uses its stored token only when the base URL — a trailing `/`
  aside — and the proxy are the saved ones: the stored token is sent only to the saved address, through the saved
  proxy, since a proxy you have not saved would see it in the path of an `http` base URL. After a change of the base
  URL or of the proxy, the check makes only the dry probe there, `GET <base>/bot0:x/getMe` without your token, and
  `getMe` and `getWebhookInfo` ask you to type the bot token again to check the new address or proxy, or to save
  first. A new Connection without a token gets the dry probe alone too.

The check is `POST /api/v1/connections/checks`, which needs `connections:write`; with a Personal access token of an
Admin in `MUSTER_TOKEN`:

```sh
curl -X POST https://muster.example.org/api/v1/connections/checks \
  -H "Authorization: Bearer $MUSTER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"type":"telegram","bot_api_base_url":"https://api.telegram.org","update_mode":"long_polling",
       "bot_token":"123456789:AA…"}'
```

Add `"connection_id":"CN…"` to check the changes of a saved Connection, whose stored token the rule above may use.

## Enable comments on the channel

A Telegram Destination is a channel **with comments**. Comments on a channel post live in the channel's discussion
group, and Muster writes everything about an Alert Group after its Root message there.

1. Create the channel, or open an existing one.
2. In the channel's settings, open **Discussion** and add a group, or let Telegram create one. This enables comments,
   and Telegram links the group to the channel.

You never enter the group in Muster: the Destination check finds it through the channel.

## Make the bot an admin of the channel and of the group

1. In the channel's settings, under **Administrators**, add the bot. Telegram adds a bot to a channel only as an admin:
   added as a subscriber, it stays outside the channel. Allow it to **post messages** and to **edit messages of
   others**; Muster needs both, because it edits its own posts as the Alert Group changes.
2. In the discussion group's settings, under **Administrators**, add the bot as well. An admin may always post in the
   group. The bot must be an admin, not a plain member: Telegram does not send a bot that is a plain member the copies
   of the channel's posts in the group, which the Threads of the Root messages hang under.

## Add a Destination

A Telegram Destination is the channel only: Muster finds its discussion group.

1. Open **Destinations**, select **Create destination** and choose **Telegram**.
2. Choose the **Connection** and enter the **Channel**: its chat id, such as `-1001234567890`, or `@username` for a
   public channel. Give the Destination a **Name**.

    ![The form of a new Telegram Destination: the Connection, the channel @muster_alerts and the name alerts](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/telegram/04-new-destination.png){ .screenshot }

3. Select **Save**. Saving runs the **Destination check**:

    - `getChat` on the channel: it exists and is a channel, and it names its discussion group;
    - `getChatMember` for the bot in the channel: an admin allowed to post and to edit messages;
    - `getChatMember` for the bot in the discussion group: an admin there;
    - once those pass, `getChatMember` in the discussion group, once per person, for each person with a Telegram
      Account link of the Teams that name the Destination and each one whom an Escalation chain Paging in it can Page
      through a Schedule, the item **Members of the discussion group**, which always passes and names the people
      outside the group, whom a Mention in a Thread does not notify
      ([Unreachable On-calls](https://muster-io.github.io/muster/latest/concepts/schedules.md#unreachable-on-calls)); a person who left the group shows as
      outside only some time later, about a minute (F-128). A new Destination has no Team and no Route yet, so its
      save asks about nobody.

    A Destination that fails the check is not saved, and the check says what to fix:

    - "Comments are not enabled for this channel. Enable comments in the channel settings in Telegram; this creates
      its discussion group."
    - "The bot is not an admin of the discussion group {group}. Make the bot an admin there, allowed to post
      messages."
    - "The bot is not an admin of the channel.", "The bot may not post messages in the channel." or "The bot may not
      edit messages in the channel."

    The saved Destination shows the channel and the discussion group it found.

    ![The saved Destination alerts: Telegram, Healthy, the channel Muster alerts and its discussion group](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/telegram/05-saved-destination.png){ .screenshot }

4. Under **Test and preview**, on the tab **Test**, select **Send test message**. A message marked 🧪 appears in the
   channel; the result shows the request Muster sent, with the bot token as `bot[redacted]`, and Telegram's answer.
   Links in the screenshot start with `http://localhost:8080`, the address of a development installation; yours start
   with your `MUSTER_PUBLIC_URL`.

    ![The result of the test message: Test passed, Message: Sent, with the request to the Bot API](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/telegram/06-test-message.png){ .screenshot }

Muster keeps sending to that channel and that group: when comments are moved to another group later, or the
`@username` to another channel, the check fails with "The channel or its discussion group changed since the
Destination was saved. Save the Destination again." until you save it. **Check** on the Destination page runs the same
check at any time, and `muster doctor` prints one line per Telegram Destination with its result: a warning that names
the people of its Teams outside the discussion group, and the same warning as **Check** when the channel or its
discussion group changed since the Destination was saved. When Telegram refuses
the bot later — for example, someone removed its admin rights — the Destination becomes **Broken**; Muster runs the
same check every few minutes while nothing waits for the Destination, and ends the Broken state once the check passes
again.

## Long polling or webhook

Muster receives the bot's updates — button presses and the messages of the discussion group — in one of two **update
modes**, set on the Connection:

- **Long polling**, the default. The Leader asks Telegram for updates with `getUpdates`. Muster needs no public address:
  it only calls out to Telegram. Only one process may poll a bot: when a second one starts — another
  Muster installation with the same token, or a test script — Telegram ends one of the polls with `409 Conflict`, and
  the two then take turns. Muster backs off and logs `telegram_poll_conflict`; the Destination does not become Broken.
  Give each installation its own bot.
- **Webhook**. Telegram posts each update to Muster at
  `https://ingest.muster.example.org/api/v1/callbacks/telegram/CN…`, under `MUSTER_INGEST_URL`, with a secret token
  header that Muster checks. Saving the Connection in this mode calls `setWebhook`; leaving the mode, or deleting the
  Connection, calls `deleteWebhook`. Use the webhook mode when Telegram can reach `MUSTER_INGEST_URL` over HTTPS.

Where Telegram is blocked, a Connection can reach the Bot API through a proxy or through another Bot API address; see
[Telegram in restricted networks](https://muster-io.github.io/muster/latest/messengers/telegram-restricted-networks.md).

## Join the discussion group and mute the channel

For the people on call:

- **Join the discussion group, and mute the channel itself.** Telegram copies every channel post into the discussion
  group, so each new Alert Group reaches the members of the group once, through its copy, with the Thread of its
  replies under it.
- Only members of the discussion group are notified about the replies in a Thread — even a reply that mentions them.
  Someone who only subscribed to the channel sees the Root messages, but not what happens to them later.
- Muting the discussion group does not hide a Mention from an ordinary member: a Mention in a comment rang a member who
  had muted the group, on the desktop and on the phone (F-129). The creator of the group, who is anonymous in it, was
  not rung by a Mention in a group they had muted, so a person who created the discussion group or is anonymous in it
  should not mute it. The Destination check cannot see that.

Telegram mentions only people, by a link to their account; a Destination's
[Mention entries](https://muster-io.github.io/muster/latest/concepts/mentions.md#telegram) offer a person and "On-call of a Team", and no group, Team or
everyone in the chat. A person whom an entry names without a Telegram Account link is left out of the message.

## Known limitation: Quiet Root messages ring the group

A Quiet Root message is sent with `disable_notification`, which in Telegram silences the notification but does not
remove it. Members of the discussion group still get a notification **with sound** for every new Alert Group, because
Telegram notifies them about the copy of the post in the group, and that copy cannot be sent without sound.

## What Muster sends

- The Root message is a regular message in Telegram's HTML, with the layout of
  [Messages and templates](https://muster-io.github.io/muster/latest/configure/messages-and-templates.md#the-default-message): the title `#N` and the Alert
  Group's title, bold and linked to the Alert Group page, with the status as a word and its emoji; the fields as lines
  `Severity: warning`; the summary and the description; one line of key labels; the Alerts on one line by the label that
  tells them apart — never a table, which phones cannot show; the notices; the footer; and the line of links that starts
  with "Open in Muster", with the buttons as the inline keyboard. A Route with the Fallback template shows its labels in
  an expandable quote instead. The footer — "Acknowledged by", "Snoozed by", "Resolved by" — names a person with a
  Telegram Account link by a link to their account with their Muster name, as a Mention does, and anyone else by their
  name as text. Alert data are escaped, so a label value cannot format the message or mention anyone. A message is at
  most 4,096 characters: a long one drops its description first, then its Alerts, its summary and its key labels, but
  always keeps its title, status, fields, footer, buttons and link to Muster.
- Every edit of the Root message carries all its buttons again, because Telegram removes the buttons of a message
  edited without them. The bot may edit its own messages at any age.
- Muster never replies inside the channel: a reply there would be a new post that notifies every subscriber.
- The bot token never appears in a log line, an error, the Timeline or a metric: logs show the scheme and host of the
  Bot API address only, and the token in a request path is written as `bot[redacted]`.

# Telegram in restricted networks

Muster talks to Telegram only by calling out to the Bot API, `https://api.telegram.org` by default. Where the network
of your installation cannot reach it — Telegram is blocked, or the cluster has no direct way out — there are three
ways to reach it. Use them in this order:

1. [A proxy on the Connection](https://muster-io.github.io/muster/latest/messengers/telegram-restricted-networks.md#1-a-proxy-on-the-connection), when a proxy can reach Telegram.
2. [A reverse proxy under your own domain](https://muster-io.github.io/muster/latest/messengers/telegram-restricted-networks.md#2-a-reverse-proxy-under-your-own-domain), when you run a host that can
   reach Telegram.
3. [A self-hosted Bot API server](https://muster-io.github.io/muster/latest/messengers/telegram-restricted-networks.md#3-a-self-hosted-bot-api-server), only when neither of the first two works. It has
   sharp edges that the first two avoid.

All three keep the bot in Telegram's cloud or move it to one server you control; none needs a change to the
Destinations.

## 1. A proxy on the Connection

Each Connection may send its requests through its own proxy, while the rest of Muster — other Connections, the
identity provider, outgoing webhooks — keeps its own path. On the Connection page, under **Proxy**, turn on
**Use a proxy** and set:

- **Type**: HTTP, HTTPS or SOCKS5;
- **Address**: `host:port` of the proxy;
- **Username** and **Password**, if the proxy asks for them. The password is stored encrypted and never shown again.

Leave the **Bot API base URL** at `https://api.telegram.org`: the HTTPS connection to Telegram runs through the proxy
end to end, so the proxy never sees the bot token in the request path. Press **Check connection**: every step shows
its latency and whether it went "through the proxy" or "direct", and a proxy that refuses Muster's credentials is
named as such. Pressed before you save a new proxy, the check sends the stored token nowhere and makes only the dry
probe through it, unless you type the bot token again (see [Check before saving](https://muster-io.github.io/muster/latest/messengers/telegram.md#check-before-saving)).

The proxy's own address is checked by the Organization's outbound address policy (**Outbound addresses**,
`/admin/organization/outbound`) like any other target: the standard policy allows private addresses and blocks
loopback; the strict policy blocks a proxy on a private address unless an allowed network covers it. `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` are never
read; the proxy is set only on the Connection.

## 2. A reverse proxy under your own domain

When a host that you run can reach `api.telegram.org` — for example a small virtual machine in another network — put
a reverse proxy on it, under a name of your installation's own domain such as `tg.muster.example.org`, in front of
`api.telegram.org`. Muster then calls your domain, and only that host talks to Telegram.

The reverse proxy must:

- connect to `api.telegram.org` over HTTPS with the upstream **SNI** and the **`Host`** header set to
  `api.telegram.org`;
- allow the upstream to answer for longer than the long-polling timeout. In the long polling update mode, Muster asks
  Telegram to hold each `getUpdates` request open for up to 25 seconds and waits up to 35 seconds for the answer; give
  the proxy timeouts of 60 seconds;
- limit the request **body size**. Muster sends no files, only messages of at most 4,096 characters and their
  buttons, so 1 MB is plenty;
- turn the **access log** off, or write it without the request URI: every request path carries the bot token, as in
  `/bot123456789:AA…/sendMessage`;
- answer only Muster: put everything under a **secret path prefix**, a long random string that is never logged, and
  refuse every other path, or allow only Muster's egress addresses with an address **allowlist**, or both.

Then set the Connection's **Bot API base URL** to the reverse proxy, with the prefix:
`https://tg.muster.example.org/8f1c2e…`. Muster sends its requests to `<base>/bot<token>/<method>`. A new base URL
needs the bot token again, so that the stored token never reaches an address you did not mean; type it again and press
**Check connection** before you save: the check runs its three steps against the new address with the typed token;
without the token it makes only the dry probe there (see [Check before saving](https://muster-io.github.io/muster/latest/messengers/telegram.md#check-before-saving)). Its
first step is a dry probe, `GET <base>/bot0:x/getMe` without your token, which
`api.telegram.org` answers with `401` and JSON: it tells a wrong host, a wrong path prefix or a server that is not a
Bot API apart before your token goes anywhere. Use an `https` base URL; with `http`, Muster warns that the token
travels in clear text.

### nginx

```nginx
server {
    listen 443 ssl;
    server_name tg.muster.example.org;
    ssl_certificate     /etc/nginx/tls/tg.muster.example.org.crt;
    ssl_certificate_key /etc/nginx/tls/tg.muster.example.org.key;

    # Every request path carries the bot token.
    access_log off;
    client_max_body_size 1m;

    # The secret path prefix; replace it with your own long random string.
    location /8f1c2e…/ {
        # An address allowlist instead of, or besides, the prefix:
        # allow 203.0.113.0/28;
        # deny all;

        proxy_pass https://api.telegram.org/;
        proxy_ssl_server_name on;
        proxy_ssl_name api.telegram.org;
        proxy_ssl_verify on;
        proxy_ssl_trusted_certificate /etc/ssl/certs/ca-certificates.crt;
        proxy_set_header Host api.telegram.org;
        proxy_http_version 1.1;

        # Above the long-polling timeout of getUpdates.
        proxy_connect_timeout 10s;
        proxy_send_timeout 60s;
        proxy_read_timeout 60s;
    }

    location / {
        return 404;
    }
}
```

`proxy_pass` with a trailing `/` strips the prefix, so Telegram receives `/bot<token>/<method>`. nginx's error log
names the request of a failed upstream call too; keep it where only administrators can read it.

### Caddy

```caddy
tg.muster.example.org {
    # Caddy writes no access log unless the site has a log directive: leave it out.
    request_body {
        max_size 1MB
    }

    # The secret path prefix; replace it with your own long random string.
    handle_path /8f1c2e…/* {
        # An address allowlist instead of, or besides, the prefix:
        # @outside not remote_ip 203.0.113.0/28
        # respond @outside 404

        reverse_proxy https://api.telegram.org {
            header_up Host api.telegram.org
            transport http {
                tls_server_name api.telegram.org
                # Above the long-polling timeout of getUpdates.
                dial_timeout 10s
                response_header_timeout 60s
            }
        }
    }

    handle {
        respond 404
    }
}
```

`handle_path` strips the prefix before the request goes upstream. Caddy gets and renews the certificate of
`tg.muster.example.org` itself. Caddy's error log entries carry the request URI, with the token, when an upstream
call fails; keep that log where only administrators can read it.

## 3. A self-hosted Bot API server

Telegram publishes the source of its Bot API server
([tdlib/telegram-bot-api](https://github.com/tdlib/telegram-bot-api)), and a bot can be moved to a server you run.
That server connects to Telegram's data centres itself, over Telegram's own protocol, not through `api.telegram.org`;
it needs a direct route to them (its `--proxy` option applies only to the webhook requests it sends, not to its
connection to Telegram). Use it only when neither a proxy nor a reverse proxy works: it changes
where the bot lives, and every warning below applies.

- **It needs an `api_id` and an `api_hash`.** The server starts only with `--api-id` and `--api-hash`, which you
  register at [my.telegram.org](https://my.telegram.org) with a personal Telegram account. Use a **dedicated** account
  for it, not a person's own: the server's access depends on that account.
- **A bot lives on one server at a time.** While it is on your server, Telegram's cloud does not serve it, and the
  other way round. Every installation and every script that uses the token must use the same server.
- **`logOut` drops unread updates, and the way back to the cloud is closed for 10 minutes.** Moving a bot off the
  cloud starts with `logOut` on `api.telegram.org`. Updates that Muster has not fetched by then — button presses and
  messages of the discussion group — are lost, and after `logOut` the bot cannot log in to the cloud again for
  10 minutes.
- **Any request with the bot's token to `api.telegram.org` moves the bot back to the cloud, silently.** Even a `getMe`
  from a script or a health check on another host is enough. Muster keeps sending to your server, which no longer
  receives the bot's updates: button presses and messages of the discussion group go missing without an error. Never call
  `api.telegram.org` with this token from anywhere while the bot is on your server.
- **The server has no authentication of its own.** Anyone who reaches it can use it with any bot token. Never expose
  it to the internet or to networks other than Muster's; put it on a private address that only the replicas reach.
- **Tokens are visible on its statistics port.** `--http-stat-port` serves statistics that include the bots' tokens.
  Leave it off, or bind it to loopback with `--http-stat-ip-address 127.0.0.1` so that it stays local.
- **Do not use `--local`.** In local mode the server accepts local paths and `file://` URIs in requests and answers
  with absolute paths of its own disk, so anyone who reaches it can make it serve the server's files. Muster sends
  and receives no files and needs none of it.
- **There are no releases.** The project publishes no releases or tags, and container images built from it carry no
  version you can rely on. Build your own image, or pin a third-party image by **digest** (`image@sha256:…`), never by
  a tag such as `latest`.
- **Route `MusterDestinationBroken` of Telegram Destinations elsewhere.** When the server stops, every Telegram
  Destination of that bot becomes Broken at once. Route the Internal alert
  [`MusterDestinationBroken`](https://muster-io.github.io/muster/latest/operations/runbooks/MusterDestinationBroken.md) of Telegram Destinations to a
  Destination that is not in Telegram — Mattermost or an outgoing webhook — and its chart rule around Muster.

The server's address is an ordinary target of the outbound address policy: the standard policy allows a private
address and blocks loopback.

### Move a bot between servers

Muster has no wizard for this; the move is a **manual** procedure. Plan for a short gap in which presses and messages
of the discussion group are lost.

What Muster does with `deleteWebhook`: it calls `deleteWebhook` only when a Connection leaves the webhook update mode
— saved from Webhook to Long polling — and calls it at the base URL saved before, the server the bot is leaving. When
that call fails, the save fails ("deleteWebhook failed: …") and nothing changes. Changing only the base URL while the
Connection stays in the webhook mode calls `setWebhook` at the new base URL and never `deleteWebhook` at the old one.
Deleting a Connection in the webhook mode also calls `deleteWebhook`, best effort, at its saved base URL: the outcome
is logged (`telegram_webhook_deleted` or `telegram_webhook_delete_failed`) and never fails the deletion. Muster never
calls `logOut` or `close`.

From Telegram's cloud to your server:

1. Start the Bot API server as above and check from a replica that it answers:
   `curl -s http://bot-api.internal.example.org:8081/bot0:x/getMe` returns `401` and JSON. The server listens on
   plain HTTP (port 8081 by default); with an `http` base URL Muster warns that the token travels in clear text,
   which is acceptable only on a private network or through a tunnel.
2. If the Connection uses the webhook update mode, switch it to **Long polling** and save **while the old server
   still answers**, so that Muster's own `deleteWebhook` reaches it. If the save fails, fix the path to the old server
   first.
3. Stop every other process that uses the bot's token.
4. Optionally call `deleteWebhook` yourself on the old server, then `logOut`:

    ```sh
    curl -s "https://api.telegram.org/bot$TOKEN/deleteWebhook"
    curl -s "https://api.telegram.org/bot$TOKEN/logOut"
    ```

    The `deleteWebhook` before `logOut` is a best-effort step: if it fails, go on with `logOut`; it does not stop the
    move.
5. On the Connection, set the **Bot API base URL** to your server, enter the bot token again, and save.
6. Press **Check connection**: the dry probe, then `getMe` and `getWebhookInfo` with your token against the saved
   base URL. Run `muster doctor` too; it checks the saved Connections the same way.
7. Switch back to the webhook update mode if you used it: Muster calls `setWebhook` on your server.

From one server you run to another, use the same steps on the old server, as Telegram documents in
[Moving a bot from one local server to another](https://github.com/tdlib/telegram-bot-api#moving), in one of two ways:

- call `logOut` on the old server instead of on `api.telegram.org`; updates not yet fetched are lost;
- or call `deleteWebhook` and then `close` on the old server, and move the bot's subdirectory — named by the bot's
  user id, the number before the colon in its token — from the old server's working directory to the new server's;
  no updates are lost. `close` answers `429` during the first 10 minutes after the bot started on that server.

Back to Telegram's cloud: the same steps in the other direction — switch to long polling while your server still
answers, `logOut` on your server, then set the base URL back to `https://api.telegram.org` with the token. The cloud
takes the bot back only when 10 minutes have passed since its `logOut` from the cloud.

See also Telegram's [`logOut`](https://core.telegram.org/bots/api#logout),
[`close`](https://core.telegram.org/bots/api#close) and
[Using a Local Bot API Server](https://core.telegram.org/bots/api#using-a-local-bot-api-server).

# Connect Slack

Muster posts to Slack through the Web API with the **bot** of a Slack app that you create from a manifest and install in
your workspace: one message per Alert Group, the **Root message**, which Muster edits as the Alert Group changes, and
replies in its **Thread** for what happens later. People act on the Alert Group with the buttons of the message and its
**Snooze…** menu. Muster uses no incoming webhook, no Events API subscription and no user token.

In the examples, `MUSTER_PUBLIC_URL` is `https://muster.example.org` and `MUSTER_INGEST_URL` is
`https://ingest.muster.example.org`.

## Socket Mode or HTTP

A button press reaches Muster in one of two **event modes**, set on the Connection (`connection.slack.event_mode`).
Choose before you create the app, because the app's manifest differs.

Socket Mode
:   The Leader holds a WebSocket connection to Slack, so Slack needs no address of Muster: Muster only calls out. It is
    the way when Muster has no address that Slack can reach. It needs the app-level token. Only the Leader holds the
    socket, so a press made while the Leader changes is lost: the person sees Slack's error, and Muster does not count
    on Slack to send it again. A handover takes well under a minute; see
    [High availability](https://muster-io.github.io/muster/latest/operations/high-availability.md).

HTTP
:   Slack posts every press to the Connection's callback address, which the Connection page shows:

    ```text
    https://ingest.muster.example.org/api/v1/callbacks/slack/CN…
    ```

    Slack must reach this address over HTTPS. Any replica receives the press, so no press is lost while the Leader
    changes. It needs the app's Slack signing secret: Muster verifies the signature of every press with it, and
    refuses a request whose timestamp is further than `slack.request_tolerance` (5 minutes) from its own clock, so keep
    the clocks of Muster's nodes right. A request with a wrong or missing signature, a stale timestamp, an unknown
    Connection or a Connection in Socket Mode is answered `401` with the same body, which reveals nothing about which
    Connections exist; a body over 1 MiB, or one without a `payload`, is answered `400`.

    If Slack is the only client outside your network that reaches the ingest listener, expose only `/api/v1/callbacks/`
    on the address Slack reaches, for example with a reverse proxy that forwards that path alone to the ingest port.
    `MUSTER_INGEST_URL` is also the address of Alertmanagers and Heartbeats: when they come from outside too, publish
    their paths as well, or give Slack's callbacks a route of their own. See
    [The two public addresses](https://muster-io.github.io/muster/latest/install/helm.md#the-two-public-addresses).

A Slack app sends its presses to the sockets alone while its Socket Mode is on, and over HTTP alone while it is off, so
the app and the Connection must agree: a Connection receives presses only in its own mode.

### One Slack app per Connection

Slack hands each press to any one of the app's open socket connections, and Muster binds a press to a Destination of
the Connection that receives it. Two Connections on one Slack app, in one Muster or in two, would therefore share its
presses at random, and a press that reaches the wrong Connection is refused as "This button could not be verified".
Over HTTP an app has one Request URL, so it serves one Connection. Create a Slack app for each Connection, a test copy
of Muster included.

Muster notices it. When Slack tells the Leader that the app has more socket connections than the Leader holds, another
program is connected to the same app, usually a second Connection or Muster, or a script: the **Check connection** of a
Connection in Socket Mode passes with the warning `another_client_connected`, the Connection page shows the same
warning, `muster doctor` prints a `WARN` line, and the Leader logs
[`slack_socket_shared`](https://muster-io.github.io/muster/latest/reference/log-events.md#slack_socket_shared). Presses go on working, but some of them are
lost to the other program. Muster takes the count at each `hello`: when a socket reconnects, at the planned refresh
hours after the previous one, and when the Connection is saved with a change, which restarts its socket at once. So the
warning can stay for hours after its cause is gone; to clear it, save the Connection with its app-level token entered
again. How long Slack counts the connection of a Leader that crashed has not been verified.

### What the manifest sets

The app and its bot are named **Muster**. The bot posts under the name in the app's settings: Muster does not ask for
`chat:write.customize`, so a name that a message carries would be ignored. To use another name, change both names in
the manifest.

The Messages tab is on and read-only
:   Account links send a person a code by direct message from the bot, and the direct messages of an app show in its
    Messages tab. Read-only means that the person reads the code and cannot write to the bot. Keep the tab on: Slack
    documents that with it off it refuses the bot's direct message, and the request for a code then fails with the
    problem `messages_tab_disabled` (`409`), which has not been seen yet on a real workspace. A refused request still
    counts toward the limits of Account links, 5 requests an hour for a person and 3 from a person for one Slack
    account (`account_link.slack_code_requests`), so after you turn the tab on again, a person who tried several times
    may have to wait up to an hour. Turn it on under **App Home → Show Tabs → Messages Tab**. See [Link
    Slack](https://muster-io.github.io/muster/latest/messengers/account-links.md#link-slack).

The Home tab is off
:   Muster publishes no Home tab.

Interactivity is on
:   Buttons and menus send nothing to Muster without it. Over HTTP it holds the Request URL.

Socket Mode is on, or off for HTTP
:   See [Socket Mode or HTTP](https://muster-io.github.io/muster/latest/messengers/slack.md#socket-mode-or-http).

Token rotation is off
:   With rotation, the bot token expires and Slack issues a new one. Muster stores the token you enter and has no way to
    renew it, so a rotating token ends as `token_expired` and every Destination of the Connection becomes
    [Broken](https://muster-io.github.io/muster/latest/concepts/broken-destinations.md).

The app is not deployed to an organization
:   One Connection serves one app in one workspace.

There is no event subscription
:   Muster does not use the Events API: it hears only the presses of buttons and menus.

### The scopes

Muster needs the first six of these bot scopes and no other, and takes `usergroups:read` when you want to mention Teams
by Slack user groups. **Check connection** reads the scopes Slack grants the token, fails with `missing_scope`, naming
the missing ones of the six, and reports whether `usergroups:read` is granted, which never fails it.

`chat:write`
:   Posts, edits and deletes the bot's own messages, and answers the people who press its buttons.

`channels:read`
:   Reads a public channel to check a Destination, and lists the public channels the bot is a member of.

`groups:read`
:   The same for private channels.

`im:write`
:   Lets the bot open a direct chat with a person. The Connection check fails without it. The code of an Account link
    is sent with `chat.postMessage` to the person's user id, which needs `chat:write`; whether Slack also needs
    `im:write` for that has not been verified, so Muster keeps the scope.

`users:read`
:   Finds a person by name for an Account link, and reads the app of the bot so that the check can tell whether both
    tokens belong to one app.

`users:read.email`
:   Finds a person by email for an Account link.

`usergroups:read`, optional
:   Lists the user groups of the workspace, so that a Team can be mentioned by its user group
    ([Team mentions](https://muster-io.github.io/muster/latest/concepts/teams.md#team-mentions)). Without it a Slack Connection works as before, but takes no
    Team mention, whose reason a Team reads as `usergroups_read_missing`. The Connection records whether its last
    successful check found the scope (`usergroups_read`).

Muster never joins a channel on its own, so it asks for no `channels:join`: you invite the bot.

### Add usergroups:read to an installed app

An app installed from an earlier manifest lacks `usergroups:read`. Add it under **OAuth & Permissions → Scopes → Bot
Token Scopes**, or add the line to the app's manifest, and reinstall the app when Slack asks for it: a scope added to an
installed app reaches its bot token only after the reinstall. The reinstall keeps the bot token, so the Connection needs
no change: select **Check connection** on it again, and the check records the new scope (F-125). Until then the app
shows the new scope in its settings but the token still lacks it. A workspace may let only its Admins and Owners create
user groups, so a Team's user group may have to be created by one of them.

## Install the app and create the tokens

1. In the app's settings, open **Install App** and install it in the workspace. Slack then shows the **Bot User OAuth
   Token** under **OAuth & Permissions**; it starts with `xoxb-`. Copy it. Anyone with the token controls the bot.
2. In Socket Mode, open **Basic Information → App-Level Tokens** and generate a token with the scope
   `connections:write`. It starts with `xapp-`. Copy it. Anyone with this token can open sockets of the app and take
   its presses.
3. Over HTTP, open **Basic Information → App Credentials** and copy the **Signing Secret**. Anyone with it can send
   Muster presses that pass the signature check.

Muster stores all three secrets encrypted, never shows them again and writes them to no log line.

## Create the Connection

1. In Muster, open **Connections**, select **Create connection** and choose **Slack**.
2. Enter a **Name**, choose the **Event mode**, and enter the **Bot token** and, in Socket Mode, the **App-level
   token**, or over HTTP the **Slack signing secret**, each after **Set a value**. A Slack Connection has no address
   field, since Slack's address is fixed.

    ![The form of a new Slack Connection in Socket Mode, with the bot token and the app-level token](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/slack/01-new-connection.png){ .screenshot }

3. Select **Check connection**. The check runs in steps and shows the latency of each and whether it went through the
   proxy:

    1. **Token**: `auth.test` with the bot token, which names the bot and the workspace and fails if the token is not
       a bot's;
    2. **Scopes**: every scope the bot needs is granted, and whether the optional `usergroups:read` is;
    3. **App-level token**, in Socket Mode: the token belongs to the same app as the bot token, and Slack opens a
       connection for it. The check opens no WebSocket.

    ![The Connection check: the token, the scopes and the app-level token passed, with the bot and the workspace](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/slack/02-check-connection.png){ .screenshot }

4. Select **Save**. On the saved Connection, **Check connection** records the bot, the workspace and the app, which
   the page then names.

    ![The saved Connection Slack with its bot, workspace and app, in Socket Mode](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/slack/03-saved-connection.png){ .screenshot }

Over HTTP no request can show that Slack reaches the callback address or that the Slack signing secret is right, because
a bot cannot press its own button. The first press does: see [The test message](https://muster-io.github.io/muster/latest/messengers/slack.md#the-test-message).

**Check connection** also works in the form before anything is saved. It checks the values in the form and saves
nothing, and no bot name is recorded. A stored token goes to Slack only through the saved proxy: after a change of the
proxy, type the tokens again to check, or save first.

## Invite the bot and create Destinations

A bot posts only to channels it is a member of. In Slack, invite the bot to each channel a Destination posts to, public
or private:

```text

```

In Muster, create a **Destination** of type Slack with the Connection and the channel:

1. Open **Destinations**, select **Create destination** and choose **Slack**.
2. Choose the **Connection** and the **Channel**. The form lists the public and private channels the bot is a member
   of; for a channel that is not listed, type its id as Slack shows it in the channel's details, `C…` or `G…`. A direct
   chat or a person cannot be a Destination. Give the Destination a **Name**.

    ![The form of a new Slack Destination: the Connection Slack, the channel #alerts and the name alerts](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/slack/04-new-destination.png){ .screenshot }

3. Select **Save**, which runs the Destination check below. The saved Destination shows the channel's name.

    ![The saved Destination alerts: Slack, Healthy, the channel #alerts](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/slack/05-saved-destination.png){ .screenshot }

4. Under **Test and preview**, on the tab **Test**, select **Send test message**: a message marked 🧪 appears in the
   channel. In the screenshot the request line, which names a development server, is hidden, and links start with
   `http://localhost:8080`, the address of a development installation; yours start with your `MUSTER_PUBLIC_URL`. See
   [The test message](https://muster-io.github.io/muster/latest/messengers/slack.md#the-test-message).

    ![The result of the test message: Test passed, Message: Sent](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/slack/06-test-message.png){ .screenshot }

Saving runs the **Destination check**, which asks Slack about the channel with `conversations.info` and refuses a
Destination that fails:

- `channel_not_found`: no such channel, or a private channel the bot is not in;
- `channel_archived`: the channel is archived;
- `bot_not_in_channel`: "Invite the bot to the channel: /invite @{bot}", where `{bot}` is the bot's name as Slack
  reports it for the bot token, such as `muster`.

The bot's name appears in that hint only after **Check connection** has run on the saved Connection; before that it
says only "Invite the bot to the channel."

**Check** on the Destination page runs the same check at any time. When Slack refuses the bot later, for example
because someone removed it from the channel, the Destination becomes **Broken**; Muster runs the check every few
minutes while nothing waits for the Destination, and ends the Broken state once it passes again, for example after
someone invites the bot back. See [Broken Destinations](https://muster-io.github.io/muster/latest/concepts/broken-destinations.md).

## Link accounts

A button acts as a Muster User, and a Mention reaches a person, only through an Account link. The person enters their
Slack email or name in their profile, and the bot sends a code by direct message, in the Messages tab of the app. The
code has 8 characters, is valid for 10 minutes and allows 5 attempts (`account_link.slack_code`). See [Link
Slack](https://muster-io.github.io/muster/latest/messengers/account-links.md#link-slack).

## Where answers to presses show

A successful press is not answered: the Root message changes. Whatever the person who pressed must read — that the press
was refused, that their Slack account is not linked to Muster yet, or that the button could not be verified — shows in
the channel as a message only they can see, marked "Only visible to you". Unlike Mattermost, Slack needs no permission
beyond `chat:write` for it. For a press on a Thread reply, such as a Reminder, the answer shows in the Thread. The one
success that is answered is "Still on it", which changes no message.

Slack does not guarantee such a message: the person must be active and in the channel. When Slack refuses it, Muster
sends the same text to the press's `response_url`, on `hooks.slack.com`; an answer that fails both ways is logged and
not tried again. Answers are in the language of the User the account is linked to, and in English for an account
without a link.

A replica handles at most 2 presses at a time (`slack.parallel_presses`); the others wait, already confirmed to Slack. A
press whose deadline ends while it waits for a slot, 30 seconds after it was handed over (`slack.press_deadline`), is
answered, in English, that it failed. At most 64 presses wait for a slot in a process (`slack.max_waiting_presses`): one
more, and a press still waiting or running at the end of the shutdown's grace period, fails without an answer and is
logged. None of these bounds is configurable.

## What Muster posts

A Root message is a message with one attachment in the colour of its status. Its blocks are a section with the title,
`#N` and the Alert Group's title linked to the Alert Group page, and the status as a word; one section with the
Severity, Route, Teams and Started as fields; a section with the summary and the description; a context with the key
labels; a section with the Alerts and the notices; a context with the footer; a section with the links, "Open in
Muster" first; and the buttons. See [Messages and templates](https://muster-io.github.io/muster/latest/configure/messages-and-templates.md#the-default-message)
for the layout and its preview, and [Labels in the message](https://muster-io.github.io/muster/latest/configure/messages-and-templates.md#labels-in-the-message)
for the key labels. Each section is at most 3,000 characters as Slack gets them; a long message drops its description
first, then its Alerts, its summary and its key labels.

## Who gets notified

Slack cannot send a message without a notification: whom a new message notifies depends on each member's settings for
the channel and the Thread. So, as in Mattermost, **Quiet** means "without a Mention", not "nobody is notified".

- **Edits are Quiet.** An edit of the Root message carries no Mention, so a Loud change is always a new message: a new
  Root message, or a reply in the Thread. The edit drops the Mentions that the Root message had; Slack may then remove
  them from the person's list of mentions.
- **Mentions** are those of the Destination's [Mention entries](https://muster-io.github.io/muster/latest/concepts/mentions.md): `@channel` and `@here`, user
  groups and Teams, and people through their Account links. A person whom an entry names is mentioned only through their
  Account link; without one they are left out. The Owner of a Reminder, an auto-unacknowledge or a Takeover is still
  named by their display name as text without a link, which notifies nobody. A Slack Destination takes neither
  `@everyone` nor `@all`: a bot's `<!everyone>` mentions only in the workspace's general channel and does nothing
  elsewhere, with no error, while `@channel` reaches the same people (F-127). User groups and Teams are taken once the check found `usergroups:read`, and
  a user group or a Team mention is written as `<!subteam^…>` of the user group's id, which Slack shows as its handle and which mentions
  its members, in a Root message and in a Thread reply alike. The footer of a Root message — "Acknowledged by", "Snoozed
  by", "Resolved by" — writes a person with an Account link for the Connection as their Mention, which Slack shows as
  their name, in an edit as in a new message; a person without one is their display name as text.
- **Thread replies** stay in the Thread: Muster never also broadcasts them to the channel.
- **Alert data and template text never mention anyone.** An `&`, `<` or `>` in a label or an annotation is escaped, and
  so is `@`. A literal `<!here>` or `<@U…>` written in a template is shown as text and notifies nobody. Only the
  Destination's Mention entries, `{{ mention "here" }}` and its siblings, and linked people notify.

See [Loud and Quiet](https://muster-io.github.io/muster/latest/concepts/loud-and-quiet.md).

## Rate limits

Muster limits itself, and Slack limits it too.

`connection.slack.limiter`
:   50 requests a minute for every call of the Connection to the Web API together, the minimum Slack documents for the
    methods that edit and delete.

`destination.slack.limiter`
:   30 requests a minute for the sends and edits of a Destination together, half of Slack's "one message per second per
    channel".

Slack limits each method per app and workspace. When it answers `429`, Muster holds every request of the Connection, for
any of its Destinations, for the seconds of `Retry-After`; this is not counted as a failed attempt, and does not make a
Destination Broken. A `429` without `Retry-After` counts as a transient failure. You can change both limiters.

## Edits and deleted Root messages

Muster edits a Root message for as long as its Alert Group is open, which can be days. Slack lets a
bot edit its own messages, and no edit window is known for them. Whether a window that your workspace sets applies to
the messages of a bot, hours or days old, has not been verified; an edit that Slack refuses that way ends that delivery
as Not delivered and does not make the Destination Broken.

When someone deletes a Root message, Muster finds out at its next edit, when Slack answers `message_not_found`. It
checks that the bot is still in the channel and the channel is not archived, and then posts the Alert Group again once,
Quietly, with a note. If the bot is gone or the channel archived, the Destination becomes Broken instead. A Root message
that already had replies stays in the channel as "This message was deleted." with its replies, and Muster's later
replies still go under it until the next edit finds it gone.

A Root message deleted before it had any reply takes no reply: Slack posts a reply to it into the channel, as an
ordinary message, and answers as if it had worked. Muster notices, deletes that message at once and posts the Alert
Group again. The reply may stay in the channel for a moment. If Slack refuses the deletion, Muster does not try again:
the stray reply stays until someone deletes it, and the delivery records why.

## The test message

**Send test message** on the Destination page posts one message marked "🧪 Test message", with the buttons of its status,
and **Preview** shows the message as Muster would send it. No Alert Group changes.

A bot cannot press its own button in Slack, so the test message cannot prove that presses reach Muster, as Mattermost's
does. Press a button of the test message yourself: Muster answers you "This is a test message; nothing was changed",
even from an account without a link. That answer proves that presses reach Muster and, over HTTP, that the Slack
signing secret is right.

## The proxy

A Slack Connection has a proxy section like the others; see [Proxies](https://muster-io.github.io/muster/latest/messengers/proxies.md). The proxy must allow `CONNECT` to
`slack.com`; in Socket Mode also to the hosts under `slack.com` that the socket uses; and to `hooks.slack.com`, where
the fallback answers to presses go. Where only the proxy can resolve outside names and the Organization's outbound
address policy is strict, add `slack.com` and `*.slack.com` to **Allowed**: the domain entry covers `hooks.slack.com`
and the socket's hosts, but not `slack.com` itself. See [Proxies](https://muster-io.github.io/muster/latest/messengers/proxies.md#what-the-outbound-address-policy-checks).

Muster accepts a Socket Mode address only on `slack.com` or a host below it, and an answer address only on
`hooks.slack.com`. If the socket cannot open, the Leader backs off (`slack.socket_backoff`, from 1 second up to 5
minutes), logs [`slack_socket_failed`](https://muster-io.github.io/muster/latest/reference/log-events.md#slack_socket_failed), and does not make any
Destination Broken. It waits `slack.hello_timeout`, 10 seconds, for Slack's greeting on a new socket.

## Request log

The **Request log** of a Slack Connection records its calls to the Web API named as Slack names them, such as
`chat.postMessage` and `apps.connections.open`. Over HTTP it records each press that reaches the callback address as
`interactive`, with Muster's answer, refused ones included. In Socket Mode it records each envelope that carries an
envelope id under the type of the envelope, with the socket's host as its address and Muster's confirmation as its
answer; the app subscribes to no events, so only `interactive` envelopes arrive. Slack's greetings, disconnects and
keep-alive frames are not recorded. The answers Muster sends to a press's `response_url` are recorded as `response_url`,
with the address masked: look there when an answer never shows. Tokens, the Slack signing secret and the signature are
masked, and so are the address of the socket, the `response_url` of a press, the signed ids of buttons and the code of
an Account link. See [Request log](https://muster-io.github.io/muster/latest/operations/request-log.md).

## Check from the command line

`muster doctor` prints one line per Slack Connection and per Slack Destination with the same checks, without sending
anything, and a `WARN` line for a Connection whose app another program shares.

# Proxies

Muster has no proxy for the whole installation. Each client that talks to the outside has a proxy setting of its own, so
that traffic that must go through a proxy does, and traffic that must not, such as the identity provider's, goes
straight. `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` are **never read**, in any process of Muster.

## Where you set a proxy

| Client | Where |
|---|---|
| a Mattermost, Slack, Telegram or Bridge Connection | the Connection's proxy section |
| an outgoing webhook Destination | the Destination's proxy section |
| the identity provider (OpenID Connect) | the OIDC settings |
| the Organization's outgoing heartbeat | its settings |

The setting is off by default. Every one of these has the same form:

- **Use a proxy**, a switch. Switching it off keeps the other fields, so that you can switch it on again.
- **Type**: `http`, `https` or `socks5`.
- **Address**, as `host:port` with a port from 1 to 65535.
- **Username** and **password**, when the proxy needs them. The username must not contain a colon or a line break and is
  at most 255 bytes long.

The three types differ in how Muster talks to the proxy:

| Type | Muster speaks to the proxy | Notes |
|---|---|---|
| HTTP | plain HTTP | for an HTTPS target, Muster asks the proxy for a tunnel with `CONNECT` |
| HTTPS | HTTP over TLS | the connection to the proxy is encrypted |
| SOCKS5 | the SOCKS5 protocol | the proxy resolves the name of the target |

## The password

The proxy password is a secret like the others: it is encrypted with the master key, write-only in the API and the web
UI (they show whether it is set, never the value), and replaced with `[redacted]` in every log line and error. A stored
password is used only with the proxy type and address it was saved with. When you change either, type the password
again.

## Checks take the same path

The connection check of a Connection, and the test of a Destination, go through the saved proxy just as real traffic
does. If the check works, delivery works by the same route. A check run from the form before saving uses the proxy in
the form instead. A token that is already stored goes only to the saved address of its Connection, through its saved
proxy: with a changed but unsaved address or proxy and no token typed, the check makes only a probe without the
token.

## What the outbound address policy checks

Every outbound connection of Muster is checked by the Organization's outbound address policy, **standard** or
**strict**, with its lists of allowed and denied networks, host names and domains. The Admins edit the policy under
Organization → Outbound addresses. Through a proxy, two things are checked:

1. **The proxy's own address.** It is checked like any other target, after name resolution. A proxy setting cannot reach
   a link-local or cloud metadata address, such as `169.254.169.254`, and a proxy on a loopback address works only when an
   allowed network contains it.
2. **The target.** The proxy resolves the target's name, so Muster resolves it too, and every address it gets must pass
   the policy; for a target given as an IP address, that address is checked. A request to a name that resolves to a
   blocked address is refused before it is sent, without retry, and the error names the rule.

In a closed network, only the proxy may be able to resolve outside names. When Muster cannot resolve the target's name
itself, it checks the name instead: a name that matches a denied entry is blocked, and in strict mode only a name that
matches an allowed entry passes. A request that passes is sent without an address check, and Muster logs that.

Muster cannot see where the proxy finally connects to. The Admin who sets the proxy chooses to trust it.

## Telegram

Telegram is often reached through a proxy where it is blocked. [Telegram in restricted
networks](https://muster-io.github.io/muster/latest/messengers/telegram-restricted-networks.md) shows the proxy on the Connection, and the alternatives: a reverse proxy
under your own domain and a self-hosted Bot API server.

## Slack

A Slack Connection has no address field, since Slack's address is fixed, so a proxy sees only Slack's hosts. It must
allow `CONNECT` to `slack.com`; in Socket Mode also to the hosts under `slack.com` that the socket uses; and to
`hooks.slack.com`, where Muster sends the answer to a press when it cannot send it in the channel. When only the proxy
can resolve outside names and the policy is strict, add `slack.com` and `*.slack.com` to **Allowed**: the domain entry
covers the socket's hosts and `hooks.slack.com`, but not `slack.com` itself. See [Connect Slack](https://muster-io.github.io/muster/latest/messengers/slack.md#the-proxy).

# Connect a messenger through a bridge

A **bridge** connects Muster to a messenger that Muster does not support natively. It is a separate service that
speaks the Bridge protocol with Muster on one side and talks to your messenger on the other: Muster sends it every
message as an **envelope** — the status, the title, a link, the text and the buttons — and the bridge renders the
envelope in its messenger. A **Bridge Connection** is one bot of your messenger behind one bridge: one token is one
bot. Muster posts one **Root message** per Alert Group to a channel of that messenger, edits it as the Alert Group
changes, and replies in its **Thread** for what happens later, as it does for Mattermost, Slack and Telegram.

To write a bridge, read [Write a bridge](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md); the protocol itself is the
[Bridge protocol](https://muster-io.github.io/muster/latest/reference/bridge-protocol.md) reference.

In the examples, `MUSTER_PUBLIC_URL` is `https://muster.example.org`, `MUSTER_INGEST_URL` is
`https://ingest.muster.example.org` and the bridge listens on `https://bridge.example.org`. The steps use the web UI;
the examples do the same with the [API](https://muster-io.github.io/muster/latest/reference/api.md), with a Personal access token of an Admin in
`MUSTER_TOKEN`.

## Create the Connection

From your bridge, you need:

- its **base URL**, an `http` or `https` address with an optional path prefix, such as
  `https://bridge.example.org/muster`. Muster sends every request to `<base URL>/v1/…`, and only there, with
  `User-Agent: Muster/<version>`;
- the **token** it gave your bot. Muster sends it as `Authorization: Bearer` on every request, stores it encrypted and
  never shows it again.

Choose how the bridge reports **events** — the presses of buttons and the messages people write in a Thread — with the
**event delivery** mode:

- **`poll`** (`connection.bridge.event_delivery`, the default) when the bridge cannot reach Muster. The Leader asks the
  bridge for new events, so the bridge needs no address of Muster.
- **`push`** when the bridge can reach `MUSTER_INGEST_URL`. The bridge posts each event to the Connection's callback
  address, `https://ingest.muster.example.org/api/v1/callbacks/bridge/CN…`, which the Connection shows in
  `callback_url`, signed with a **push secret** that you configure on both sides. The push secret has the Standard
  Webhooks form, `whsec_` followed by the base64 of at least 24 random bytes, and is write-only like the token. The
  callback is authenticated by this signature alone, so Muster refuses a shorter key with `invalid_format`. Generate
  one with `printf 'whsec_%s\n' "$(openssl rand -base64 32)"`. A Connection saved with a shorter push secret before
  Muster required 24 bytes keeps working; the API's `warnings` lists `push_secret_too_short`, and the form and
  `muster doctor` warn about it, until you save a new push secret here and in the bridge.

A Connection also has a **proxy**, for a bridge that Muster reaches only through one, and a **limiter**: 10 requests
per second by default, shared by all its Destinations. When the bridge answers that it is rate-limited, Muster waits
as long as it asks, whatever the limiter allows.

1. Open **Connections**, select **Create connection** and choose **Bridge**.
2. Enter a **Name**, the **Base URL** and, after **Set a value**, the **Token**. Choose the event delivery mode,
   **Polling** or **Push**; with push, also the push secret.

    ![The form of a new Bridge Connection: the name Team chat, the base URL https://bridge.example.org, the token and polling](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/bridge/01-new-connection.png){ .screenshot }

3. Select **Check connection**, below the form. It runs the steps of [What the check shows](https://muster-io.github.io/muster/latest/messengers/bridge.md#what-the-check-shows)
   against the values in the form and saves nothing.

    ![The Connection check: the steps Bridge info and Event delivery passed](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/bridge/02-check-connection.png){ .screenshot }

4. Select **Save**, then **Check connection** on the saved Connection: Muster keeps what the bridge offers, which the
   page shows.

    ![What the bridge offers, as the saved Connection shows it: the bridge, the messenger, the protocol version and its features](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/bridge/03-saved-connection.png){ .screenshot }

With the API:

```sh
curl -X POST https://muster.example.org/api/v1/connections \
  -H "Authorization: Bearer $MUSTER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"type":"bridge","name":"Team chat","base_url":"https://bridge.example.org/muster",
       "bot_token":"the-token-of-the-bot","event_delivery":"poll","proxy":{"enabled":false},
       "limiter":{"limit":10,"per_seconds":1}}'
```

For `push`, set `"event_delivery":"push"` and add `"push_secret":"whsec_…"`.

## What the check shows

Check the Connection after you create it, and after every change of the bridge:

```sh
curl -X POST https://muster.example.org/api/v1/connections/CNK7M3QX9P2RTA/checks \
  -H "Authorization: Bearer $MUSTER_TOKEN"
```

The check calls the bridge's `getInfo` and shows two steps, each with its latency and whether it went through the
proxy:

1. **`info`**: the bridge's name and version, the messenger's name, the protocol version — Muster speaks `1` — what
   the bridge offers, such as buttons and Thread messages, its limits, such as the longest text of a message, how it
   finds people for Account links, and its event delivery modes. Muster keeps this copy on the
   Connection and reads it again before a call that depends on it once it is older than 10 minutes, so a change in the
   bridge reaches Muster without a restart.
2. **`event_delivery`**: whether the bridge offers the Connection's event delivery mode.

A failed step names its cause with a code:

`token_invalid`
:   The bridge refused the token.

`protocol_version_unknown`
:   The bridge speaks a protocol version that this Muster does not speak.

`protocol_mismatch`
:   The answer does not match the protocol, or is larger than 64 KiB.

`event_delivery_not_offered`
:   The bridge does not offer the Connection's event delivery mode.

`proxy_refused`
:   The Connection's proxy refused its credentials (`407`).

`timeout`, `connect_failed`, `dns_failed`, `tls_failed`
:   Muster got no answer from the bridge.

`blocked`
:   The outbound address policy does not allow the bridge's address.

`request_failed`
:   The bridge answered with another error; the message names its class and the bridge's text.

## Roles

A bridge declares its roles in its `info`, and the check shows them. A bridge in the role `messenger`, which is every
bridge that declares no roles, connects a messenger: its channels are Destinations, and people link their accounts
through it. A bridge in the role `gateway` is a **Notification gateway**: it reaches people outside messengers, by
phone call or SMS for example, through a provider of its own. A bridge may have both roles. [Notification gateways](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md) says how
to connect one and how people confirm a contact; [A gateway bridge](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#a-gateway-bridge) is for the
authors of one.

A Bridge Connection whose only role is `gateway` cannot be a Destination: creating or saving a Destination for it is
refused with `422` and the code `gateway_only` at `connection_id`. It is not offered for Account links either, since
it looks nobody up in a messenger. Its read in the API has `roles`, from the `info` of its last check:

```sh
curl https://muster.example.org/api/v1/connections/CNK7M3QX9P2RTA \
  -H "Authorization: Bearer $MUSTER_TOKEN"
```

```json
{
  "id": "CNK7M3QX9P2RTA",
  "type": "bridge",
  "name": "Phone calls",
  "roles": ["gateway"]
}
```

The Connection list takes `role`: `role=gateway` lists the Notification gateways, `role=messenger` every Connection of
a messenger, Mattermost, Slack and Telegram ones included.

## Check before saving

The check above reads a saved Connection. **Check connection** in the form of a new Connection, or on the page of a
saved one while the form holds changes, checks the values in the form before anything is saved, with
`POST /api/v1/connections/checks`. It saves nothing: the `info` it reads is returned, not stored, and the Audit log
gets no entry.

- With the token typed, the steps `info` and `event_delivery` run against the base URL in the form, through the proxy in
  the form, with that token.
- Without one, a saved Connection (`connection_id`) uses its stored token only when the base URL — a trailing `/`
  aside — and the proxy are the saved ones: the stored token is sent only to the saved address, through the saved
  proxy. After a change of the base URL or of the proxy, the check makes only a dry probe, `GET <base>/v1/info` without
  the token, which a bridge answers with `401` and a problem (`application/problem+json`). An address that answers
  otherwise fails with `not_bridge`, a `404` with `wrong_path_prefix`, another status with a problem with
  `unexpected_status`; after a dry probe that passes, `info` and `event_delivery` ask you to type the token again to
  check the new address or proxy, or to save first. A new Connection without a token gets the dry probe alone too.

```sh
curl -X POST https://muster.example.org/api/v1/connections/checks \
  -H "Authorization: Bearer $MUSTER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"type":"bridge","base_url":"https://bridge.example.org/muster","event_delivery":"poll",
       "bot_token":"the-token-of-the-bot"}'
```

## Add a Destination

A **Bridge Destination** is one channel of the messenger, named by its **channel id** — the channel as your messenger
names it, which the bridge's documentation explains how to find. Its [Mention entries](https://muster-io.github.io/muster/latest/concepts/mentions.md)
take people and the On-call, and everyone in the chat, groups and Teams as far as the bridge declares them in its
`info`; [What Muster posts](https://muster-io.github.io/muster/latest/messengers/bridge.md#what-muster-posts) says how each arrives. Its limiter allows 30 requests per minute by
default, sends and edits together.

1. Open **Destinations**, select **Create destination** and choose **Bridge**.
2. Choose the **Connection**, enter the **Channel id** and a **Name**.

    ![The form of a new Bridge Destination: the Connection Team chat, the channel id ch-alerts and the name alerts](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/bridge/04-new-destination.png){ .screenshot }

3. Select **Save**, which runs the Destination check below. The saved Destination shows the channel's name as the
   bridge reports it.

    ![The saved Destination alerts: Bridge, Healthy, with the channel's name](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/bridge/05-saved-destination.png){ .screenshot }

4. Under **Test and preview**, on the tab **Test**, select **Send test message**: the bridge posts a message marked 🧪,
   and the result shows the envelope Muster sent. Links in the screenshot start with `http://localhost:8080`, the
   address of a development installation; yours start with your `MUSTER_PUBLIC_URL`. See
   [Test messages and previews](https://muster-io.github.io/muster/latest/messengers/bridge.md#test-messages-and-previews).

    ![The result of the test message: Test passed, Message: Sent, with the envelope sent to the bridge](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/bridge/06-test-message.png){ .screenshot }

With the API:

```sh
curl -X POST https://muster.example.org/api/v1/destinations \
  -H "Authorization: Bearer $MUSTER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"type":"bridge","name":"alerts","connection_id":"CNK7M3QX9P2RTA","channel_id":"C024BE91L",
       "mention_entries":[{"target":{"kind":"everyone","everyone":"here"},"events":["new_alert_group"]}],
       "limiter":{"limit":30,"per_seconds":60}}'
```

Saving the Destination runs its **Destination check**, the one item `channel`: the bridge's `checkChannel`, which
posts nothing. It passes when the bot can post, edit and reply in the channel, and the Destination then shows the
channel's name as the bridge reports it. It fails with the bridge's own text when the bridge refuses the channel —
it does not exist, or the bot is not in it — with `proxy_refused` when the Connection's proxy refuses its credentials,
and with the class of the bridge's answer otherwise; a Destination that fails the check is not saved.
`POST /api/v1/destinations/DS…/checks` runs the same check at any time.

## What Muster posts

- **The envelope.** Every Root message carries its status with a colour and an emoji, the title `#N` and the Alert
  Group's title, the link "Open in Muster" to the Alert Group page, and its text in CommonMark as `body`: the fields,
  the summary and the description, the key labels, the Alerts, the links, the notices and the footer. A Thread reply
  carries its text in CommonMark. Alert data are escaped, so a label value cannot format the message, link anywhere or
  mention anyone. A Loud message asks the bridge to notify; a Quiet one does not.
- **Mentions.** A Loud message starts its `body` with its Mentions, each a marker `[@name](muster-mention:m1)` whose
  `ref` names an entry of `mentions`, and each entry has a kind:

    `user`
    :   A person with an Account link for the Connection: `external_id` is their account's id, and `display_name` the
        display name of their Account link, or their display name in Muster when the link has none. It is the default,
        and Muster sends such an entry without `kind`, so a bridge that declares no group or everyone mentions sees the
        entries it always saw.

    `group`
    :   A group of the messenger — a [Team mention](https://muster-io.github.io/muster/latest/concepts/teams.md#team-mentions) or a group entry of the
        Destination — with the name an Admin typed for it as `external_id` and `display_name`, which the bridge maps to
        its messenger's group. It comes only while Muster's copy of the bridge's `info` declares `group_mentions`. A
        `{{ mention "group" "payments_team" }}` in a Route's template stays text in `body`, which notifies nobody, and
        adds its entry to the line of Mentions of a Loud message or Thread reply, once beside a group entry of the same
        name, when the bridge's `info` declares `group_mentions`.

    `everyone`
    :   Everyone in the chat, with the symbolic name `channel`, `here`, `all` or `everyone` as `external_id` and
        `display_name`. It comes only with a name that Muster's copy of the bridge's `info` lists in
        `everyone_mentions`. A `{{ mention "here" }}`, `{{ mention "channel" }}` or `{{ mention "all" }}` in a
        Route's template stays text in `body`, which notifies nobody, and adds its entry to the line of Mentions of a
        Loud message or Thread reply, when the bridge's `info` lists it in `everyone_mentions`.

    A bridge that declares group mentions or a mention of everyone renders the markers of those entries as its
    messenger's mentions, `@payments_team` or `@here` for example, whether or not it has native mentions. A bridge with
    native mentions renders the markers of people as its mentions of their accounts, and any other bridge shows them by
    their link text, which mentions nobody. A group or a mention of everyone that Muster's copy of the bridge's
    `info` does not declare is left out of the message, and so is a person whom an entry names without an Account
    link; a bridge that nevertheless receives a `group` or an `everyone` entry it does not declare, because its `info`
    changed since, shows the marker's link text, which notifies nobody, and never refuses the message. See
    [Whom a message mentions](https://muster-io.github.io/muster/latest/concepts/mentions.md#undelivered-mentions). That copy is at most `bridge.info_max_age` (10 minutes) old: Muster reads `info` again when it is older, and when a
    Connection check runs. A long line of Mentions keeps, in their order, the whole markers that fit half of the
    bridge's longest text, with their entries, and leaves out the others: each person, group, Team mention or mention
    of everyone left out, a template's token included, is recorded as "Mention not delivered" with the reason
    `message_too_long`. Only the Owner's Mentions — of a Reminder, an
    auto-unacknowledge or a Takeover — the footer and the Assignees name a person without one, by their display name as
    text. A Root message of a Destination that mentions the Team payments, `here` and Alice starts:

    ```json
    {
      "body": "[@payments\\_team](muster-mention:m1) [@here](muster-mention:m2) [@Alice Smith](muster-mention:m3)\n\n…",
      "mentions": [
        { "ref": "m1", "kind": "group", "external_id": "payments_team", "display_name": "payments_team" },
        { "ref": "m2", "kind": "everyone", "external_id": "here", "display_name": "here" },
        { "ref": "m3", "external_id": "u-alice", "display_name": "Alice Smith" }
      ]
    }
    ```

- **The layout.** Beside `body`, a Root message and a test message carry the same content as structured data in
  `layout`: the number alone and the title without it, the status as a key and a word, the fields as name and value,
  the summary and the description, the key labels as key and value, the Alerts by the label that tells them apart
  with whether each is resolved and how many there are in all, the notices, the people and the links. Its values are
  plain text, never CommonMark, so `Queue *full* on #1` arrives as it is, and the bridge escapes it for its
  messenger. The people are the Owner while the Alert Group is acknowledged, with the `ref` of their entry in
  `mentions` when the message carries their Mention, and `null` in an edit and through a bridge without native
  mentions; its `name` is their display name in Muster, which may differ from the `display_name` of their entry in
  `mentions`. Who snoozed or resolved the Alert Group is only text in a line of `notices`, such as "Snoozed by Bob until
  …", with no `ref`: a bridge cannot mention them from `layout`. A bridge renders either `body` or `layout`; a bridge
  that ignores `layout` works as before. Storm summaries and Thread replies have no `layout`, nor has a Root message
  whose Route has its own Root message template or line template, or that the fallback template shows after a template
  failed, since part of its content exists only in `body`: render `body` whenever `layout` is absent. A test message
  has "🧪 Test message" as the first of its `notices`, which a bridge shows before the rest. A link's `url` is an
  absolute `http` or `https` address as the Route gives it, and may be an IRI, with characters outside ASCII in its
  host or path. The libraries for Go and Python, from 0.1.1, drop a `layout` that does not match the protocol and
  render `body`, rather than refuse the message. How a bridge renders `layout` is in
  [Render the structured layout](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#render-the-structured-layout); the
  [Bridge protocol](https://muster-io.github.io/muster/latest/reference/bridge-protocol.md) reference shows its schema, and
  [Messages and templates](https://muster-io.github.io/muster/latest/configure/messages-and-templates.md#the-default-message) shows what it says in each
  messenger.
- **The length.** The text fits the longest text the bridge declares, read from the Connection's copy of its info: a
  long Root message drops its description first, then its Alerts, its summary and its key labels, but always keeps its
  title, its status, its fields, its footer, its buttons and its links, the one to Muster first. `layout` loses the
  same parts as `body`, so that the two never disagree. The bridge may still shorten what it renders, and says so.
- **Buttons.** When the bridge offers buttons, a Root message carries the buttons of its status — Ack, Resolve, one
  per Snooze duration and the two [Snooze presets](https://muster-io.github.io/muster/latest/concepts/statuses-and-commands.md#in-messengers) "Until tomorrow
  09:00" and "Until Monday 09:00", for example — with a style hint for each, the presets `neutral` like the durations,
  at most as many as the bridge allows. Beyond that limit the Snooze buttons go first, whatever their labels: the
  "Until Monday" preset (the first day of the week), then the "Until tomorrow" preset, then the durations from the
  longest. A firing Root message on a Paging Route has seven buttons, so a bridge that allows five gets Ack, Resolve
  and the three durations, and one that allows six also "Until tomorrow 09:00". Without buttons, a bridge that forwards
  the messages of a Thread gets a last line in each Root message that is not resolved, such as "Reply in the Thread:
  ack · resolve · snooze 1h", and takes the presets as Text commands such as `snooze tomorrow`.
- **Edits and Thread replies.** An edit sends the whole envelope of the new state, Quiet and without Mentions. A Thread
  reply goes under the Root message with the Thread reference the bridge returned last.
- **The footer.** "Acknowledged by", "Snoozed by" and "Resolved by" name a person with an Account link for the
  Connection by a Mention marker in a new Root message to a bridge with native mentions, Loud or Quiet; in an edit,
  which carries no Mentions, and through any other bridge, by the name the bridge reported for their account.
- **Posts are not repeated.** Every new message carries an idempotency key, the same for every retry of it. When an
  answer is lost — a timeout, or a connection cut after the request — Muster retries with the same key, the bridge
  answers with the message it posted already, and Muster edits it to the current state. When the bridge did not know
  the key, the retry may have posted a second message: the Timeline records a **possible duplicate**.
- **The token never shows** in a log line, an error, the Timeline or a metric; a test shows it as `[redacted]`.

## Edit windows

Some messengers let a bot edit a message only for a while after posting it. A bridge for such a messenger declares
how long in its info, as `limits.edit_max_age_seconds`, and Muster stops editing its Root messages in time. A bridge
that declares no limit (`null`) has none: Muster edits each Root message for as long as its Alert Group changes.

- **When Muster stops editing.** Muster makes no edit of a Root message once it is as old as the bridge's limit less
  60 seconds, counted from its Publication on Muster's clock, so that a last edit does not race the messenger's: with
  a limit of 600 seconds, the last edit is made within 9 minutes. Muster reads the limit from the Connection's copy of
  the info, as for every call. When the messenger refuses an edit earlier than declared, the bridge answers `gone` with
  the `reason` `edit_window_closed`: this is not a deletion, and Muster treats the Root message as past its window at
  once. A Root message that Muster posts again after it was deleted has a window of its own.
- **Alerts reach only the Thread.** Past the window, a change that keeps the status of the Alert Group — new Alerts,
  Alerts that resolve, the counters — no longer changes the Root message, which keeps the state of its last edit; the
  Thread replies that such a change makes are sent as usual.
- **A change of status posts a new Root message.** When the status changes past the window — Acknowledge, Resolve,
  Snooze, a Reopen — Muster posts a new Root message with the current state, Quietly, to the same channel, and replies
  under the old one: "This message is no longer updated. The current one: {link}", with a link to the new message when
  the bridge returned one and to the Alert Group page otherwise. Later Thread replies go under the new Root message,
  which has a window of its own. This reply is sent once: when the bridge refuses it, the failure is recorded with the
  delivery event and the reply is not sent again.
- **A new Root message is not left behind.** When the answer to the post of a new Root message is lost, Muster posts
  it again with the same key, even if the status has changed back meanwhile, so that a message the bridge may have
  taken is never left with a stale status and live buttons: a bridge that took the first post answers with that
  message instead of posting a second one. When the Destination left the Route meanwhile, the post carries the final
  text; when the bridge answers with the earlier post, which shows an older state, Muster then gives that message the
  final edit.
- **The old message keeps working.** A press on the buttons of an older Root message, or a Text command in its
  Thread, acts on the Alert Group as on the current one.
- **The final edit is a Thread reply.** When the Destination leaves the Route or is deleted, each open Root message
  gets a final edit, "No longer updated here; current state in Muster: {link}"; past the window, Muster sends the same
  text as a Thread reply instead.
- **Storm summaries are never posted again.** Past its window, a Storm summary keeps the state of its last edit.
- **What the delivery shows.** `GET /api/v1/alert-groups/AG…/deliveries` shows `past_edit_window` as `true` for a
  Destination whose Root message is past its window, while the delivery stays `delivered`, or `pending` while a new
  Root message is due. Each new Root message posted past the window is the delivery event
  `republished_past_edit_window` in the Alert Group's Timeline, with the error of the reply under the old message when
  it failed, and the log line `bridge_republished_past_edit_window`, with the ids of the old and the new message.

It posts one message of the kind `test`, Quiet, marked "🧪 Test message" before its text, with the buttons of its
status, whose presses change nothing. It goes through the same limiters as delivery, and the result shows the step
`message` with the request — the token masked — the bridge's answer and its error class. Use
`{"source":{"kind":"alert_group","alert_group_id":"AG…"}}` to render a recent Alert Group of one of the
Destination's Routes instead of the example. `POST …/previews` with the same body returns, without posting anything,
the envelope the test would post, as JSON in the item `message`.

## Broken Destinations

A Bridge Destination becomes **Broken** when the bridge refuses it — it answers `forbidden`, for example because the
bot was removed from the channel — with the bridge's text as the reason, or when the bridge keeps failing or does not
answer for the whole Transient budget: 10 attempts within 30 minutes. A bridge that asks Muster to wait does not make
a Destination Broken unless it asks for more than 15 minutes (`bridge.retry_after_max`); an answer the bridge calls `invalid` ends that one
delivery as Not delivered and leaves the Destination healthy. When the bridge answers that a Root message is gone,
Muster publishes the Alert Group again, once; an edit refused as `gone` with the `reason` `edit_window_closed` is not a
deletion, but the end of the message's [edit window](https://muster-io.github.io/muster/latest/messengers/bridge.md#edit-windows).

While a Destination is Broken, Muster tries again every 5 minutes: with the oldest waiting delivery, or, when nothing
waits, with the Destination check, which posts nothing. The first success ends the Broken state, and so does a
successful check or test message. See [MusterDestinationBroken](https://muster-io.github.io/muster/latest/operations/runbooks/MusterDestinationBroken.md).
A Bridge Connection whose bridge cannot be reached does not become Broken itself: its Destinations do, and its
Connection check shows the cause.

## Account links

A press or a Mention through a bridge names a person through their Account link for that Connection; see
[Link your messenger accounts](https://muster-io.github.io/muster/latest/messengers/account-links.md).

## Check from the command line

`muster doctor` prints one line per Bridge Connection, with the result of `getInfo`, and one line per Bridge
Destination, with the result of `checkChannel`, without posting anything.

# Write a bridge

A **bridge** connects Muster to a messenger that Muster does not support natively. This page is for the people who
write one. It starts with the bridge libraries, which do the protocol's part of a bridge, and then describes the
**Bridge protocol** step by step for a bridge written without a library. If you run a bridge that somebody else wrote,
read [Connect a messenger through a bridge](https://muster-io.github.io/muster/latest/messengers/bridge.md) instead.

## What a bridge is, and when to write one

Muster has native support for [Mattermost](https://muster-io.github.io/muster/latest/messengers/mattermost.md), [Slack](https://muster-io.github.io/muster/latest/messengers/slack.md) and [Telegram](https://muster-io.github.io/muster/latest/messengers/telegram.md). For any other
messenger, Muster talks to a bridge: a small HTTP service that you write and run. Muster calls the bridge to post, edit
and reply to messages. The bridge calls the messenger. When people press a button or write in a Thread, the bridge
reports it back to Muster as an **event**.

Write a bridge when your team uses a messenger with a bot API that Muster does not support. A bridge does not need to
live in Muster's repository, and it may stay closed: the protocol is MIT licensed (see [Licence](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#licence)).

```mermaid
flowchart TB
  subgraph muster["Muster"]
    calls["Delivery worker and interactive path"]
    poller["Poller"]
    callback["Push callback on the ingest listener"]
    handler["Commands and Account links"]
    health["Destination health"]
  end
  subgraph bridge["Your bridge"]
    api["Bridge protocol: the /v1/ operations"]
    queue["Event queue"]
  end
  messenger["Your messenger"]

  calls -- "getInfo, postMessage, editMessage, replyInThread, checkChannel, answerEvent, findUsers, sendDirectMessage" --> api
  api -- "calls the messenger's own API" --> messenger
  messenger -- "presses, Thread messages, direct messages, deletions" --> queue
  poller -- "poll mode: pollEvents" --> queue
  queue -. "push mode: bridgeEvent, signed" .-> callback
  poller --> handler
  callback --> handler
  api -. "answers and error classes" .-> health
  health -- "Broken, every 5 minutes: the oldest waiting delivery, or checkChannel when nothing waits" --> api
```

Muster is always the caller of the `/v1/` operations, and the bridge is always the caller of the messenger. Events
travel the other way, in one of two modes that the Admin chooses on the Bridge Connection: Muster **polls** the bridge
with `pollEvents`, or the bridge **pushes** each event, signed, to Muster's callback address. The bridge answers every
call with a result or an error class, and Muster turns those into the health of the Destination: a Destination whose
bridge keeps failing, or refuses the channel, becomes Broken until a check succeeds (see
[Run your bridge](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#run-your-bridge)).

Terms follow Muster's glossary: a **Root message** is the one editable message that shows an Alert Group in a channel
of the messenger, its **Thread** holds the replies under it, and a **Mention** is a deliberate @-reference. A **Bridge
Connection** in Muster is one bot of your messenger behind one bridge: one token is one bot.

## Start with a library

Most bridge authors should not write the protocol again. A bridge library does the protocol's part of a bridge, and
you write only the calls to your messenger.

### What a library does, and what is left to you

A library:

- serves every operation of the protocol under `/v1/`;
- checks the token of each bot in constant time, and keeps the events and idempotency keys of each bot apart;
- validates every request against `api/bridge.yaml` and every answer before it is sent, and enforces the bridge's
  limits;
- keeps each `Idempotency-Key` with its result and answers a repeated key with that result and `replayed: true`;
- builds the answer to `getInfo` from the features and limits you give it;
- answers failures as problems with an error class, and never logs a token or a push secret;
- queues events for `pollEvents`, and pushes them with Standard Webhooks signatures and retries;
- turns a direct message that carries an Account link token into an `account_link` event.

You write:

- the calls to your messenger: post, edit, reply in a Thread, check a channel and show an answer to a person, and,
  where the messenger offers them, finding a person, sending a direct message and deleting a message;
- the mapping of the messenger's failures to the five error classes (see [Error classes](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#error-classes));
- the reports of what people do: a press, a message in a Thread, a deleted message and a direct message;
- the rendering of the envelope in the messenger's markup (see [Rendering the envelope](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#rendering-the-envelope)).

The Go library, `muster-bridge-go`, is released from its own repository, under the MIT licence and without a CLA. The
same holds for every bridge library of the project.

### The Go library

The Go module is `github.com/muster-io/muster-bridge-go`, and its package is `bridge`.

```sh
go get github.com/muster-io/muster-bridge-go
```

Each release of a library is a tag `vX.Y.Z`, and `go get` without a version takes the newest release. Versions stay
`0.x` until Muster 1.0, and every library release speaks the protocol versions Muster supports at that time, today
protocol version 1; a breaking protocol change is a new protocol version, not a new major version of a library.

**1. Implement `bridge.Messenger`.** It has five methods, each given the name of the bot whose token Muster sent:
`PostMessage`, `EditMessage`, `ReplyInThread`, `CheckChannel` and `AnswerEvent`. The sketch below is for Parley, a
fictional messenger; its client `parleyClient` stands for whatever library your messenger has.

```go
// parleyMessenger is the bridge's calls to the fictional messenger Parley.
type parleyMessenger struct{ api *parleyClient }

// mention is how Parley writes a mention of a person.
func mention(p bridge.Mention) string { return "<@" + p.ExternalId + ">" }

func (m *parleyMessenger) PostMessage(ctx context.Context, bot string, in bridge.MessageInput) (
	bridge.MessagePosted, error) {
	body := bridge.ReplaceMentions(in.Body, in.Mentions, mention)
	id, err := m.api.Send(ctx, in.ChannelId, render(in.Title, body))
	if err != nil {
		return bridge.MessagePosted{}, classify(err)
	}
	return bridge.MessagePosted{MessageId: id}, nil
}

func (m *parleyMessenger) EditMessage(ctx context.Context, bot, messageID string, in bridge.MessageContent) (
	bridge.MessageEdited, error) {
	if err := m.api.Edit(ctx, messageID, render(in.Title, in.Body)); err != nil {
		return bridge.MessageEdited{}, classify(err)
	}
	return bridge.MessageEdited{}, nil
}

func (m *parleyMessenger) ReplyInThread(ctx context.Context, bot, messageID string, in bridge.ThreadReplyInput) (
	bridge.ThreadReplyPosted, error) {
	var thread string
	if in.ThreadRef != nil {
		thread = *in.ThreadRef
	}
	body := bridge.ReplaceMentions(in.Body, in.Mentions, mention)
	id, thread, err := m.api.Reply(ctx, messageID, thread, body)
	if err != nil {
		return bridge.ThreadReplyPosted{}, classify(err)
	}
	return bridge.ThreadReplyPosted{MessageId: id, ThreadRef: thread}, nil
}

func (m *parleyMessenger) CheckChannel(ctx context.Context, bot, channelID string) (string, error) {
	name, err := m.api.ChannelName(ctx, channelID)
	if err != nil {
		return "", classify(err)
	}
	return name, nil
}

// AnswerEvent answers an Account link in its direct chat, a Thread message in its Thread, and a press privately.
func (m *parleyMessenger) AnswerEvent(ctx context.Context, bot string, ev bridge.ReportedEvent, text string) (
	bridge.AnswerShownShownAs, error) {
	switch ev.Type {
	case bridge.EventTypeAccountLink:
		if err := m.api.SendDirect(ctx, ev.Chat, text); err != nil {
			return "", classify(err)
		}
		return bridge.AnswerShownShownAsDirect, nil
	case bridge.EventTypeThreadMessage:
		if _, _, err := m.api.Reply(ctx, ev.MessageID, ev.ThreadRef, text); err != nil {
			return "", classify(err)
		}
		return bridge.AnswerShownShownAsThread, nil
	default:
		if err := m.api.Whisper(ctx, ev.Chat, text); err != nil {
			return "", classify(err)
		}
		return bridge.AnswerShownShownAsEphemeral, nil
	}
}
```

For the features you declare, also implement `UserFinder` (when `UserLookup` is not `none`), `DirectMessenger` (when
the bridge offers direct messages) and `Deleter` (when it offers deletion). `bridge.New` refuses a configuration whose
features lack their interface, or whose `info` would not match the protocol, and names the reason.

**2. Answer failures with error classes.** A method returns `bridge.TransientError`, `bridge.RateLimitedError`,
`bridge.GoneError` (with `bridge.ReasonEditWindowClosed` for an edit that the messenger refuses only for the message's
age), `bridge.ForbiddenError` or `bridge.InvalidError`. Any other error, and a panic, is answered as `transient`.

```go
// classify tells Muster what a failure of Parley means. Only the bridge knows.
func classify(err error) error {
	var pe *parleyError
	if !errors.As(err, &pe) {
		return bridge.TransientError("Parley did not answer.")
	}
	switch pe.Code {
	case "slow_down":
		return bridge.RateLimitedError(time.Duration(pe.RetryIn)*time.Second, bridge.ProblemScopeChannel,
			"Parley asks to slow down.")
	case "message_not_found", "thread_removed":
		return bridge.GoneError("The message no longer exists.")
	case "edit_too_old":
		return bridge.GoneError("The message can no longer be edited.", bridge.ReasonEditWindowClosed)
	case "channel_not_found", "not_a_member", "bot_banned", "no_permission":
		return bridge.ForbiddenError("The bot is not a member of this channel.")
	case "user_blocked_bot":
		return bridge.ForbiddenError("This person cannot receive a message from the bot.")
	case "text_too_long", "bad_request":
		return bridge.InvalidError("Parley refused the request.")
	default:
		return bridge.TransientError("Parley is not available.")
	}
}
```

**3. Create the bridge with `bridge.New`.** Give it the bot's token in `Config.Bots`, the features in
`Config.Capabilities` and the limits in `Config.Limits`, and mount `b.Handler()` behind an HTTP server. The code below
is the body of a function that returns an `error`.

```go
token, err := os.ReadFile("/run/secrets/muster-token")
if err != nil {
	return err
}
messenger := &parleyMessenger{api: &parleyClient{}}

b, err := bridge.New(bridge.Config{
	Name:          "parley-bridge",
	Version:       "0.1.0",
	MessengerName: "Parley",
	Bots:          []bridge.Bot{{Name: "main", Token: strings.TrimSpace(string(token))}},
	Limits:        bridge.Limits{MaxBodyLength: 4000},
	Capabilities: bridge.Capabilities{
		Buttons: &bridge.Capabilities_Buttons{MaxPerMessage: 5, MaxPerRow: 5, DataMaxBytes: 64,
			Styles: []bridge.ButtonStyle{bridge.ButtonStylePrimary, bridge.ButtonStyleSuccess,
				bridge.ButtonStyleNeutral, bridge.ButtonStyleDanger}},
		ThreadMessages: new(bridge.CapabilitiesThreadMessagesAll),
		PrivateAnswers: &[]bridge.CapabilitiesPrivateAnswers{bridge.CapabilitiesPrivateAnswersEphemeral},
	},
	UserLookup: bridge.InfoUserLookupNone,
}, messenger)
if err != nil {
	return err
}
defer b.Close(context.Background())

srv := &http.Server{
	Addr:              "127.0.0.1:8095",
	Handler:           b.Handler(),
	ReadHeaderTimeout: 10 * time.Second,
	// No WriteTimeout: pollEvents holds a request open for up to 60 seconds.
}
return srv.ListenAndServe()
```

`MaxBodyLength` is the longest `body` that your bridge always accepts, after its own rendering; the protocol's smallest
value is 500, and the library takes at most 100000. `Capabilities` lists the optional features: a nil member is a
feature the bridge does not offer, and Muster never calls an operation that the bridge did not declare. To serve the
handler under a path prefix, mount it with `http.StripPrefix`.

!!! warning "No WriteTimeout"
    `pollEvents` holds a request open for up to 60 seconds. Serve the handler with no `WriteTimeout`, or one above 75
    seconds. A shorter one cuts a poll off without an answer, and its events reach Muster late.
    `ReadHeaderTimeout` and `IdleTimeout` are safe to set.

**4. Report what happens in the messenger.** When a person presses a button, writes in a Thread, deletes a message of
the bot or writes to the bot, call `b.Press`, `b.ThreadMessage`, `b.MessageDeleted` or `b.DirectMessage`. Each returns
at once, so confirm a press to your messenger within its deadline whatever Muster does. Give the messenger's own id of
the update as `UpdateID`: an update that the messenger delivers twice is then queued once.

```go
// onPress is called when a person presses a button in Parley. chat is what AnswerEvent needs to whisper to
// the person; the library keeps it with the event and never sends it to Muster.
func onPress(ctx context.Context, b *bridge.Bridge, updateID, messageID, data, chat string, who bridge.Person) error {
	// ... confirm the press to Parley first, then report it. Press returns at once.
	return b.Press(ctx, "main", bridge.Press{
		UpdateID: updateID, MessageID: messageID, User: who, Data: data, Chat: chat,
	})
}
```

`Chat` comes back as `ReportedEvent.Chat` when Muster answers the event; `b.ThreadMessage` and `b.DirectMessage` take
one too.

A direct message whose whole text is an Account link token becomes an `account_link` event; any other direct message is
ignored.

**5. Turn Mention markers into mentions.** `bridge.ReplaceMentions(body, mentions, render)` replaces each marker
`[@Name](muster-mention:ref)` by what `render` returns for its entry in `mentions`, as the sketch above does. For a
bridge without `NativeMentions`, pass a nil `render` and the markers become plain names.

**6. Push, if you want it.** Give a bot a `bridge.PushTarget` with the callback address that its Bridge Connection
shows and the push secret you entered on it, in `Config.Bots` or later with `b.SetPush`. `b.Close` stops the pushers.

**7. Use a `Store` that survives restarts.** `bridge.NewMemoryStore`, the default, keeps the idempotency keys and the
queued events in memory. A restart forgets them: a retried request that Muster sends after the restart then posts a
second message, and events that Muster has not collected are lost. Implement `bridge.Store` over your database and
set `Config.Store`. Long polls and pushers are woken in the process that queued an event, so with several processes
over one store, run each bot in one process only.

**8. Check it.** Run `muster bridge check` against your bridge (see [Test your bridge](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#test-your-bridge)).

The library's repository has a complete bridge in one file, `examples/minimal`: its messenger lives in memory and
writes every message the bot posts to the log. From a clone of the repository, with Go 1.26 or newer, run it with a
token, the one a Bridge Connection in Muster would hold:

```sh
git clone --branch v0.1.0 https://github.com/muster-io/muster-bridge-go && cd muster-bridge-go
printf example-token > /tmp/bt
```

### The Python library

The Python library is `muster-bridge` on PyPI, and its import package is `muster_bridge`. It needs Python 3.11 or
newer and depends only on Starlette, httpx and pydantic 2. Like the Go library, it is released from its own repository,
`muster-bridge-python`, under the MIT licence and without a CLA.

```sh
python3 -m venv .venv && . .venv/bin/activate
pip install muster-bridge
```

Its versions stay `0.x` until Muster 1.0 and speak the protocol versions Muster supports, as the Go library's do.

The library serves the protocol as an ASGI application, `BridgeApp`, and calls your code with `async` methods on the
event loop that serves the bridge. Call your messenger with an asynchronous client, or move a blocking call off the
loop with `asyncio.to_thread`.

**1. Implement `Messenger`.** It is a protocol of five coroutines, each given the name of the bot whose token Muster
sent: `post_message`, `edit_message`, `reply_in_thread`, `check_channel` and `answer_event`. Define them with
`async def`. The sketch below is for Parley, the same fictional messenger; its asynchronous client `ParleyClient`
stands for whatever library your messenger has.

```python
from muster_bridge import (
    AnswerShownShownAs,
    Mention,
    MessageContent,
    MessageEdited,
    MessageInput,
    MessagePosted,
    ReportedEvent,
    ThreadReplyInput,
    ThreadReplyPosted,
    replace_mentions,
)


def mention(m: Mention) -> str:
    """Write a mention of a person as Parley does."""
    return f"<@{m.external_id}>"


class ParleyMessenger:
    """The bridge's calls to the fictional messenger Parley."""

    def __init__(self, api: ParleyClient) -> None:
        self.api = api

    async def post_message(self, bot: str, message: MessageInput) -> MessagePosted:
        body = replace_mentions(message.body, message.mentions, mention)
        try:
            message_id = await self.api.send(message.channel_id, render(message.title, body))
        except ParleyError as error:
            raise classify(error) from error
        return MessagePosted(message_id=message_id)

    async def edit_message(self, bot: str, message_id: str, content: MessageContent) -> MessageEdited:
        try:
            await self.api.edit(message_id, render(content.title, content.body))
        except ParleyError as error:
            raise classify(error) from error
        return MessageEdited()

    async def reply_in_thread(self, bot: str, message_id: str, reply: ThreadReplyInput) -> ThreadReplyPosted:
        body = replace_mentions(reply.body, reply.mentions, mention)
        try:
            reply_id, thread = await self.api.reply(message_id, reply.thread_ref, body)
        except ParleyError as error:
            raise classify(error) from error
        return ThreadReplyPosted(message_id=reply_id, thread_ref=thread)

    async def check_channel(self, bot: str, channel_id: str) -> str:
        try:
            return await self.api.channel_name(channel_id)
        except ParleyError as error:
            raise classify(error) from error

    async def answer_event(self, bot: str, event: ReportedEvent, text: str) -> AnswerShownShownAs:
        """Answer an Account link in its direct chat, a Thread message in its Thread, and a press privately."""
        try:
            if event.type == "account_link":
                await self.api.send_direct(event.chat, text)
                return AnswerShownShownAs.direct
            if event.type == "thread_message":
                await self.api.reply(event.message_id, event.thread_ref, text)
                return AnswerShownShownAs.thread
            await self.api.whisper(event.chat, text)
            return AnswerShownShownAs.ephemeral
        except ParleyError as error:
            raise classify(error) from error
```

For the features you declare, also implement `UserFinder` (`find_user`, when `user_lookup` is not `none`),
`DirectMessenger` (`send_direct_message`, when the bridge offers direct messages) and `Deleter` (`delete_message`, when
it offers deletion). `BridgeApp` raises `ConfigError` for a configuration whose features lack their methods, or whose
`info` would not match the protocol, and names every reason.

**2. Answer failures with error classes.** A method raises `Transient`, `RateLimited` (with the wait `retry_after` in
seconds, and `scope` `"channel"` or `"bot"`), `Gone` (with `edit_window_closed=True` for an edit that the messenger
refuses only for the message's age), `Forbidden` or `Invalid`. Each takes a `detail` that Muster shows the Admin, so
keep secrets out of it. Any other exception is answered as `transient`, with a generic detail that carries none of its
text.

```python
from muster_bridge import BridgeError, Forbidden, Gone, Invalid, RateLimited, Transient


def classify(error: ParleyError) -> BridgeError:
    """Tell Muster what a failure of Parley means. Only the bridge knows."""
    match error.code:
        case "slow_down":
            return RateLimited("Parley asks to slow down.", retry_after=error.retry_in, scope="channel")
        case "message_not_found" | "thread_removed":
            return Gone("The message no longer exists.")
        case "edit_too_old":
            return Gone("The message can no longer be edited.", edit_window_closed=True)
        case "channel_not_found" | "not_a_member" | "bot_banned" | "no_permission":
            return Forbidden("The bot is not a member of this channel.")
        case "user_blocked_bot":
            return Forbidden("This person cannot receive a message from the bot.")
        case "text_too_long" | "bad_request":
            return Invalid("Parley refused the request.")
        case _:
            return Transient("Parley is not available.")
```

**3. Create the bridge with `BridgeApp`.** Give its `Config` the bot's token in `bots`, the features in
`capabilities` and the limits in `limits`, and serve the `BridgeApp` with uvicorn or another ASGI server.

```python
from pathlib import Path

import uvicorn

from muster_bridge import (
    Bot,
    BridgeApp,
    ButtonStyle,
    Capabilities,
    CapabilitiesButtons,
    CapabilitiesPrivateAnswer,
    CapabilitiesThreadMessages,
    Config,
    Limits,
)

token = Path("/run/secrets/muster-token").read_text(encoding="utf-8").strip()

config = Config(
    name="parley-bridge",
    version="0.1.0",
    messenger_name="Parley",
    bots=[Bot(name="main", token=token)],
    limits=Limits(max_body_length=4000, edit_max_age_seconds=None),
    capabilities=Capabilities(
        buttons=CapabilitiesButtons(
            max_per_message=5,
            max_per_row=5,
            data_max_bytes=64,
            styles=[ButtonStyle.primary, ButtonStyle.success, ButtonStyle.neutral, ButtonStyle.danger],
        ),
        thread_messages=CapabilitiesThreadMessages.all,
        private_answers=[CapabilitiesPrivateAnswer.ephemeral],
    ),
    user_lookup="none",
)
bridge = BridgeApp(config, ParleyMessenger(ParleyClient()))

uvicorn.run(bridge, host="127.0.0.1", port=8095)
```

`max_body_length` is the longest `body` that your bridge always accepts, after its own rendering; the protocol's
smallest value is 500, and the library takes at most 100000. `Limits` also needs `edit_max_age_seconds`, how long the
bot can edit a message after posting it, or `None` when edits never expire. A member of `Capabilities` left `None` is
a feature the bridge does not offer, and Muster never calls an operation that the bridge did not declare.

To serve the bridge under a path of a Starlette or FastAPI application, mount it there and pass its `lifespan` to the
application. The base URL of the Bridge Connection then ends with that path.

```python
from fastapi import FastAPI

app = FastAPI(lifespan=bridge.lifespan)
app.mount("/bridge", bridge)
```

Starlette runs the lifespan of the top-level application only, and the bridge's lifespan starts and stops its pushers.
An application with a lifespan of its own enters the bridge's in it, with `async with bridge.lifespan(app):`. A
`BridgeApp` has one lifespan, and its end stops the pushers for good: a program or a test that starts the application
again makes a new `BridgeApp`.

!!! warning "A read timeout above 75 seconds"
    `pollEvents` holds a request open for up to 60 seconds. uvicorn sets no timeout that cuts such a request short, but
    a proxy in front of the bridge needs a read timeout above 75 seconds. A shorter one cuts a poll off without an
    answer, and its events reach Muster late.

**4. Report what happens in the messenger.** When a person presses a button, writes in a Thread, deletes a message of
the bot or writes to the bot, await `bridge.press(...)`, `bridge.thread_message(...)`, `bridge.message_deleted(...)`
or `bridge.direct_message(...)`, all four coroutines, in the event loop that serves the bridge. Each queues
the event and returns at once, so confirm a press to your messenger within its deadline whatever Muster does. Give the
messenger's own id of the update as `update_id`: an update that the messenger delivers twice is then queued once.

```python
from muster_bridge import BridgeApp, Person


async def on_press(bridge: BridgeApp, update_id: str, message_id: str, data: str, chat: str, who: Person) -> None:
    """Report a press in Parley.

    chat is what answer_event needs to whisper to the person; the library keeps it with the event and never sends it
    to Muster.
    """
    # ... confirm the press to Parley first, then report it. press returns at once.
    await bridge.press("main", message_id=message_id, user=who, data=data, update_id=update_id, chat=chat)
```

`chat` comes back as `ReportedEvent.chat` when Muster answers the event; `thread_message` and `direct_message` take
one too. `Person` and the other models validate when they are built, so cut a display name to 200 characters before you
build the `Person` of a report. A report raises `UnknownBotError` for a bot that the `Config` lacks, `NotOfferedError`
for a feature that the bridge does not offer, and `InvalidEventError` for an event that would not match the protocol.
From another thread, hand the coroutine to the event loop with `asyncio.run_coroutine_threadsafe`.

A direct message whose whole text is an Account link token becomes an `account_link` event; any other direct message is
ignored.

**5. Turn Mention markers into mentions.** `replace_mentions(body, mentions, render)` replaces each marker
`[@Name](muster-mention:ref)` by what `render` returns for its entry in `mentions`, as the sketch above does. For a
bridge without `native_mentions`, pass `None` as `render` and the markers become plain names.

**6. Push, if you want it.** Give a bot a `PushTarget` with the callback address that its Bridge Connection shows and
the push secret you entered on it, in `Bot(push=...)` or later with `bridge.set_push(bot, target)`, from the thread of
the event loop that serves the bridge. The end of the bridge's lifespan, or `await bridge.aclose()`, stops the
pushers; the events stay queued for polling.

**7. Use a `Store` that survives restarts.** `MemoryStore`, the default, keeps the idempotency keys and the queued
events in memory. A restart forgets them: a retried request that Muster sends after the restart then posts a second
message, and events that Muster has not collected are lost. Implement the protocol `Store` over your database and pass
it as `Config(store=...)`. Long polls and pushes are woken in the process that queued an event, so with several
processes over one store, run each bot in one process only.

**8. Check it.** Run `muster bridge check` against your bridge (see [Test your bridge](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#test-your-bridge)).

The library's repository has a complete bridge in one file, `examples/memory_bridge.py`: its messenger lives in memory
and writes every message the bot posts to the log. With the library installed as above, clone the repository, install
uvicorn beside the library and run the example with a token, the one a Bridge Connection in Muster would hold:

```sh
git clone --branch v0.1.0 https://github.com/muster-io/muster-bridge-python && cd muster-bridge-python
pip install uvicorn
printf example-token > /tmp/bt
python examples/memory_bridge.py --token-file /tmp/bt
```

Like the Go library's example, it listens on `127.0.0.1:18095`, knows the channels `alerts` and `ops` and the people
`alice` and `bob`, and offers every feature of the protocol, or only those that `BRIDGE_FEATURES` lists. The `curl`
calls and the `muster bridge check` command of [the Go library](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#the-go-library) give the same answers against it.
Outside the protocol, the example serves `POST /demo/press`, which presses the first button of a message as a person,
so that a script can play the person of an interactive check. It has no authentication of its own: keep it on
loopback.

The library's README and the docstrings of the package describe what the library does for every operation.

### The example bridge

The **example bridge** is built on the Go library and lives in its repository, in `examples/chat`. It is a small chat
that runs in memory, with a web page: channels, Threads, buttons, direct chats between a person and the bot, and users
found by login. It offers every feature of the protocol, one by one switchable, and both event delivery modes. Use it
to try Muster without a real messenger, and as a reference for your own bridge.

Its image is `ghcr.io/muster-io/muster-example-bridge`, tagged `vX.Y.Z` with each release of the Go library; `edge`
follows the `master` branch of the library's repository.

```sh
docker run --rm -p 8095:8095 -e BRIDGE_TOKEN=example-token ghcr.io/muster-io/muster-example-bridge:v0.1.0
```

The page is then at `http://127.0.0.1:8095/`, and the protocol under `/v1/` on the same port. `BRIDGE_FEATURES` limits
the features the example offers, comma-separated: with `BRIDGE_FEATURES=thread_messages`, for one, it shows no buttons,
and people answer with Text commands in Threads.

!!! warning "The page has no authentication"
    The protocol under `/v1/` needs the token, but the example's page and its JSON API under `/chat/api/` have no
    authentication of their own: whoever reaches them reads every message and acts as any person. Keep the example on
    your machine's loopback, or put it behind an authenticating proxy.

**Next to `muster dev`:**

1. Start `muster dev` from a Muster checkout (`make dev`) and sign in.
2. Start the example on the host's loopback at `127.0.0.1:18095`. From a checkout of the library, `go run
   ./examples/chat -token-file <file>` listens there by default. With the image on Linux, use `--network host`, mount
   the token file, and give `-listen 127.0.0.1:18095 -token-file /token`, because the image listens on `:8095`
   otherwise. The image runs as the user 65532, so the mounted file must be readable by that user, for example with
   mode 0644. `muster dev` lets Muster call loopback addresses; elsewhere the Organization's outbound address policy
   blocks them, and you allow the example's address there.
3. Create a Bridge Connection with the base URL `http://127.0.0.1:18095`, the token you gave the example and the
   event delivery **Polling**. **Check connection** shows "Messenger: Example chat" and the features the example
   offers.
4. Create a Destination on that Connection for the channel `alerts`. **Send test message** makes the message
   "🧪 Test message" appear in `#alerts` on the page.
5. Alert Groups that a Route sends to the Destination appear in `#alerts`, one Root message each. A press acts for the
   Muster User whose account is linked to the person who pressed, so link an account first: copy the token from your
   profile, pick the person under "You are", open their direct chat with the bot under "Direct", and send the token.

**Next to the Quick start:** run the example as one more service of the compose project, so that Muster reaches it by
name and nothing on the host's loopback is involved.

1. In the directory of the [Quick start](https://muster-io.github.io/muster/latest/quick-start.md), where `docker-compose.yml` and `.env` are, add a token to
   `.env` and write a file `compose.override.yaml` next to them, which Docker Compose merges into the project by itself.
   `docker compose up -d --wait` then starts the example, and leaves Muster running if it already runs:

    ```sh

    cat >compose.override.yaml <<'EOF'

      example-bridge:
        image: ghcr.io/muster-io/muster-example-bridge:v0.1.0

    ```

    The example's page is published on the loopback of the host only, at `http://127.0.0.1:8095/`, because it has no

    The whole port is published, so `/v1/` is reachable on the host's loopback too, and it needs the token. Muster
    reaches
    the example inside the compose network.
2. Create a Bridge Connection with the base URL `http://example-bridge:8095`, the token from `.env`

`compose.override.yaml`. Do not run `docker compose down -v` for this: it deletes Muster's database too.

For **Push**, choose a push secret (see [Push](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#push)), enter it in the Connection, and restart the example with
`BRIDGE_PUSH_URL` set to the callback address that the Connection shows, and the secret in `BRIDGE_PUSH_SECRET` or in
the file of `-push-secret-file`. With the compose service, set `BRIDGE_PUSH_URL` in the override's `environment` to the

## The protocol without a library

This part describes the protocol in the order a bridge author implements it. The full definition is the
[Bridge protocol reference](https://muster-io.github.io/muster/latest/reference/bridge/spec/index.html), rendered from `api/bridge.yaml`; the page
[Bridge protocol](https://muster-io.github.io/muster/latest/reference/bridge-protocol.md) in the Reference gives its version and the specification itself.
Every request and answer below follows that specification. The values in the examples are examples only.

**Conventions.**

- Every path is under `/v1/`. `GET /v1/info` returns `protocol_version` `"1"`. A bridge ignores request fields it does
  not know, and Muster ignores fields of `info` it does not know. A change that breaks existing bridges gets a new major
  path.
- Muster sends the Connection's token on every request as `Authorization: Bearer <token>`. The bridge answers `401` to
  a missing or wrong token. Muster sends the token only to the base URL saved on the Connection, and follows no
  redirects.
- The Bridge Connection's base URL may have a path prefix. Muster sends every request to `<base URL>/v1/…`.
- `message_id` and `channel_id` are opaque strings of up to 512 characters. Muster percent-encodes each as one path
  segment, and the bridge decodes it.
- Request bodies are JSON, with `Content-Type: application/json`. Errors are `application/problem+json`.
- One token is one bot. A bridge that serves several Connections tells them apart by the token.

**What every bridge implements:** `getInfo`, `postMessage`, `editMessage`, `replyInThread`, `checkChannel`,
`answerEvent`, and events by `pollEvents`, by the `bridgeEvent` push, or by both. A bridge sends at least
`account_link` events, because every bridge takes Account link tokens. Everything else is optional and declared in the
`capabilities` of `info`.

### `getInfo`

Muster calls it on every Connection check, and again before a call that depends on it when its copy is older than 10
minutes. A bridge whose features change is therefore picked up without a restart of Muster.

```http
GET /v1/info HTTP/1.1
Authorization: Bearer <token>
```

```json
{
  "protocol_version": "1",
  "bridge": { "name": "parley-bridge", "version": "0.1.0" },
  "messenger": { "name": "Parley" },
  "capabilities": {
    "buttons": { "max_per_message": 5, "max_per_row": 5, "data_max_bytes": 64,
                 "styles": ["primary", "success", "neutral", "danger"] },
    "thread_messages": "all",
    "direct_messages": { "bot_can_start": true },
    "private_answers": ["ephemeral"],
    "native_mentions": true,
    "group_mentions": true,
    "everyone_mentions": ["channel", "here"],
    "quiet_messages": true,
    "status_color": true
  },
  "limits": { "max_body_length": 4000, "edit_max_age_seconds": null },
  "user_lookup": "login",
  "event_delivery": ["poll", "push"],
  "link_url_template": "https://chat.example.org/bots/muster?start={token}"
}
```

- `messenger.name` is shown on the Connection and the Destinations.
- `limits.max_body_length` is the longest `body` you always accept, in code points, at least 500.
  `limits.edit_max_age_seconds` is how long after posting the bot can still edit a message, at least 300, or `null`
  when edits never expire.
- `user_lookup` is what a person enters to be found for an Account link by code: `email`, `login`, `username`,
  `user_id` or `none`.
- `event_delivery` lists the modes you offer, `poll`, `push` or both. Each Connection chooses one.
- `link_url_template` is an `http` or `https` link that opens a chat with the bot and hands it the Account link token,
  with `{token}` where the token goes. Use `null` or leave it out when your messenger has no such link.

The answer must match the protocol and be smaller than 64 KiB, or the Connection check fails.

### `checkChannel`

The Destination check. It must **not** post anything. Answer `200` only when the bot can post, edit its own messages and
reply in Threads in the channel. Muster runs it when a Destination is saved, when a person presses **Check**, and every
few minutes while the Destination is Broken.

```http
POST /v1/channels/ch-alerts/check HTTP/1.1
Authorization: Bearer <token>
```

```json
{ "channel_id": "ch-alerts", "name": "alerts" }
```

`name` is the channel's name as people see it. When the channel does not exist, or the bot cannot use it, answer
`forbidden` with a `detail` that a person can act on:

```json
{
  "title": "Forbidden",
  "status": 403,
  "detail": "The bot is not a member of this channel.",
  "class": "forbidden"
}
```

### `postMessage`

Posts a Root message, a Storm summary or a test message. The request carries an `Idempotency-Key`, and the answer
names the message for later edits and Thread replies.

```http
POST /v1/messages HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: <key>
Content-Type: application/json
```

```json
{
  "channel_id": "ch-alerts",
  "kind": "root",
  "status": "firing",
  "color": "#d32f2f",
  "emoji": "🔴",
  "title": "#42 HighErrorRate",
  "link": {
    "url": "https://muster.example.org/alert-groups/AGK7M3QX9P2RTA",
    "label": "Open in Muster"
  },
  "body": "[@Alice Smith](muster-mention:m1)\n\nprod · started 14:03\n\n> **namespace** payments\n\n- `api-7f9c` error rate 12 %\n- `api-5d2a` error rate 9 %\n\n[Runbook](https://wiki.example.org/runbooks/high-error-rate)",
  "buttons": [
    { "label": "Ack", "style": "primary", "data": "a1.k2.QmFzZTY0U2lnbmF0dXJlRXhhbXBsZQ" },
    { "label": "Resolve", "style": "success", "data": "a2.k2.U2Vjb25kU2lnbmF0dXJlRXhhbXBsZQ" }
  ],
  "mentions": [
    { "ref": "m1", "external_id": "u-alice", "display_name": "Alice Smith" }
  ],
  "notify": true
}
```

```json
{
  "message_id": "m-77",
  "thread_ref": null,
  "url": "https://chat.example.org/c/alerts/m-77",
  "truncated": false,
  "replayed": false
}
```

- `kind` is `root`, `storm_summary` or `test`. `status` is `firing`, `acknowledged`, `snoozed`, `resolved` or `storm`.
- `message_id` is opaque to Muster: encode in it whatever you need to edit the message and reply under it.
- `thread_ref` may be returned when the messenger's Thread id is known at once; otherwise the first `replyInThread`
  returns it (see [`thread_ref`](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#thread_ref)).
- `url` is a link that opens the message in your messenger, if it has one. Muster shows it on the Alert Group page and
  links to it from the Thread of an older Root message.
- `truncated` is `true` when you shortened the body to fit your messenger (see
  [Rendering the envelope](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#rendering-the-envelope)).

### `editMessage`

Replaces the whole message with the envelope of its new state. An edit is always Quiet and never carries Mentions, so
its body has no `channel_id`, `kind`, `mentions` or `notify`. An empty `buttons` removes the buttons. Editing to the
state that the message already shows is a success.

```http
PATCH /v1/messages/m-77 HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "status": "acknowledged",
  "color": "#f57c00",
  "emoji": "🟠",
  "title": "#42 HighErrorRate",
  "link": {
    "url": "https://muster.example.org/alert-groups/AGK7M3QX9P2RTA",
    "label": "Open in Muster"
  },
  "body": "prod · started 14:03\n\n> **namespace** payments\n\n- `api-7f9c` error rate 12 %\n- `api-5d2a` error rate 9 %",
  "buttons": [
    { "label": "Unack", "style": "neutral", "data": "a3.k2.VGhpcmRTaWduYXR1cmVFeGFtcGxl" },
    { "label": "Resolve", "style": "success", "data": "a2.k2.U2Vjb25kU2lnbmF0dXJlRXhhbXBsZQ" }
  ]
}
```

```json
{ "truncated": false }
```

A message that no longer exists is `gone`. An edit that the messenger refuses because the message is older than it
allows is `gone` with the `reason` `edit_window_closed` (see [Edit windows](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#edit-windows)).

### `replyInThread`

Posts a reply in the Thread of a message, usually a Root message. Muster sends the last `thread_ref` it received for
that message, or `null` when it has none, and the bridge creates the Thread if its messenger needs that.

```http
POST /v1/messages/m-77/thread-replies HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: <key>
Content-Type: application/json
```

```json
{
  "thread_ref": null,
  "body": "New alert: `api-1c3e` error rate 14 %",
  "buttons": [],
  "mentions": [],
  "notify": false
}
```

```json
{
  "message_id": "m-78",
  "thread_ref": "t-77",
  "truncated": false,
  "replayed": false
}
```

`message_id` of the answer is the reply; a press on its buttons names it. A Thread that no longer exists, or a message
that was deleted, is `gone`. A reply may carry buttons, such as "Still on it" on a Reminder, when the bridge declares
`buttons`.

### Events and `answerEvent`

The rest of the required protocol is the way a person's actions reach Muster, and the way Muster answers them:

- `pollEvents`, `GET /v1/events`, returns the events after a cursor, and the `bridgeEvent` push posts each event,
  signed, to Muster's callback address. A bridge offers either or both; the Admin chooses one per Connection. See
  [Events](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#events).
- `answerEvent`, `POST /v1/answers`, shows Muster's answer to the person behind an event. See
  [Presses within 3 seconds, and answers later](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#presses-within-3-seconds-and-answers-later).

### Optional: `deleteMessage`, `findUsers` and `sendDirectMessage`

- `DELETE /v1/messages/{message_id}` is offered when `capabilities.delete` is declared. Muster L1 never deletes
  messages; the operation is reserved so that a later version of Muster can remove its test messages without a new
  protocol version. A message that no longer exists is a success, `204`.
- `GET /v1/users?handle=alice` is offered when `user_lookup` is not `none`. Muster calls it when a person asks to link
  an account by a code. The answer lists the one account with that handle, or none; a handle you cannot search for is
  `invalid`.
- `POST /v1/direct-messages` is offered when `capabilities.direct_messages` is declared with `bot_can_start`. Muster
  uses it to send the code of an Account link. An account that cannot receive a message from the bot is `forbidden`.

```http
GET /v1/users?handle=alice HTTP/1.1
Authorization: Bearer <token>
```

```json
{ "items": [ { "external_id": "u-alice", "display_name": "Alice Smith", "handle": "alice" } ] }
```

```http
POST /v1/direct-messages HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: <key>
Content-Type: application/json
```

```json
{
  "user_external_id": "u-alice",
  "body": "You requested a link to Muster. Do not share this code.\n\n**K7M3Q9XT**"
}
```

```json
{ "message_id": "dm-12", "replayed": false }
```

## Required and optional features

The `capabilities` of `info` declare the optional features. A missing member means the feature is not offered, and
Muster adapts:

`buttons`
:   Without it: Muster sends no buttons. When the bridge has `thread_messages`, a Root message that is not resolved ends
    with the commands line, such as "Reply in the Thread: ack · resolve · snooze 1h", and people write **Text
    commands** in the Thread. Without either, the link to Muster is the only way to act.

`thread_messages`
:   Without it: Muster receives no Text commands. `all` reports every message of a person in a Thread of a message of
    the bot, `mentions_only` only those that mention the bot (the commands line then says "mentioning the bot").

`direct_messages` with `bot_can_start`, and a `user_lookup` other than `none`
:   Without it: Account links work by token only: the person sends the token to the bot. With both, a person can also
    link by a code that the bot sends.

`private_answers`
:   Without it: Muster's answer to a press appears in the Thread of the message instead of privately. `ephemeral` is a
    message only the person sees, `popup` a short plain-text pop-up.

`native_mentions`
:   Without it: a Mention marker of a person is rendered as the person's name in plain text, which notifies nobody.

`group_mentions`
:   Declares that the bridge renders a mention of a group of its messenger. Without it: Muster offers no group entry or
    Team mention for the Connection's Destinations and sends no `group` entry; a group an entry still names is left out
    of the message.

`everyone_mentions`
:   Lists the mentions of everyone in the chat the messenger has, by the symbolic names `channel`, `here`, `all` and
    `everyone`. Without a name: Muster offers no such entry for it and sends none; one an entry still names is left
    out of the message.

`quiet_messages`
:   Without it: a Quiet message (`notify: false`) is posted as an ordinary message, without Mentions.

`status_color`
:   Without it: the bridge shows the `emoji` of the status instead of the `color`.

`deletion_events`
:   Without it: Muster learns that a Root message was deleted from `gone` on its next edit or Thread reply, instead of
    at once.

`delete`
:   Without it: Muster L1 never deletes messages, so nothing changes.

`link_url_template`
:   Without it: the profile shows the Account link token without a link that opens the bot.

`edit_max_age_seconds`
:   Without it: a value of `null` means Muster edits a Root message for as long as its Alert Group changes.

A bridge sends `press` events only with `buttons`, `thread_message` events only with `thread_messages`, and
`message_deleted` events only with `deletion_events`. Muster handles every event type whatever its copy of `info`
says, so an event sent just after a feature was switched on is not lost.

## Rendering the envelope

Muster sends a JSON envelope: the `status`, `color` and `emoji`, the `title`, the `link`, the `body` and the `buttons`, and
for a Root message and a test message also the `layout`, the same content as structured data (see
[Render the structured layout](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#render-the-structured-layout)). **The bridge renders it in its messenger's markup.**
Muster never writes a messenger's markup for a bridge.

**The body is CommonMark 0.31 with one extension, strikethrough** (`~~text~~`) as GitHub Flavored Markdown writes it.

- Muster uses paragraphs, hard line breaks, emphasis, strong emphasis, strikethrough, code spans, links, bullet lists
  and block quotes.
- Muster never uses headings, tables, images or raw HTML.

Use a CommonMark parser rather than patterns, and map each construct to the closest thing your messenger has. The
`title` is plain text. Show it as the heading of the message, linked to `link`. Alert data in the body is already
escaped for CommonMark, and it cannot mention anyone or form a link.

**Links** are `http` and `https` links, plus Mention markers.

**Mention markers** are links of the form `[@Display Name](muster-mention:<ref>)`, where `ref` names an entry of
`mentions`. A bridge with `native_mentions` renders the marker as its messenger's mention of the entry's `external_id`,
which notifies that person. Any other bridge renders the link text alone, as plain text. Each entry of `mentions` has a
`kind`: `user`, the default and what Muster sends when it omits the field, `group`, which a bridge that declares
`group_mentions` renders as its messenger's group mention, with the group's name as `external_id`, and `everyone`, which
a bridge renders as the mention of everyone in the chat named by `external_id`, one of `channel`, `here`, `all` and
`everyone` that it lists in `everyone_mentions`. Muster sends a `group` or an `everyone` only while its copy of `info`
declares it, but that copy may be up to `bridge.info_max_age` old: a bridge that receives a kind it no longer declares
never refuses the message, and shows the marker's link text, which notifies nobody. The Mentions of a Loud message form
the first line of its body, which keeps the whole Mentions that fit half of `limits.max_body_length`; see
[Whom a message mentions](https://muster-io.github.io/muster/latest/concepts/mentions.md#what-each-messenger-supports). The `external_id` is the account's id
in the messenger as the bridge reported it when the account was linked.

**Colours and emoji.** `color` is `#rrggbb` in lower case, for messengers that colour messages. `emoji` is the status
as an emoji, for messengers that do not: 🔴 firing, 🟠 acknowledged, ⚪ snoozed, 🟢 resolved, ⛈ storm.

**Loud and Quiet.** `notify: true` is a **Loud** message: it should notify people as the messenger's new messages do,
and it carries the `mentions` of the envelope. `notify: false` is **Quiet**: with `quiet_messages` declared, send it
without a notification. Edits are always Quiet. Do not make an edit ring anyone.

**Buttons.** Each button has a `label` (up to 64 characters), a `style` hint (`primary`, `danger`, `neutral` or
`success`), and `data`. The data is opaque and signed by Muster; return it unchanged with the press. Map a style that
your messenger lacks to the closest one, or show a plain button. Muster sends at most `max_per_message` buttons, and
drops Snooze buttons first: the preset of the first day of the week ("Until Monday 09:00"), then the preset of the next
morning ("Until tomorrow 09:00"), then the durations from the longest. A firing Root message on a Paging Route has
seven buttons, Ack, Resolve, three durations and the two presets, so a bridge that declares `max_per_message: 5` gets
Ack, Resolve and the three durations.

**Length and safe truncation.** Muster keeps the `body` within `limits.max_body_length` code points of the CommonMark it
sends. Choose that limit so that a body of that length fits your messenger after your rendering. When the rendered
message is still too long, you make the final cut where your markup needs it, and answer `truncated: true`. Cut by
whole code points, never inside an entity, a tag or a surrogate pair, and close any markup you opened. A request whose
body exceeds `max_body_length` is `invalid`.

### Render the structured layout

A Root message and a test message carry their content twice: as CommonMark in `body`, and as plain-text data in
`layout`, beside it. **A bridge renders either `body` or `layout`, never both.** A bridge that ignores `layout` works as
before. One that renders it has no CommonMark to parse and no `#N` that its messenger turns into a hashtag, and decides
for itself how its messenger shows a field, a label or a person.

**Render `body` whenever `layout` is absent.** Muster sends no `layout` for a Storm summary or a Thread reply, for a Root
message whose Route has its own Root message template or line template, for the Fallback template that shows when a
template fails, and, of course, in a request from a version of Muster that has none. Those messages hold content that
only `body` has. The Routes' own templates are described in
[Messages and templates](https://muster-io.github.io/muster/latest/configure/messages-and-templates.md#what-you-can-change-and-what-you-cannot).

What `layout` has, in the order a message shows it:

`number` and `title`
:   The Alert Group's number alone, such as `1287`, and its title without it. `#1287` written in text becomes a hashtag
    in some messengers, so the number is a field of its own: write it as your messenger writes a number that is not a
    tag, or as a field.

`status`
:   `key` (`firing`, `acknowledged`, `snoozed` or `resolved`) for your colour or emoji, and `word`, the status in the
    Route's language.

`fields`
:   A list of `name` and `value`: Severity, Route, Teams (left out when the Alert Group has none) and Started.

`summary` and `description`
:   Two texts, empty when there is none.

`labels`
:   The key labels of the Route's [Labels in the message](https://muster-io.github.io/muster/latest/configure/messages-and-templates.md#labels-in-the-message),
    each a `key` and a `value`: the value of a label whose Alerts differ is "3 values", in the Route's language.

`alerts`
:   `null` for an Alert Group of one Alert. Otherwise the `label` that tells the Alerts apart, `values` — each with
    `resolved`, firing ones first — and `total`, how many Alerts the Alert Group has. Muster sends no "…and 7 more":
    count the Alerts you do not show yourself, as `total` minus the values you listed, because you may cut more than
    Muster did.

`notices`
:   The notices that apply, such as "Reopened ×2", then the footer, as lines: who snoozed or resolved the Alert Group, or
    why Muster resolved it. A test message has the mark of a test as its first notice, which is localized ("🧪 Test message" is the English form), and a bridge shows it before the
    rest of the message, so that nobody takes a test for an Alert Group.

`owner` and `assignees`
:   People, each with a `name`, their name in Muster, and a `ref`. `owner` is who acknowledged the Alert Group, while it
    is acknowledged, and `null` otherwise; it has no `team`, and "Escalation chains stopped" after an acknowledgement
    that stopped running chains is the last line of `notices`. `assignees` are the people whom Muster's
    [Escalation chains](https://muster-io.github.io/muster/latest/concepts/escalation-chains.md#assignees) Paged last and reached, before an acknowledgement,
    and are empty until Muster Pages people; each has the owning Team of their chain in `team`, an object with a `name`,
    where it has one. Write them as a line of their own, such as "Assignees: @ivan (devops), @petr (payments)", not as
    part of the `notices`. A `ref` names the entry of the same `ref` in the envelope's `mentions`, which has the
    person's `external_id` in your messenger, so that you mention them by your own user id. It is `null` where the
    message carries no Mention of them: in every edit, which carries no Mentions at all, and in a message to a bridge
    without `native_mentions` or for a person whose account is not linked. Then write the `name`. A person who
    snoozed or resolved the Alert Group is no `owner`: they appear only as text in a line of `notices`, with no `ref`,
    so that a bridge cannot mention them from `layout`.

`links`
:   A list of `label` and `url`, "Open in Muster" first. A `url` is an absolute `http` or `https` address as the Route
    gives it, and may be an IRI, with characters outside ASCII in its host or path: a messenger that needs ASCII
    encodes it.

The buttons are not in `layout`: they stay in the envelope's `buttons`.

**The values are plain text, never CommonMark.** `Queue *full* on #1` arrives as it is, and the bridge escapes it for its
messenger. Alert data in them cannot mention anyone, and a value that contains markup is data, not markup. This is the
one rule that decides whether the bridge is safe: escape every value you write. A link's `url` is a link target, not
text: do not escape it like text, but give it to your messenger as a link, and let your messenger refuse what it cannot
open.

**When Muster shortens the `body`** to `limits.max_body_length`, it shortens `layout` the same way: the description
first, then the Alerts, the summary and the labels, while the title, the status, the fields, the people and the links
stay. A bridge that has to cut more cuts in the same order.

**A `layout` that does not match the protocol** is no reason to refuse the message. The libraries for Go and Python,
from 0.1.1, drop it, accept the message and give your code `Layout` nil, or `layout` `None`, so that you render the
`body`, and log one warning with the place and the reason, never the content. A bridge without a library does the same:
it treats a `layout` it cannot read as absent.

The examples below render the message for Parley, the fictional messenger of [Start with a library](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#start-with-a-library).
Parley reads `*bold*`, `~strikethrough~`, `` `code` `` and `<@id>` mentions, so a hashtag `#42` and the other
characters it reads are escaped. They print the same lines for the same message:

```text

Teams: payments
Started: 2026-10-04 03:12 UTC

The container exceeded its limit.
```

**In Go**, `bridge.MessageInput` and `bridge.MessageContent` have `Layout *bridge.Layout`, nil when Muster sends none. The
library has checked it against the protocol before it calls your code.

```go
// parleyEscape makes plain text safe for Parley, which reads *bold*, ~strikethrough~, `code`, <@id> mentions and #tags.
var parleyEscape = strings.NewReplacer(`\`, `\\`, `*`, `\*`, `~`, `\~`, "`", "\\`", `<`, `\<`, `#`, `\#`).Replace

// renderLayout writes the structured layout of a Root message or a test message as text for Parley. mentions is the
// envelope's list, which an edit leaves empty.
func renderLayout(l *bridge.Layout, kind bridge.MessageKind, mentions []bridge.Mention) string {
	byRef := map[string]bridge.Mention{}
	for _, m := range mentions {
		byRef[m.Ref] = m
	}
	person := func(p bridge.LayoutPerson) string {
		if p.Ref != nil {
			if m, ok := byRef[*p.Ref]; ok {
				return "<@" + m.ExternalId + ">"
			}
		}
		return parleyEscape(p.Name)
	}
	var lines []string
	add := func(format string, args ...any) { lines = append(lines, fmt.Sprintf(format, args...)) }

	// The mark of a test message is its first notice, and it comes before everything else.
	notices := l.Notices
	if kind == bridge.MessageKindTest && len(notices) > 0 {
		add("*%s*", parleyEscape(notices[0]))
		notices = notices[1:]
	}
	add("*%s* %s", parleyEscape(l.Status.Word), parleyEscape(l.Title))
	add("Alert Group %d", l.Number)
	for _, f := range l.Fields {
		add("%s: %s", parleyEscape(f.Name), parleyEscape(f.Value))
	}
	for _, text := range []string{l.Summary, l.Description} {
		if text != "" {
			lines = append(lines, parleyEscape(text))
		}
	}
	if len(l.Labels) > 0 {
		pairs := make([]string, len(l.Labels))
		for i, label := range l.Labels {
			pairs[i] = parleyEscape(label.Key) + "=" + parleyEscape(label.Value)
		}
		lines = append(lines, strings.Join(pairs, " · "))
	}
	if a := l.Alerts; a != nil {
		values := make([]string, len(a.Values))
		for i, v := range a.Values {
			values[i] = parleyEscape(v.Value)
			if v.Resolved {
				values[i] = "~" + values[i] + "~"
			}
		}
		line := parleyEscape(a.Label) + ": " + strings.Join(values, ", ")
		// The bridge counts what it does not show: Muster sends the total, not "…and K more".
		if more := a.Total - len(a.Values); more > 0 {
			line += fmt.Sprintf(" …and %d more", more)
		}
		lines = append(lines, line)
	}
	for _, notice := range notices {
		lines = append(lines, parleyEscape(notice))
	}
	if l.Owner != nil {
		add("Acknowledged by %s", person(*l.Owner))
	}
	if len(l.Assignees) > 0 {
		names := make([]string, len(l.Assignees))
		for i, p := range l.Assignees {
			names[i] = person(p)
		}
		add("Paged: %s", strings.Join(names, ", "))
	}
	for _, link := range l.Links {
		add("%s: %s", parleyEscape(link.Label), link.Url)
	}
	return strings.Join(lines, "\n")
}
```

```go
func (m *parleyMessenger) PostMessage(ctx context.Context, bot string, in bridge.MessageInput) (
	bridge.MessagePosted, error) {

	}
	if err := m.api.Edit(ctx, messageID, text); err != nil {
		return bridge.MessageEdited{}, classify(err)
	}
	return bridge.MessageEdited{}, nil
```

**In Python**, `MessageInput` and `MessageContent` have `layout`, `None` when Muster sends none:

```python
import re

from muster_bridge import Layout, LayoutPerson, Mention, MessageKind


def parley_escape(text: str) -> str:
    """Make plain text safe for Parley, which reads *bold*, ~strikethrough~, `code`, <@id> mentions and #tags."""
    return re.sub(r"([\\*~`<#])", r"\\\1", text)


def render_layout(layout: Layout, kind: MessageKind, mentions: list[Mention]) -> str:
    """Write the structured layout of a Root message or a test message as text for Parley.

    `mentions` is the envelope's list, which an edit leaves empty."""
    by_ref = {m.ref: m for m in mentions}

    def person(who: LayoutPerson) -> str:
        mention = by_ref.get(who.ref) if who.ref else None
        return f"<@{mention.external_id}>" if mention else parley_escape(who.name)

    lines: list[str] = []
    notices = list(layout.notices)
    # The mark of a test message is its first notice, and it comes before everything else.
    if kind == MessageKind.test and notices:
        lines.append(f"*{parley_escape(notices.pop(0))}*")
    lines.append(f"*{parley_escape(layout.status.word)}* {parley_escape(layout.title)}")
    lines.append(f"Alert Group {layout.number}")
    lines += [f"{parley_escape(f.name)}: {parley_escape(f.value)}" for f in layout.fields]
    lines += [parley_escape(text) for text in (layout.summary, layout.description) if text]
    if layout.labels:
        lines.append(" · ".join(f"{parley_escape(l.key)}={parley_escape(l.value)}" for l in layout.labels))
    if layout.alerts:
        values = [f"~{parley_escape(v.value)}~" if v.resolved else parley_escape(v.value) for v in layout.alerts.values]
        line = f"{parley_escape(layout.alerts.label)}: {', '.join(values)}"
        # The bridge counts what it does not show: Muster sends the total, not "…and K more".
        if (more := layout.alerts.total - len(values)) > 0:
            line += f" …and {more} more"
        lines.append(line)
    lines += [parley_escape(notice) for notice in notices]
    if layout.owner:
        lines.append(f"Acknowledged by {person(layout.owner)}")
    if layout.assignees:
        lines.append("Paged: " + ", ".join(person(who) for who in layout.assignees))
    lines += [f"{parley_escape(link.label)}: {link.url}" for link in layout.links]
    return "\n".join(lines)
```

## `Idempotency-Key`

Every request that creates something carries an `Idempotency-Key` header: `postMessage`, `replyInThread`,
`sendDirectMessage` and `answerEvent`. The key is one to 255 printable ASCII characters without spaces. Muster reuses a
key when it retries a request, also after a crash or a timeout.

The bridge must:

- store each key **per token**: the same key sent with another Connection's token is another request;
- keep each key with its **successful** (`2xx`) result for **at least 24 hours**, because Muster may retry long after
  the first attempt, and a bridge that forgot the key would post a second message;
- answer a repeated key with that first result and `replayed: true`, whatever the body of the repeated request, without
  creating anything again;
- store nothing for a failed request, so that its retry is a new attempt;
- answer a repeated key whose first request is still running with `transient`;
- pass the key on to the messenger when the messenger has an idempotency mechanism of its own.

Muster treats a `postMessage` whose answer says `replayed` as the same message, and follows it with an `editMessage` of
its current state, because the retry may carry a newer state than the request whose answer was lost. If the bridge did
not know the key, the retry posts a second message, and Muster records a **possible duplicate** in the Alert Group's
Timeline.

```mermaid
sequenceDiagram
  autonumber
  participant M as Muster
  participant B as Bridge
  participant X as Messenger

  M->>B: POST /v1/messages with Idempotency-Key K1
  B->>X: post the message
  X-->>B: posted
  Note over B: stores K1 with its result for 24 hours, per token
  B--xM: the answer is lost, Muster times out
  M->>B: POST /v1/messages with the same Idempotency-Key K1
  B-->>M: 201 with message_id and replayed true, nothing is posted again
  M->>B: PATCH /v1/messages/message_id with the current state
  B->>X: edit the message
  B-->>M: 200 truncated false
  M->>B: POST /v1/messages/message_id/thread-replies with Idempotency-Key K2 and thread_ref null
  B->>X: reply in the Thread
  B-->>M: 201 with thread_ref
  M->>B: POST the next reply with Idempotency-Key K3 and that thread_ref
  B-->>M: 201 with the same thread_ref
```

## `thread_ref`

The messenger decides how a Thread is named, and some messengers need a Thread to be created before the first reply.
The `thread_ref` carries that between calls, so that the bridge needs no store of its own that maps messages to Threads:

- `postMessage` may return a `thread_ref` when the Thread's id is known at once, and may leave it out or return
  `null`.
- `replyInThread` carries the last `thread_ref` Muster received for that message, from `postMessage` or from an earlier
  reply, or `null` when it has none. When it is `null`, create the Thread if your messenger needs that.
- `replyInThread` always returns a `thread_ref`. Muster stores it and sends it with the next reply of the same Thread.

A `thread_ref` is opaque to Muster, up to 512 characters, and it may equal the message id. In a `thread_message` event,
the `thread_ref` is the same value, or `null`.

## Presses within 3 seconds, and answers later

The bridge confirms a press to its messenger itself, within the messenger's deadline and **at most 3 seconds after the
press**, before Muster has seen it. Messengers expect that quick answer; Muster would be too late. Only then does the
bridge report the press to Muster as an event.

When Muster has something to say to the person, it answers with a separate `answerEvent` call, made before it
acknowledges the event: before it answers a push with `204`, or polls with the next cursor. Muster makes the call within
a few seconds of receiving the event, or not at all. A press that works is not answered; the edited Root message shows
its result. A refusal, a failure, a press from an account without an Account link and a press on a test message are
answered.

```http
POST /v1/answers HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: <key>
Content-Type: application/json
```

```json
{ "event_id": "ev-1001", "text": "Done: Acknowledged #42" }
```

```json
{ "shown_as": "ephemeral", "replayed": false }
```

The bridge shows `text` to the person who caused the event `event_id`, as plain text of at most 500 characters, and
answers where:

A `press`
:   Privately (`ephemeral` or `popup`) when the messenger allows it, with `private_answers`, and the press is recent
    enough; otherwise in the Thread of the message (`thread`).

A `thread_message`
:   In that Thread (`thread`), never as a pop-up.

An `account_link`
:   In the direct chat it came from (`direct`).

A `notification_acknowledged`
:   In the call, or in the reply to the message of the notification (`notification`); see [Answering during a
    call](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#answering-during-a-call).

An event that the bridge no longer knows, or can no longer answer anywhere, is `gone`.

```mermaid
sequenceDiagram
  autonumber
  actor P as Person
  participant X as Messenger
  participant B as Bridge
  participant M as Muster

  P->>X: presses a button
  X->>B: callback with the button's data
  B->>X: confirms the press at once, within 3 seconds
  B->>B: queues a press event
  alt Poll mode
    M->>B: GET /v1/events with the cursor
    B-->>M: the events and next_cursor
  else Push mode
    B->>M: POST the signed event to the callback address
  end
  M->>M: verifies the button's data and runs the Command
  opt Muster has something to say
    M->>B: POST /v1/answers with event_id and text
    B->>X: shows the text to the person
    X-->>P: privately (ephemeral or pop-up), or in the Thread
    B-->>M: 200 with shown_as
  end
  alt Poll mode
    M->>B: the next GET /v1/events with next_cursor
  else Push mode
    M-->>B: 204
  end
  Note over M: A press that works is not answered, the edited Root message shows the result
```

Muster ignores, without answering, a press or a Thread message about a message that it did not post through that
Connection. It drops a press or a Text command whose `occurred_at` is more than an hour old.

## Error classes

Errors are RFC 9457 problems (`application/problem+json`) with a `class` member that **the bridge chooses**, because
only the bridge knows what its messenger's codes mean. Muster acts on the class:

`transient`
:   A temporary failure: the messenger is down, a timeout.

    Muster retries with exponential backoff; repeated failures make the Destination Broken.

`rate_limited`
:   The messenger or the bridge throttles; send `Retry-After` in seconds.

    Muster waits exactly that long, for the channel, or for every channel of the bot when `scope` is `bot`; not counted
    as a failure; a wait longer than 15 minutes (`bridge.retry_after_max`), or none given, is treated as `transient`.

`gone`
:   The message no longer exists: deleted, or its Thread is gone.

    Muster publishes the Alert Group again once; with `reason` `edit_window_closed`, treats the message as past its edit
    window.

`forbidden`
:   The channel is missing, the bot was removed from it or lacks a right, the bot was blocked.

    Muster marks the Destination Broken until a check succeeds.

`invalid`
:   The request cannot succeed as sent: too long, malformed, an unknown id.

    Muster ends that delivery as Not delivered, without retrying.

The problem members are `title`, `status`, an optional `detail`, the `class`, and for `rate_limited` a `scope` of
`channel` (the default) or `bot`. The `detail` is shown to the Admin as the reason, as untrusted text, so write it for a
person and never put a secret in it.

```json
{ "title": "The messenger is not available.", "status": 503, "class": "transient" }
```

```json
{ "title": "Too many requests", "status": 429, "class": "rate_limited", "scope": "channel" }
```

The `429` carries `Retry-After: 7`, for example.

```json
{ "title": "The message no longer exists.", "status": 404, "class": "gone" }
```

```json
{ "title": "The message is too long for this messenger.", "status": 400, "class": "invalid" }
```

**Who decides `gone`.** Only the bridge. Muster never treats a message as gone because of a status code, and a `404`
without the class `gone` is `invalid`. A bridge that means `gone` says so in `class`. Use it for a message, a Thread or
an event that no longer exists. Muster reacts by publishing the Alert Group again, once, so do not use it for anything
else.

**Why a missing channel is `forbidden`.** A channel that does not exist, or that the bot cannot see, is
**`forbidden`, never `gone`**. `gone` makes Muster post the message again, and that would fail again at once.
`forbidden` marks the Destination Broken with your `detail`, which the Admin reads ("The bot is not a member of this
channel."), and Muster probes it with `checkChannel` until the channel works again.

**An answer without a `class`.** Muster still classifies a problem without a `class`, or an answer that is not a
problem, by its status, so a plain framework error does no harm:

`401`, `403`
:   class: `forbidden`

`408`
:   class: `transient`

`429`, and `503` with `Retry-After`
:   class: `rate_limited`

Other `5xx`, timeouts and network errors
:   class: `transient`

`404`, `410`, a redirect and everything else
:   class: `invalid`

No status is ever read as `gone`. Muster also follows no redirects, and treats one as a configuration error.

**An example mapping.** Parley, a fictional messenger, answers its own error codes. The bridge for Parley maps them
like this, as the `classify` function above does:

`502`, a timeout, `unavailable`
:   class: `transient` · why: the messenger is down

`slow_down`, with `retry_in` seconds
:   class: `rate_limited` · why: send `Retry-After`; use `scope` `bot` if the limit holds for the whole account

`message_not_found`, `thread_removed`
:   class: `gone` · why: the message or its Thread is deleted

`edit_too_old`
:   class: `gone` with `reason` `edit_window_closed` · why: the message exists, but cannot be edited any more

`channel_not_found`, `not_a_member`, `bot_banned`, `no_permission`
:   class: `forbidden` · why: the channel is unusable until somebody fixes it

`text_too_long`, `bad_request`
:   class: `invalid` · why: this request cannot succeed

`user_blocked_bot` on a direct message
:   class: `forbidden` · why: the account cannot receive a message from the bot

### Edit windows

Some messengers let a bot edit a message only for a while. Declare how long in `limits.edit_max_age_seconds`. Muster
then stops editing a Root message once it is as old as that, less 60 seconds, measured from its publication on Muster's
clock, without sending a failing request. If the messenger refuses an edit earlier than declared, answer `gone` with
`reason` `edit_window_closed`:

```json
{
  "title": "The message can no longer be edited.",
  "status": 404,
  "class": "gone",
  "reason": "edit_window_closed"
}
```

This is not a deletion. Muster marks the Root message as past its window. When the status of the Alert Group changes
after that, Muster posts a new Root message, Quietly, to the same channel, and replies under the old Thread: "This
message is no longer updated. The current one: {link}", where the link is the new message's `url` when you returned one,
and the Alert Group page otherwise. Later Thread replies go under the new Root message. Any other change leaves the old
Root message as it is. The old message keeps working: a press on its buttons, and a Text command in its Thread, act on
the Alert Group as on the current one, so the bridge must keep reporting them.

```mermaid
sequenceDiagram
  autonumber
  actor P as Person
  participant M as Muster
  participant B as Bridge
  participant X as Messenger

  M->>B: PATCH /v1/messages/old_id after a change of status
  B->>X: edit the message
  X-->>B: refused, the message is too old
  B-->>M: 404 with class gone and reason edit_window_closed
  Note over M: marks the Root message as past its edit window
  M->>B: POST /v1/messages with the new state, Quiet, new Idempotency-Key
  B->>X: post the new Root message
  B-->>M: 201 with the new message_id and url
  M->>B: POST /v1/messages/old_id/thread-replies, a pointer to the new message
  B->>X: reply in the old Thread
  B-->>M: 201
  Note over M: later Thread replies go under the new Root message
  P->>X: presses a button of the old message
  X->>B: callback
  B->>M: press event with the old message_id
  M->>M: runs the Command on the Alert Group as for the current message
```

## Events

The bridge reports what people do in the messenger as events. Every event has a stable `id`, a `type` and
`occurred_at`; Muster handles each `id` of a Connection once. An `id` is up to 200 printable ASCII characters without
spaces, because it travels as the `webhook-id` header of a push. A bridge delivers every event at least once, so
Muster deduplicates.

`press`
:   needs: `buttons`

    A person pressed a button of a message of the bot, already confirmed to the messenger.

`thread_message`
:   needs: `thread_messages`

    A person, never the bot itself, wrote in the Thread of a message of the bot.

`account_link`
:   needs: always

    A person sent the bot an Account link token, or opened the `link_url_template` link.

`message_deleted`
:   needs: `deletion_events`

    A message of the bot was deleted in the messenger.

```json
{
  "id": "ev-1001",
  "type": "press",
  "occurred_at": "2026-10-18T14:05:12Z",
  "message_id": "m-77",
  "user": { "external_id": "u-alice", "display_name": "Alice Smith", "handle": "alice" },
  "data": "a1.k2.QmFzZTY0U2lnbmF0dXJlRXhhbXBsZQ"
}
```

```json
{
  "id": "ev-1002",
  "type": "thread_message",
  "occurred_at": "2026-10-18T14:07:40Z",
  "message_id": "m-77",
  "thread_ref": "t-77",
  "user": { "external_id": "u-alice", "display_name": "Alice Smith", "handle": "alice" },
  "text": "ack"
}
```

`message_id` of a `thread_message` is the message whose Thread it is in, as in the path of `replyInThread`, usually the
Root message, never the id of a reply. `text` is plain text of at most 4000 characters, with mentions of the bot
removed.

```json

  "id": "ev-1003",
  "type": "account_link",
  "occurred_at": "2026-10-18T14:09:03Z",
  "token": "0123456789abcdefghijklmnopqrstuvwxyzABCDEFG",
  "user": { "external_id": "u-alice", "display_name": "Alice Smith", "handle": "alice" }
}
```

```json
{

  "type": "message_deleted",
  "occurred_at": "2026-10-18T14:11:30Z",
  "message_id": "m-77"
```

### Polling

Offer `poll` in `event_delivery` and implement `pollEvents`. Muster, on the Leader, calls it in a loop:

```http
GET /v1/events?cursor=<next_cursor>&wait=25 HTTP/1.1
Authorization: Bearer <token>
```

```json
{
  "events": [
    {
      "id": "ev-1001",
      "type": "press",
      "occurred_at": "2026-10-18T14:05:12Z",
      "message_id": "m-77",
      "user": { "external_id": "u-alice", "display_name": "Alice Smith", "handle": "alice" },
      "data": "a1.k2.QmFzZTY0U2lnbmF0dXJlRXhhbXBsZQ"
    }
  ],
  "next_cursor": "c-5"
}
```

- Return the events after `cursor`, oldest first, at once when there are any. Without `cursor`, return all of them.
  When there are none, hold the request open until one arrives or until `wait` seconds have passed, and then return an
  empty list. `wait` is 0 to 60, 25 by default (`bridge.poll_wait` is the 25 that Muster sends). Muster waits for your answer up to `wait` plus 15 seconds.
- `next_cursor` is opaque to Muster. Muster handles the batch and sends the `next_cursor` with its next call; only
  then may you forget the events before that cursor. Keep events that Muster has not passed for at least 24 hours.
- A cursor that you do not know is `invalid`; Muster then polls again without one. Return only the events of the
  token's bot.
- Only one Muster replica polls a Connection at a time, but after a handover two calls may overlap. That is why events
  are deduplicated by `id`.

### Push

Offer `push` in `event_delivery`. The Admin chooses it on the Connection and enters a **push secret**. The bridge posts
each event, one per request, to the callback address that the Connection shows:

```text
<MUSTER_INGEST_URL>/api/v1/callbacks/bridge/<connection id>
```

The request is signed as [Standard Webhooks](https://www.standardwebhooks.com/) specifies:

`webhook-id`
:   The event's `id`, kept across retries.

`webhook-timestamp`
:   The Unix time of this attempt, in seconds.

`webhook-signature`
:   `v1,` followed by the base64 of HMAC-SHA256 over `<webhook-id>.<webhook-timestamp>.<body>`.

The push secret is `whsec_` followed by the base64 of at least 24 random bytes. The HMAC key is **the decoded bytes**:
strip the prefix `whsec_` and base64-decode the rest. The signed content is the three values joined with full stops,
followed by the exact body that you send. `webhook-signature` may hold several signatures separated by spaces, which is
how a secret is rotated. Muster refuses a `webhook-timestamp` more than 5 minutes away from its own clock, so keep your
clock right, and sign each attempt with the time of that attempt.

Generate a secret and enter it on both sides:

```sh
printf 'whsec_%s\n' "$(head -c 32 /dev/urandom | base64)"
```

Muster answers:

| Answer | Means | The bridge |
|---|---|---|
| `204` | Muster handled the event, now or before | forgets the event |
| `400` | the event can never be handled | drops it |
| `401` | the signature, the Connection or its mode is wrong | keeps the event, retries after fixing its configuration |
| anything else, a timeout | a temporary failure | retries with backoff for at least an hour, same `webhook-id` |

Muster answers `401` for a bad signature, an unknown Connection and a Connection in poll mode alike, so the endpoint
reveals nothing about which Connections exist.

**In the protocol the bridge signs and Muster verifies.** The snippets below show both sides: the signer is what your
bridge needs, and the verifier is what Muster checks, which is useful in your tests. Both were run against Muster's own
code.

```go
package pushsig

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/base64"
	"errors"
	"regexp"
	"strconv"
	"strings"
	"time"
)

// timestampPattern is what Muster accepts as webhook-timestamp: Unix seconds, digits only.
var timestampPattern = regexp.MustCompile(`^[0-9]{1,12}$`)

// key decodes a push secret: whsec_ and the standard base64 of the key.
func key(secret string) ([]byte, error) {
	encoded, ok := strings.CutPrefix(secret, "whsec_")
	if !ok {
		return nil, errors.New("the push secret does not start with whsec_")
	}
	k, err := base64.StdEncoding.DecodeString(encoded)
	if err != nil || len(k) == 0 {
		return nil, errors.New("the push secret is not whsec_ and base64")
	}
	return k, nil
}

// signature is v1, a comma and the base64 HMAC-SHA256 of "<id>.<timestamp>.<body>".
func signature(k []byte, id, timestamp string, body []byte) string {
	mac := hmac.New(sha256.New, k)
	mac.Write([]byte(id + "." + timestamp + "."))
	mac.Write(body)
	return "v1," + base64.StdEncoding.EncodeToString(mac.Sum(nil))
}

// Sign returns the value of webhook-timestamp and of webhook-signature for the event with this id, sent now.
// The bridge sets webhook-id to the id of the event, and retries the event with the same webhook-id, with a new
// timestamp and signature.
func Sign(secret, id string, now time.Time, body []byte) (timestamp, sig string, err error) {
	k, err := key(secret)
	if err != nil {
		return "", "", err
	}
	timestamp = strconv.FormatInt(now.Unix(), 10)
	return timestamp, signature(k, id, timestamp, body), nil
}

// Verify checks the three headers of a pushed event the way Muster does. The header may hold several
// signatures separated by spaces; one that matches is enough.
func Verify(secret, id, timestamp string, body []byte, header string, now time.Time) error {
	k, err := key(secret)
	if err != nil {
		return err
	}
	want := []byte(signature(k, id, timestamp, body))
	matched := false
	for _, part := range strings.Fields(header) {
		if hmac.Equal([]byte(part), want) {
			matched = true
		}
	}
	if !matched {
		return errors.New("no signature matches")
	}
	if !timestampPattern.MatchString(timestamp) {
		return errors.New("the timestamp is not Unix seconds")
	}
	sent, err := strconv.ParseInt(timestamp, 10, 64)
	if err != nil {
		return err
	}
	if d := now.Sub(time.Unix(sent, 0)); d > 5*time.Minute || d < -5*time.Minute {
		return errors.New("the timestamp is more than 5 minutes from the clock")
	}
	return nil
}
```

For a bridge in Python:

```python
import base64
import hashlib
import hmac
import re
import time


def _key(secret: str) -> bytes:
    """Decode a push secret: whsec_ and the standard base64 of the key."""
    if not secret.startswith("whsec_"):
        raise ValueError("the push secret does not start with whsec_")
    key = base64.b64decode(secret.removeprefix("whsec_"), validate=True)
    if not key:
        raise ValueError("the push secret is not whsec_ and base64")
    return key


def _signature(secret: str, msg_id: str, timestamp: str, body: bytes) -> str:
    mac = hmac.new(_key(secret), f"{msg_id}.{timestamp}.".encode() + body, hashlib.sha256)
    return "v1," + base64.b64encode(mac.digest()).decode()


def sign(secret: str, msg_id: str, body: bytes, now: float | None = None) -> tuple[str, str]:
    """Return the values of webhook-timestamp and webhook-signature."""
    timestamp = str(int(now if now is not None else time.time()))
    return timestamp, _signature(secret, msg_id, timestamp, body)


def verify(secret: str, msg_id: str, timestamp: str, body: bytes, header: str,
           now: float | None = None) -> bool:
    """Check the three headers of a pushed event the way Muster does."""
    if not re.fullmatch(r"[0-9]{1,12}", timestamp):
        return False
    want = _signature(secret, msg_id, timestamp, body).encode()
    matched = False
    for part in header.split():
        if hmac.compare_digest(part.encode(), want):
            matched = True
    drift = (now if now is not None else time.time()) - int(timestamp)
    return matched and abs(drift) <= 300
```

Verification compares in constant time, so that the time it takes tells nothing about the signature. It accepts a
header with several signatures when one of them matches, and refuses a timestamp more than 5 minutes from the clock.
Sign and send the exact bytes of the body: a re-serialized body has another signature.

### Account links

An **Account link** ties a Muster User to their account in the messenger. A press, a Text command or a Mention names a
person only through it, and it is started in the person's Muster profile, never from the messenger. Every bridge takes
a **token**; a bridge that can look people up and write to them also offers a **code**. See
[Link your messenger accounts](https://muster-io.github.io/muster/latest/messengers/account-links.md) for what the person sees.

- **By token.** The profile shows a token of 43 characters of base64url, valid for 10 minutes and for one use. The
  person sends it to the bot in a direct message, or opens your `link_url_template` link, which hands it to the bot. The
  bridge sends an `account_link` event. The token is the whole text of the direct message, trimmed and after an
  optional `/start `. Muster links the sender's account and answers with `answerEvent`, which you show in the direct
  chat the event came from: "Linked to Muster user …".
- **By code.** It is offered only with `direct_messages` and `bot_can_start`, and a `user_lookup` other than `none`. The
  person enters their handle, of the kind `user_lookup` declares, in their Muster profile. Muster calls `findUsers`,
  then `sendDirectMessage` with the code and a warning, and the person types the code into the profile. The bot sends
  no confirmation.

```mermaid
sequenceDiagram
  autonumber
  actor P as Person
  participant W as Muster profile
  participant M as Muster
  participant B as Bridge
  participant X as Messenger

  alt By token
    P->>W: selects Link and chooses the Connection
    W-->>P: a token of 43 characters, and the link from link_url_template
    P->>X: sends the token to the bot in a direct message
    X->>B: the direct message
    B->>B: the text is a token, so it queues an account_link event
    B-->>M: the event, by poll or push
    M->>M: links the sender's account to the User
    M->>B: POST /v1/answers with event_id, Linked to Muster user
    B->>X: shows the answer in the direct chat
  else By code
    P->>W: enters the handle, such as a login
    W->>M: asks for a code
    M->>B: GET /v1/users with handle
    B-->>M: items with the account
    M->>B: POST /v1/direct-messages with the code and a warning
    B->>X: sends the direct message
    X-->>P: the code
    P->>W: types the code
    W->>M: confirms, and the link is made
  end
```

## A gateway bridge

A bridge in the role `gateway` is a **Notification gateway**: it reaches a person outside a messenger, by phone call or
SMS for example, through a provider of your choice. Muster ships none. This section is for the authors of one; to
connect a gateway that already exists, read [Notification gateways](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md). A gateway is the
same kind of service as a messenger bridge, with the same token, the same `info`, the same
[`Idempotency-Key`](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#idempotency-key) and the same events, and fewer operations:

```mermaid
sequenceDiagram
  autonumber
  actor P as Person
  participant R as Provider
  participant G as Gateway bridge
  participant M as Muster

  M->>G: POST /v1/notifications, with the contact, the text and the action
  G->>R: places the call, or sends the SMS
  G-->>M: 201 with notification_id
  R-->>P: rings and reads the text out
  P->>R: presses 1
  R->>G: the provider's callback
  G->>G: queues notification_acknowledged with the action's data
  G->>M: push mode: POST the signed event to the callback address
  M->>M: verifies the data and acknowledges as the person
  M->>G: POST /v1/answers with event_id and text
  G->>R: reads the answer out
  R-->>P: "Acknowledged: #42"
  G-->>M: 200 with shown_as
  M-->>G: 204 to the push
```

The libraries do the protocol's part, as for a messenger bridge: validate every request, keep the idempotency of
`sendNotification`, keep the action data of each notification for 24 hours and queue, poll and push the events. You write
the calls to your provider and the callback of your provider that says the person pressed.

!!! note "Library versions"
    The gateway role is in the `master` branch of both libraries, after `0.1.1`. Until their next release carries it,
    take it from there: `go get github.com/muster-io/muster-bridge-go@master`, or install `muster-bridge` from the
    repository of `muster-bridge-python`.

### The role in `info`

A bridge declares its role in `info`, with `roles`. A bridge without `roles` is a messenger. A gateway that is not also a
messenger still sends every required member of `info`, with the members that are a messenger's empty:

```json
{
  "protocol_version": "1",
  "bridge": { "name": "parley-calls", "version": "0.1.0" },
  "roles": ["gateway"],
  "messenger": { "name": "Parley Voice" },
  "capabilities": {},
  "limits": { "max_body_length": 1000, "edit_max_age_seconds": null },
  "user_lookup": "none",
  "event_delivery": ["poll", "push"]
}
```

`messenger.name` names your provider; it is shown on the Connection. `capabilities` is empty, `user_lookup` is `none`
and there is no `link_url_template`. A bridge of both roles has `"roles": ["messenger", "gateway"]` and declares
everything of a messenger too. Muster reads the roles when it checks the Connection: a bridge whose only role is
`gateway` cannot be a Destination ([Roles](https://muster-io.github.io/muster/latest/messengers/bridge.md#roles)), and Muster calls `sendNotification` only on a bridge that
declares `gateway`. A bridge that does not declare it answers `invalid` to the call.

In Go, set `Config.Roles` to `[]bridge.Role{bridge.RoleGateway}` (or both roles), give the implementation as
`Config.Gateway`, and pass a nil `Messenger` to `bridge.New`. `bridge.New` refuses a role without its implementation and
an implementation without its role, and a gateway-only `Config` that declares a messenger's capabilities. In Python, set
`roles=["gateway"]` and `gateway=` in `Config`, and give `BridgeApp(config)` no `Messenger`; `BridgeApp` raises
`ConfigError` for what does not fit.

### `sendNotification`

Muster reaches a person through your gateway with one request:

```http
POST /v1/notifications HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: calls/<id of the call>
Content-Type: application/json
```

```json
{
  "contact": "+10000000001",
  "text": "Muster: 1 Alert Group needs you. #42 DiskFull, critical. Press 1 to acknowledge.",
  "language": "en",
  "action": { "data": "a1.k2.QmFzZTY0U2lnbmF0dXJlRXhhbXBsZQ", "label": "Press 1 to acknowledge" }
}
```

```json
{ "notification_id": "n-1001", "replayed": false }
```

`contact`
:   Where the person is reached, as they entered it in Muster and as your provider understands it, such as a phone
    number: 1 to 200 characters. Muster does not check it, so you do: a contact your provider refuses for good is
    `invalid`.

`text`
:   Plain text of 1 to 1,000 characters, which you read out or send, as your provider can.

`language`
:   `en` or `ru`: the language of the person, which `text` and `action.label` are in. Pick the voice of a call by it.

`action`
:   How the person acknowledges: `label` tells them ("Press 1 to acknowledge"), and `data` is opaque, up to 64 printable
    ASCII characters, signed by Muster. Return it unchanged in `notification_acknowledged`. Without `action` there is
    nothing to acknowledge, as for the code that confirms a contact.

The answer's `notification_id` is yours, 1 to 512 characters, and names the notification in `notification_acknowledged`.
Make it unique per bot, as the id your provider gives the call, for example.

**`Idempotency-Key`.** Muster sends the same key, `calls/<id of the call>`, on every attempt of a call. Answer a repeated
key with the first result and `replayed: true` and place no second call, or the person's phone rings twice after a
restart of a Muster replica. The libraries do this for you. A failed request stores nothing, so its retry is a new
attempt ([`Idempotency-Key`](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#idempotency-key)).

The text and the contact are personal data: never log them.

### Answering during a call

When the person acknowledges, you report `notification_acknowledged`, Muster acknowledges the Alert Groups as them, and
Muster answers with `answerEvent` — "Acknowledged: #42", "Already taken by Alice", "Already resolved" — which you show
to the person: in a call, you read it out. The answer must come while the person is still on the line, and that needs
the **push** mode: Muster answers a pushed event **before** it answers the push, with an `answerEvent` request within a
few seconds of receiving the event. Keep the call open for a short wait after the press, read out what `answerEvent`
brings, and then end the call. In the poll mode the time of the answer depends on Muster's next read of the event, so
it may come after the person has hung up; use the push mode for calls.

```http
POST /v1/answers HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: <key>
Content-Type: application/json
```

```json
{ "event_id": "ev-2001", "text": "Acknowledged: #42" }
```

```json
{ "shown_as": "notification", "replayed": false }
```

`shown_as` is `notification` for the answer in a call, or in the reply to the message of a notification. Muster sends
`answerEvent` within a few seconds of receiving the event, or not at all. An event that you no longer know, or can no longer
answer anywhere, is `gone`. The answer is in the language of the person's profile.

### `notification_acknowledged`

The event of a person who acknowledged a notification that carried an `action`, only from a bridge in the role `gateway`
and only for a `sendNotification` of Muster:

```json
{
  "id": "ev-2001",
  "type": "notification_acknowledged",
  "occurred_at": "2026-10-18T02:14:40Z",
  "notification_id": "n-1001",
  "data": "a1.k2.QmFzZTY0U2lnbmF0dXJlRXhhbXBsZQ"
}
```

`notification_id` is the one you answered, `data` is the notification's `action.data`, unchanged. Muster verifies the
data, which names the call and its Connection, and acknowledges each Alert Group of the call as the person the call was
for, with the Transport `gateway`, only while nobody owns it; see [Acknowledging from a
call](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#acknowledging-from-a-call). Report an acknowledgement as soon as it happens: Muster drops
one that comes more than an hour after it happened (`bridge.event_max_age`). Muster handles each event `id` once, so
report it with the same `id` if you are not sure it arrived. The events are delivered as for any bridge, by
[polling or push](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#events).

### The error classes of calls

Muster acts on the class of the answer to `sendNotification` as for any bridge ([Error classes](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#error-classes)):

`invalid`
:   The call cannot succeed as sent: a contact the provider refuses for good, a text it cannot take. That call ends
    Not delivered, without a retry, and the gateway stays healthy.

`forbidden`
:   Your provider refuses your credentials, or its account is blocked. Muster treats it, like a `401` or `403`, as a Fatal
    error and the gateway becomes **Broken**.

`transient`
:   A temporary failure of the provider. Muster retries the call, with the same `Idempotency-Key`, within its retry
    budget (`delivery.transient_budget`). When the budget runs out the call ends Not delivered, and the gateway becomes
    Broken.

`rate_limited`
:   The provider throttles: answer with `Retry-After`. Muster waits exactly that long, and the waits count toward the
    time of the retry budget. A wait longer than 15 minutes (`bridge.retry_after_max`), or none given, is treated as
    `transient`.

A gateway is **Broken** after a Fatal error or an exhausted retry budget; no call is sent while it is Broken, and the
calls that came due meanwhile are lost for good. Muster reads `info` every 5 minutes and ends the state at the first
success. A passing `info` does not prove that calls go through, since a bridge answers it also while its provider
refuses its credentials: run [`muster bridge check`](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#muster-bridge-check) with `--contact` before you trust a
recovery. See [Broken gateways](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#broken-gateways) and its
[runbook](https://muster-io.github.io/muster/latest/operations/runbooks/MusterNotificationGatewayBroken.md).

### With the Go library

Implement `bridge.Gateway`. It has two methods, each given the name of the bot whose token Muster sent:
`SendNotification` and `Answer`. The sketch is for Parley Voice, a fictional provider; its client `parleyVoice` stands
for whatever library your provider has.

```go
// parleyGateway is the bridge's calls to the fictional provider Parley Voice.
type parleyGateway struct{ api *parleyVoice }

func (g *parleyGateway) SendNotification(ctx context.Context, bot string, in bridge.NotificationInput) (
	bridge.NotificationSent, error) {
	callID, err := g.api.Call(ctx, in.Contact, in.Text, string(in.Language), in.Action != nil)
	switch {
	case errors.Is(err, errBadNumber):
		return bridge.NotificationSent{}, bridge.InvalidError("The number cannot be called.")
	case errors.Is(err, errCredentials):
		return bridge.NotificationSent{}, bridge.ForbiddenError("Parley Voice refused the credentials of the bridge.")
	case err != nil:
		return bridge.NotificationSent{}, err // anything else is answered transient
	}
	return bridge.NotificationSent{NotificationId: callID}, nil
}

// Answer reads out what Muster answers the person who pressed 1, while they are still on the line.
func (g *parleyGateway) Answer(ctx context.Context, bot string, ev bridge.ReportedEvent, text string) (
	bridge.AnswerShownShownAs, error) {
	if err := g.api.Say(ctx, ev.NotificationID, text); err != nil {
		return "", bridge.GoneError("The call has ended.")
	}
	return bridge.AnswerShownShownAsNotification, nil
}
```

A method returns the protocol's answer, or an error: an `*bridge.Error` answers its class, and any other error is answered
`transient` with a generic detail. The library validates every request before it calls your method and every answer
before it sends it, keeps the `Idempotency-Key` and refuses a text over 1,000 characters and action data over 64 bytes
as `invalid` before your code runs. `SendNotification` returns the `NotificationId`, 1 to 512 characters and unique per
bot; the library keeps the action of the first notification of an id for 24 hours in the `Store`.

Build the bridge with a nil `Messenger`, push its events to Muster and serve it:

```go
b, err := bridge.New(bridge.Config{
	Name:          "parley-calls",
	Version:       "0.1.0",
	MessengerName: "Parley Voice",
	Roles:         []bridge.Role{bridge.RoleGateway},
	Gateway:       &parleyGateway{api: voice},
	Bots: []bridge.Bot{{
		Name:  "main",
		Token: token,
		Push:  &bridge.PushTarget{URL: callbackURL, Secret: pushSecret},
	}},
	Limits: bridge.Limits{MaxBodyLength: 1000},
}, nil)
if err != nil {
	log.Fatal(err)
}
mux := http.NewServeMux()
mux.Handle("/v1/", b.Handler())
// ... serve mux, and on shutdown call b.Close(ctx), which stops the pushers
```

When your provider's callback says the person pressed 1, report it:

```go
switch err := b.Acknowledge(ctx, "main", callID); {
case errors.Is(err, bridge.ErrNoAction), errors.Is(err, bridge.ErrUnknownNotification):
	// a notification without an action, or one the bridge did not send or no longer keeps
case err != nil:
	// report again: the event was not queued
}
```

`Acknowledge` queues `notification_acknowledged` with the data of the notification's action, for polling and push, and
returns once it is queued. Acknowledging a notification twice queues one event. Then `Gateway.Answer` is called with the
event, in `ev.NotificationID`, when Muster answers.

`examples/gateway` of `muster-io/muster-bridge-go` is a whole gateway in one file, with a provider in memory that logs
each notification, and the page `/demo/acknowledge` that stands in for the person pressing 1:

```sh
printf example-token > /tmp/bt
go run ./examples/gateway -token-file /tmp/bt
```

It listens on `127.0.0.1:18095`. Check it with your contact, and acknowledge from its page when the check asks:

```sh
docker run --rm --network host -v /tmp/bt:/token:ro ghcr.io/muster-io/muster:edge bridge check \
  http://127.0.0.1:18095 --token-file /token --contact +10000000001
```

### With the Python library

Implement the protocol `Gateway`, two coroutines: `send_notification(bot, notification)` and `answer(bot, event,
text)`. The sketch is for the same provider; `ParleyVoice` stands for its asynchronous client.

```python
from muster_bridge import (
    AcknowledgedNotification,
    Bot,
    BridgeApp,
    Config,
    Forbidden,
    Invalid,
    Limits,
    NotificationInput,
    NotificationSent,
    PushTarget,
    UnknownNotificationError,
)


class ParleyGateway:
    """The bridge's calls to the fictional provider Parley Voice."""

    def __init__(self, api: ParleyVoice) -> None:
        self.api = api

    async def send_notification(self, bot: str, notification: NotificationInput) -> NotificationSent:
        try:
            call_id = await self.api.call(
                notification.contact, notification.text, notification.language.value, notification.action is not None
            )
        except BadNumber:
            raise Invalid("The number cannot be called.") from None
        except BadCredentials:
            raise Forbidden("Parley Voice refused the credentials of the bridge.") from None
        return NotificationSent(notification_id=call_id, replayed=False)

    async def answer(self, bot: str, event: AcknowledgedNotification, text: str) -> None:
        """Read out what Muster answers the person who pressed 1, while they are still on the line."""
        await self.api.say(event.notification_id, text)
```

A method raises a `BridgeError` subclass to answer its class, and any other exception is answered `transient` with a
generic detail. The library validates every request and answer, keeps the `Idempotency-Key`, and refuses a text over
1,000 characters and action data over 64 bytes as `invalid` before your code runs. `notification_id` is 1 to 512
characters and unique per bot. The library keeps the action of each notification for 24 hours in the `Store`:
`MemoryStore`, the default, does; a `Store` of your own also implements `NotificationStore`, with `save_notification`
and `find_notification`, which `Config` checks when the role is declared.

```python
config = Config(
    name="parley-calls",
    version="0.1.0",
    messenger_name="Parley Voice",
    bots=[Bot(name="main", token=token, push=PushTarget(url=callback_url, secret=push_secret))],
    limits=Limits(max_body_length=1000, edit_max_age_seconds=None),
    roles=["gateway"],  # ["messenger", "gateway"] for a bridge of both, with a Messenger as before
    gateway=ParleyGateway(voice),
)
bridge = BridgeApp(config)
```

`BridgeApp(config, messenger=None)` is an ASGI application: serve it with uvicorn, or mount it under a path of a
Starlette application, with `lifespan=bridge.lifespan`. When your provider's callback says the person pressed 1,
report it:

```python
try:
    await bridge.acknowledge("main", call_id, chat=call_id)
except UnknownNotificationError:
    ...  # a notification the bridge did not send, no longer keeps, or that carried no action
```

`acknowledge` queues `notification_acknowledged` with the `action.data` of the notification, delivered by polling and by
push, and returns once it is queued. `chat`, such as a call id, comes back in `AcknowledgedNotification.chat` when Muster's
answer reaches `Gateway.answer`, and is never sent to Muster; `update_id` makes an update reported twice queue one event.
`UnknownNotificationError` is a `ValueError`; `NotOfferedError` is raised without the role `gateway`.

`examples/gateway_bridge.py` of `muster-io/muster-bridge-python` is a whole gateway in one file, which prints each
notification and acknowledges one from `POST /demo/acknowledge` with `{"notification_id": "n1"}`:

```sh
printf example-token > /tmp/bt
python examples/gateway_bridge.py --token-file /tmp/bt
```

### A gateway without a library

A gateway in another language implements, with the conventions of [The protocol without a library](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#the-protocol-without-a-library):

1. [`getInfo`](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#getinfo) with `roles` containing `gateway`, as [above](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#the-role-in-info);
2. `sendNotification`, `POST /v1/notifications`, with the `Idempotency-Key` semantics of [`Idempotency-Key`](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#idempotency-key),
   answering `201` with `notification_id` and `replayed`;
3. `answerEvent`, `POST /v1/answers`, which shows the answer to the person who caused the event;
4. events in at least one delivery mode, with `notification_acknowledged` in the [events](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#events) of poll and push, and
   the push mode if the answer must reach a person still on the line;
5. the error classes of [Error classes](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#error-classes).

Check the result with [`muster bridge check`](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#muster-bridge-check) and its `--contact` flag: it runs the steps
`notification` and `notification_acknowledged`, and skips the steps of a messenger for a bridge whose only role is
`gateway`.

## Test your bridge

### `muster bridge check`

`muster bridge check <url>` runs the protocol against a bridge, without a Muster database, master key or configuration.
It writes no file and stores nothing, and never changes the bridge's configuration. It does post, edit and reply in the
channel of `--channel`, delete its own message there when the bridge offers deletion, and write to the person of
`--handle`.

```sh
muster bridge check http://127.0.0.1:18095 --token-file ./token --channel alerts \
  --forbidden-channel nobot --handle alice --no-interactive
```

`--token-file <file>`
:   The bridge's token, alone in the file (required).

`--channel <id>`
:   A channel the bot can post to; a bridge in the role `messenger` needs it, and without it the check stops after
    `info` with exit status `2`. A bridge whose only role is `gateway` needs none.

`--forbidden-channel <id>`
:   A channel the bot cannot use, which must answer `forbidden`; without it the step `forbidden_channel` is skipped.

`--handle <handle>`
:   A person to look up and write to; without it `user_lookup` and `direct_message` are skipped.

`--contact <contact>`
:   Where a bridge in the role `gateway` reaches you, such as your phone number; without it `notification` and
    `notification_acknowledged` are skipped.

`--push-listen <addr>`
:   Where the push listener listens, `127.0.0.1:0` by default.

`--push-url <url>`
:   Where the bridge reaches the push listener, the listener's own address by default.

`--push-secret-file <file>`
:   The push secret, `whsec_` and the base64 of at least 24 bytes, instead of a generated one.

`--no-interactive`
:   Skip `press`, `push` and `notification_acknowledged`, which need a person.

Flags may come before or after the URL. The check prints one line per step as it ends: `PASS <step>`,
`FAIL <step>: <reason>` or `SKIP <step>: <why>`. The steps run in this order: `info`, `channel_check`, `post`,
`replayed_key`, `buttons`, `edit`, `thread_reply`, `thread_ref`, `forbidden_channel`, `user_lookup`, `direct_message`,
`delete`, `poll`, `press`, `push`, `answer`, `notification` and `notification_acknowledged`. A failed `info` ends the
run; after it, `ROLES <role>…` names the roles the bridge declares, and the steps of a role it lacks are skipped: from
`channel_check` to `delete`, `press` and `push` are the role `messenger`'s, `notification` and
`notification_acknowledged` the role `gateway`'s. `replayed_key` posts the same request again with its
`Idempotency-Key`, which must return the same `message_id` with `replayed`. `notification` sends a test notification to
`--contact`, with 64 bytes of action data, and the same request again, which must answer `replayed`;
`notification_acknowledged` waits for you to acknowledge it and answers the event.

```text
PASS info
ROLES messenger
PASS channel_check
PASS post
PASS replayed_key
PASS buttons
PASS edit
PASS thread_reply
PASS thread_ref
PASS forbidden_channel
PASS user_lookup
PASS direct_message
PASS delete
PASS poll
SKIP press: --no-interactive
SKIP push: --no-interactive
PASS answer
SKIP notification: the bridge is not in the role gateway
SKIP notification_acknowledged: the bridge is not in the role gateway
```

It exits `0` when no step failed, `1` when one did, and `2` on a usage error. A step for an optional feature that the
bridge does not declare is skipped.

Without `--no-interactive`, the check also needs a person. For a bridge that offers push, it opens a push listener and
prints `PUSH <url> <secret>` (or `PUSH <url>` with `--push-secret-file`): point your bridge's push target there with
that secret. Before it waits, up to five minutes, for a press, it prints `WAIT press: …, message_id <id>`; press a
button of that message in your messenger, or play the person in a script.

The check runs from the `muster` binary, or from Muster's image:

```sh
docker run --rm --network host -v "$PWD/token:/token:ro" ghcr.io/muster-io/muster:latest bridge check \
  http://127.0.0.1:18095 --token-file /token --channel alerts --forbidden-channel nobot --handle alice \
  --no-interactive
```

(`--network host` gives the container your loopback on Linux only.)

## Run your bridge

- **The token and the push secret.** One token is one bot. Keep both in a secret store or a file with restricted
  access, not in the image or on a command line. To change the push secret without a refused push, sign with both the
  old and the new secret while it changes in Muster: `webhook-signature` may hold both signatures, separated by a
  space, and Muster accepts the header when one of them matches. The Go library's `PushTarget` holds one secret, so it
  signs with one: between the change in Muster and `b.SetPush` with the new secret, Muster answers its pushes `401`.
  The library keeps those events and retries them, for at least an hour and at once after `b.SetPush`, so none is lost
  when the bridge gets the new secret within that hour.
- **Logs.** Never log a token, a push secret, an Account link token, or an `Authorization` header. The Account link
  token is a credential until it is used. A `detail` that you answer is shown to the Admin, so keep secrets out of it
  too.
- **Who calls you.** Muster sends `User-Agent: Muster/<version>` on every request, only to the base URL saved on the
  Connection, and follows no redirects. Serve the bridge over HTTPS when it is reachable from beyond a trusted
  network. A bridge that cannot reach Muster should use polling.
- **Timeouts.** Answer quickly, and return an error class rather than hang: Muster waits only so long for an answer, and
  treats a timeout as `transient`. A `pollEvents` call may be held for up to 60 seconds, so do not put a shorter
  timeout in front of it.
- **Monitoring.** Muster monitors your bridge through the health of its Destinations. A Destination that the bridge
  refuses with `forbidden`, or that keeps failing for the whole Transient budget (10 attempts within 30 minutes),
  becomes **Broken**, with your `detail` as the reason. A bridge that asks Muster to wait does not make a Destination
  Broken unless it asks for more than 15 minutes. While a Destination is Broken, Muster probes it every 5 minutes, with
  `checkChannel` when nothing waits, and the first success ends the state. The Internal alert `MusterDestinationBroken`
  tells the operators; its runbook is [MusterDestinationBroken](https://muster-io.github.io/muster/latest/operations/runbooks/MusterDestinationBroken.md). A
  Bridge Connection whose bridge cannot be reached does not become Broken itself: its Destinations do.

# Notification gateways

A **Notification gateway** reaches people outside messengers — by phone call or SMS, for example — through a provider
of its own. It is a bridge in the role `gateway`: a service that speaks the [Bridge protocol](https://muster-io.github.io/muster/latest/reference/bridge-protocol.md)
with Muster and calls or texts people through your provider. Muster ships no gateway and never calls or texts anyone
by itself: you run a gateway written for your provider, and Muster sends it the person's contact and a plain text.

A gateway does not depend on a messenger, so it still reaches a person whose messenger is down or silent at night. Read
[At night](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#at-night) before you rely on a messenger alone for that, and
[How an alert reaches people](https://muster-io.github.io/muster/latest/concepts/how-an-alert-reaches-people.md) to see where a call fits among the Pages of
an Alert.

The page follows the way a gateway is used: [connect it](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#connect-a-notification-gateway), [let people confirm a
contact](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#contact-for-calls-and-sms), then see [how calls are made](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#how-calls-are-made), [how a person acknowledges
from a call](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#acknowledging-from-a-call) and [what to do when a gateway is Broken](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#broken-gateways).

In the examples, `MUSTER_PUBLIC_URL` is `https://muster.example.org`, and the contacts are numbers such as
`+10000000001`, which reach nobody.

## Connect a Notification gateway

A Notification gateway is a [Bridge Connection](https://muster-io.github.io/muster/latest/messengers/bridge.md) whose bridge declares the role `gateway` in its `info`:

1. Run the gateway bridge. To write one for your provider, read [Write a bridge](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md): a gateway
   implements `info`, `sendNotification`, `answerEvent` and events in at least one delivery mode.
2. Create a Bridge Connection for it, with its base URL and the token of its bot, as
   [Connect a messenger through a bridge](https://muster-io.github.io/muster/latest/messengers/bridge.md#create-the-connection) describes.
3. Check the Connection. The check reads the roles from the bridge's `info` and shows **Notification gateway**; the
   read of the Connection has `"roles": ["gateway"]`, and `GET /api/v1/connections?role=gateway` lists it.

    ![The Notification gateway card of the Connection page of Phone calls: Roles: Notification gateway, and Healthy](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/notification-gateways/01-gateway-connection.png){ .screenshot }

A Bridge Connection whose only role is `gateway` cannot be a Destination and is not offered for Account links
([Roles](https://muster-io.github.io/muster/latest/messengers/bridge.md#roles)). A bridge may have both roles, `messenger` and `gateway`: its Connection is then both a
messenger, whose channels are Destinations, and a gateway, and the Connection page shows both roles. A bridge that
once had the role `messenger` and now declares only `gateway` leaves its Destinations without messages, and the
Connection page warns about them: remove them or change the bridge.

Choose the event delivery mode with the answer to a call in mind. A person who acknowledges in a call is on the line
while Muster answers, and only a gateway that **pushes** its events, with the Connection's push secret, makes Muster
answer before it answers the push, so that the answer is read out in the same call. A gateway that is polled still
works, but the time of the answer depends on Muster's next read of the event, so it may come after the person has hung
up; see [Answering during a call](https://muster-io.github.io/muster/latest/messengers/write-a-bridge.md#answering-during-a-call).

`muster dev` runs the demo Connection "Example Gateway" on its fake bridge, whose `info` declares only the role
`gateway`; the fake bridge lists what it was sent at `/_fake/notifications`.

## Contact for calls and SMS

A gateway calls or texts a person at their **contact**: a phone number or another address the gateway understands, as
text. Muster does not check phone numbers. Each person has at most one confirmed contact per Notification gateway, and
only a confirmed contact is called.

### Add and confirm a contact

A person adds their own contact from their signed-in web session, and confirms it with a code that the gateway
delivers. In the web UI this is **Profile**, the section **Contact for calls and SMS**, with a block for each
Notification gateway: type the number in **Phone**, select **Send code**, type the code in **Code** and select
**Confirm**. The section then shows the contact as "+10000000001 · calls and SMS · confirmed", with **Remove**, and
the note that a call acknowledges an Alert Group only while nobody has it. **Another number** starts a change, and
**Send a new code** asks for another code. Without a gateway the section says "Unavailable: a Notification gateway is
needed (a bridge for calls and SMS)" and links here; a person who may create Connections sees **Connect a bridge** beside it.

![The Contact for calls and SMS section of a profile: the Notification gateway Phone calls, +10000000001 · calls and SMS · confirmed, with Another number and Remove](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/notification-gateways/02-confirmed-contact.png){ .screenshot }

The same steps through the API:

1. Add the contact for the gateway (`createMyGatewayContact`, `POST /api/v1/me/gateway-contacts`, with
   `connection_id` and `contact`). The contact is trimmed and holds 1 to 200 characters. Muster stores it
   unconfirmed and sends a code through the gateway with `sendNotification`, without action data, in the language of
   the person's profile: "Your Muster code: 123456. It is valid for 10 minutes. Do not share it."
2. Type the code back, in the same web session (`confirmMyGatewayContact`, `POST
   /api/v1/me/gateway-contacts/{id}/confirmation`, with `code`). The contact is confirmed.
3. To get another code, ask for one (`sendMyGatewayContactCode`, `POST /api/v1/me/gateway-contacts/{id}/code`); once
   the gateway accepted it, it voids the earlier codes of the contact. A code the gateway did not take leaves the
   earlier one valid.

The code (`gateway.contact_code`):

Length
:   6 digits.

Validity
:   10 minutes after it was asked for.

Attempts
:   At most 5. A wrong code answers `422` `contact_code_invalid` with `attempts_remaining`; after the fifth wrong code,
    once the code expired or was used, and once a newer code was sent, the code is void.

Session
:   A code is checked only in the web session that asked for it. The right code typed in another session is refused
    and counts as an attempt; a session that ends voids its codes.

Code requests — adding a contact and asking for a new code — are limited (`gateway.contact_code_requests`):

Per person
:   5 within an hour.

Per person and contact
:   3 within an hour from one person for one contact, as typed and trimmed.

A request beyond them answers `429` `contact_code_requests_exceeded` with `Retry-After`; a request whose code the
gateway could not deliver still counts. What others ask for never refuses a person's request: a contact receives at
most 10 codes within an hour whoever asks, and a request beyond them is answered as if its code were sent, but nothing
is sent, so that the answer never tells of other people's requests. The code is sent on the interactive path, since
the person waits for it: when no rate-limit token of the gateway is free within `delivery.interactive_budget`, the
answer is `503` with `Retry-After`, and when the gateway refuses the notification, `502` `gateway_refused` with its
`gateway_class`. The contact stays, unconfirmed, and a new code can be asked for.

### Change a contact

Add the new contact for the same gateway. Until it is confirmed, the confirmed contact stays the one called, and both
are listed, the new one naming the confirmed one in `replaces`; confirming the new contact replaces the old one, so
that changing a number never leaves a person unreachable. Adding another contact before the new one is confirmed
replaces the unconfirmed one. A person removes a contact with `deleteMyGatewayContact`.

### Admins

An Admin sees the contacts of any User (`listUserGatewayContacts`, `GET /api/v1/users/{id}/gateway-contacts`) and
removes one (`deleteUserGatewayContact`), but never sets one: `createUserGatewayContact` always answers `403`, "Only the
person sets their contact, from their own web session.", so that nobody can tie a contact to another person's User.
The operations that change a person's own contacts take the web session only; an API token, an Admin's included, gets
`403` `session_required`.

### Privacy

A contact is personal data, not a secret: the person, Admins and the gateway read it. Muster does not log it, and the
[Request log](https://muster-io.github.io/muster/latest/operations/request-log.md#masking) shows the contact and the text of every request to
`sendNotification` as `[redacted]`, the code included. Adding, confirming and removing a contact are recorded in the
Audit log. Deleting a User erases their contacts and codes, and the Audit log then shows their earlier contacts as
`[erased]`.

## How calls are made

A call is one notification through a gateway to one person, about one or more Alert Groups. Escalation chains make
calls with their steps "Call through a Notification gateway", and Notification rules with their call actions
([Calls through a Notification gateway](https://muster-io.github.io/muster/latest/concepts/escalation-chains.md#calls-through-a-notification-gateway));
`muster dev` also queues one by hand with `POST /_dev/gateway-calls` on its internal listener.

- The first call to a person through a gateway goes at once. The Pages to the same person through the same gateway
  that come due while a call to them waits, is being retried, or within 60 seconds (`gateway.combine_window`) after
  the previous call ended — accepted or not — go together in the next call, once those 60 seconds have passed.
- Right before its first attempt, a call drops the Alert Groups on which the chain or the rule that Paged has stopped
  — acknowledged, snoozed or resolved meanwhile, or whose chain started over —; a call left without any is not sent.
  From its first attempt on, a call keeps its Alert Groups and its text, and takes no more.
- A call that the gateway accepted makes the person an Assignee of the chain that called, as a delivered Mention
  does.
- The text names each Alert Group by number, title and Severity level and says how to acknowledge, in the language
  of the person's profile: "Muster: 1 Alert Group needs you. #42 DiskFull, critical. Press 1 to acknowledge." Its
  action data names the call and fits in 64 bytes however many Alert Groups it is about.
- Every replica sends calls, critical ones first, through the limiter of the gateway's Connection, with the same
  `Idempotency-Key` `calls/<id of the call>` on every attempt: a gateway that keeps idempotency keys answers a repeated
  call `replayed`, which Muster counts as accepted, so a replica that restarts after a call never makes the person's
  phone ring twice. An answer of the class `transient` is retried within the retry budget of deliveries; a gateway
  that asks to wait (`rate_limited` with `Retry-After`) is waited for, and its waits count toward the time of that
  budget. Retries end when every Alert Group of the call has stopped.
- A call is never reconciled: it has no Root message to keep up to date, and a call that has gone is not changed
  afterwards.
- A text longer than the 1,000 characters of the Bridge protocol lists as many Alert Groups as fit, then "And N
  more.", and always ends with how to acknowledge.
- A call that the gateway refuses, answers in a way Muster cannot classify, or that used up its retry budget, ends Not
  delivered, as does one to a person without a confirmed contact (`no_confirmed_contact`), one through a gateway
  deleted before the call went (`gateway_deleted`) and one that comes due while the gateway is Broken
  (`gateway_broken`). Each of its Alert Groups records
  `page_not_delivered` in its Timeline, of the kind **Escalation chains**, naming the person, the gateway and the
  reason, and the chain and the step that called; outgoing webhooks in events mode receive it.
- A gateway that answers a call with a Fatal error, or whose call used up its retry budget, becomes
  [Broken](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#broken-gateways).

The text of a call, which names its Alert Groups, is cleared when the call ends; the call itself is kept until every
Alert Group it is about is removed by `retention.alert_group_summaries`.

`muster_gateway_calls_total{connection,outcome}` counts the attempts of calls, `muster_notification_gateway_broken`
is 1 while a gateway is Broken, and the log has the events `gateway_call_queued`, `gateway_call_attempted`,
`gateway_call_not_delivered`, `gateway_call_dropped`, `gateway_call_failed`, `gateway_broken` and
`gateway_recovered`, none with the contact or the text.

## Acknowledging from a call

When the person acknowledges in the call — presses 1, for example — the gateway reports `notification_acknowledged` with
the call's action data. Muster verifies the data, which names the call and its Connection, and acknowledges each Alert
Group of the call as the person the call was for, never as whoever holds the phone, with the Transport `gateway`: the
Timeline shows "Ivan from a call through Example Gateway", with the name of the gateway. It acknowledges only while
nobody owns an Alert Group: an Alert Group someone has already, the same person included, stays theirs, as a resolved
one stays resolved — a call never takes an Alert Group over. The gateway tells the person, in the language of their
profile, what happened: "Acknowledged: #12, #13", "Already taken by Alice" or "Already resolved". A Viewer, a disabled
person, and data that does not verify or belongs to another Connection change nothing and are answered so; the log
records the latter as `gateway_acknowledge_refused`. An event is handled once, however often the gateway reports it.

An acknowledgement that the gateway reports more than an hour after it happened (`bridge.event_max_age`) is dropped,
unanswered, and logged as `bridge_acknowledgement_dropped`. Because the action data of a call is the same for each of
its retries and carries no time, an acknowledgement also acts only for the notification that the gateway accepted the
call as — its `notification_id` — and only for two hours after the gateway accepted it: an acknowledgement of a call
the gateway never accepted — still waiting, not delivered or dropped — one with another `notification_id`, and one
that comes more than two hours after the call was accepted, whatever time the gateway reports, change nothing; the log
records them as `gateway_acknowledge_refused` with the reason `not_accepted`, `notification_mismatch` or
`stale_call`. A call that is still being sent — its answer not back yet, or retried after a temporary error or a
timeout — may already have rung: an acknowledgement of it acts, with no `notification_id` to compare, as a call is
sent only within `delivery.transient_budget`. That budget is checked as the call's attempts are made, so while no
replica sends calls, a call stays being sent, and acknowledgeable, until one does. An acknowledgement through a gateway counts in
`muster_commands_total{transport="gateway"}`. The key that signed a call's action data stays needed in the Keyring
while the call is being sent, so that such an acknowledgement can act, and for two hours after it was accepted while
any of its Alert Groups is open: the hour in which an acknowledgement is acted on, and as long again for the call to
ring or be retried by the gateway after it was accepted. The Keyring also keeps the key of a call not delivered after
an attempt for those two hours, though an acknowledgement of it changes nothing.

## Broken gateways

A gateway becomes **Broken** when a call through it ends with a Fatal error — the bridge, or the provider behind it,
refuses the token or the credentials (`forbidden`), or the outbound address policy blocks the bridge's address — or
when a call used up its retry budget (`delivery.transient_budget`). A call that the gateway refuses as `invalid`, a
contact the provider refuses for good for example, does not make it Broken: that call alone ends Not delivered.

While a gateway is Broken, the calls that come due are not sent and end Not delivered with the reason
`gateway_broken`, and they are not sent after the gateway recovers either: check the Alert Groups whose Timeline shows
them. Muster raises the Internal alert `MusterNotificationGatewayBroken`, and the Connection page shows "Broken since"
with the time and the reason in a banner. It reads the gateway's `info` every 5 minutes (`delivery.broken_probe_interval`);
the first success, or a check of the Connection whose step `info` passes, ends the state. The Destinations of the same
bridge are not affected, nor the other way round.

A Broken gateway cannot call anybody about itself: route the Internal alert to a messenger Destination. The
[runbook of `MusterNotificationGatewayBroken`](https://muster-io.github.io/muster/latest/operations/runbooks/MusterNotificationGatewayBroken.md) says how to
find the cause, fix it and check that calls go through again, with `muster bridge check` and its `--contact` flag.

## At night

A person's phone is quiet at night unless something rings or buzzes it. Whether a Mention in a Thread reply reaches a
phone as a push, in Mattermost, Slack and Telegram, depends on the messenger, its app, the settings of the person's
phone and the mode of the push notifications: a push may arrive, or may not, and Muster cannot see which. A Mention
shows the person that they were named; **only a Notification gateway is reliable at night**, because a call or an SMS
does not depend on any of that.

So, for anybody who must be reached at night, connect a Notification gateway, have them [confirm a
contact](https://muster-io.github.io/muster/latest/messengers/notification-gateways.md#contact-for-calls-and-sms), put a call in their important [Notification rule](https://muster-io.github.io/muster/latest/concepts/notification-rules.md#the-switch)
or in a step of the [Escalation chain](https://muster-io.github.io/muster/latest/concepts/escalation-chains.md#calls-through-a-notification-gateway), and do
not count on a Mention alone. [How an alert reaches people](https://muster-io.github.io/muster/latest/concepts/how-an-alert-reaches-people.md) shows a Page by
Mention and by call side by side.

# Link your messenger accounts

An **Account link** ties your Telegram account, your account on a Mattermost server, your account in a Slack workspace,
or your account on a messenger that Muster reaches through a [Bridge](https://muster-io.github.io/muster/latest/messengers/bridge.md), to your Muster User. With it, a button
you press under an Alert Group in a messenger runs as you — the Timeline names you and shows the messenger you pressed
in — and Mentions in the messenger name you, as does the footer of a Root message you acknowledged, snoozed or
resolved, which mentions you there in the messenger's own form.

A Telegram account belongs to one User across every Telegram Connection. A Mattermost account belongs to one User per
Mattermost Connection, since each Connection is its own server, and so does a Slack account, per Slack Connection,
and an account reached through a Bridge, per Bridge Connection. You have at
most one Telegram account and one account per Mattermost, Slack or Bridge Connection; linking another one replaces the
earlier link, and linking the same account again keeps its link and updates its username and name.

## Why links start in your profile

Every link starts in your signed-in Muster session, and the secret travels from there to your messenger account —
never the other way. Nobody can link your account by typing your name into a chat, and nobody can link their account
to your User: only the account that receives the secret Muster gave you in your own session gets linked. That is why
linking needs no extra password or TOTP code, and why an API token, an Admin's included, cannot start, confirm or
remove a link of its own User.

## Link Telegram

1. In your profile, open **Messenger accounts** and select **Link Telegram** — or **Relink Telegram** once you have a
   Telegram link, which the new link replaces.
2. Choose the Telegram **Connection**, when there are several, and select **Get link**. Muster shows a link `https://t.me/<bot>?start=<token>` as **Open Telegram** and as a QR code
   to scan with your phone. Open it on the device where you use Telegram, within 10 minutes
   (`account_link.telegram_token_ttl`); the link works once.

    ![The dialog Link Telegram: Open Telegram, the QR code, covered here, and the time the link expires](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/account-links/01-link-telegram.png){ .screenshot }

3. Telegram opens a chat with the bot. Press **Start**.
4. The bot answers "Linked to Muster user {your name} ({your login})", and your profile shows the link at once.

If the bot answers "This link is invalid or expired. Start again from your Muster profile.", the link was used
already, expired, belongs to another Telegram bot of Muster, or was never issued: start again from your profile. If it
answers "This account is linked to another user. Its owner or an admin can unlink it.", that Telegram account is
linked to someone else; nothing changed.

## Link Mattermost

1. In your profile, open **Messenger accounts** and select **Link Mattermost**. Choose the **Connection**, enter
   **Your Mattermost username** — with or without the `@` — and select **Send code**.

    ![The dialog Link Mattermost: the Connection chat.example.org and the username alice](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/account-links/02-link-mattermost.png){ .screenshot }

2. The Connection's bot sends you a direct message: "You requested a link to Muster. Do not share this code." with an
   8-character code. If you did not ask for it, ignore it.
3. Type the code into your profile within 10 minutes (`account_link.mattermost_code`); capital and small letters are
   the same. Select **Link**. The bot confirms "Linked to Muster user {your name}".

    ![The code entry of Link Mattermost: Enter the code the bot sent you in Mattermost, 5 attempts left](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/account-links/03-mattermost-code.png){ .screenshot }


A code allows 5 attempts; after five wrong codes it stops working, even with the right code, and you request a new one.
A new request replaces your earlier one. You can request 5 codes an hour, and 3 an hour for one Mattermost account
(`account_link.mattermost_code_requests`); beyond that, wait until your oldest request is an hour old. What others ask
for never refuses your request: one account receives at most 10 codes an hour whoever asks, and a request beyond them
is answered as if its code were sent, but nothing is sent, so that the answer never tells of other people's requests.
A username the server does not know, a bot account and a deactivated account cannot be linked. An account that is
linked to another User is refused.

The bot must be allowed to open direct messages with you; see [Direct messages](https://muster-io.github.io/muster/latest/messengers/mattermost.md#direct-messages).

## Link Slack

1. In your profile, open **Messenger accounts** and select **Link Slack**. Choose the **Connection**, enter **Your
   Slack email or name** and select **Send code**. An email finds your account for sure; a name is compared with the
   name and the display name of each account, regardless of case.

    ![The dialog Link Slack: the Connection Example workspace and the email alice@example.org](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/account-links/04-link-slack.png){ .screenshot }

2. The Connection's bot sends you a direct message: "You requested a link to Muster. Do not share this code." with an
   8-character code. It shows in the **Messages** tab of the bot's app, which is read-only, so you can read the code and
   cannot write to the bot. If you did not ask for it, ignore it.
3. Type the code into your profile within 10 minutes (`account_link.slack_code`); capital and small letters are the
   same, and select **Link**. The bot confirms "Linked to Muster user {your name}".

If Muster answers "No Slack account with this email or name was found.", check what you typed. If it answers "Several
Slack accounts have this name. Enter the email instead.", do. A bot, a deleted account and Slackbot cannot be linked,
and an account that is linked to another User is refused.

A code allows 5 attempts; after five wrong codes it stops working, even with the right code, and you request a new one.
A new request replaces your earlier one. You can request 5 codes an hour, and 3 an hour for one Slack account
(`account_link.slack_code_requests`); beyond that, wait until your oldest request is an hour old. As in Mattermost, one
account receives at most 10 codes an hour whoever asks, and a request beyond them is answered as if its code were sent,
but nothing is sent.

The bot can send the code only while the Messages tab of its app is on. Slack documents that with it off it refuses the
direct message, and then Muster answers that the Messages tab of the Slack app is turned off; the problem is
`messages_tab_disabled`. Ask the admin of the Slack app to turn the tab on under **App Home**, then request a new code.
The refused request still counts toward the limits above, so if you tried several times before the tab was on, you may
have to wait up to an hour. See [Connect Slack](https://muster-io.github.io/muster/latest/messengers/slack.md#what-the-manifest-sets).

## Link through a Bridge

A Bridge Connection reaches a messenger through a bridge, which tells Muster in its info what it can do for Account
links. Every bridge takes a **token** that you send to its bot. A bridge that can look people up and start a direct
chat with them also offers a **code** that its bot sends you, as Mattermost does. Your profile offers what the
Connection's bridge declares.

Once linked, a Mention of you in a message of that Connection names you by the name the bridge reported for your
account, which a bridge with native mentions turns into its messenger's mention. The footer of a Root message you
acknowledged, snoozed or resolved mentions you the same way when Muster posts it to a bridge with native mentions; an
edit carries no Mentions, so there, and through any other bridge, the footer names you by that name. Without a link, a
Mention entry that names you leaves you out of the message, and a footer names you by your Muster name as plain text,
which notifies nobody. When you link, change or remove an account, the open
Root messages whose footer names you are edited Quietly to show the new link. When a Mattermost, Slack or Bridge
Destination moves to another Connection, its open Root messages whose footer names you are edited once, Quietly, when
you have a link in either Connection, so that the footer names you by your link of the new Connection, or by your
Muster name without one; a move between Telegram Connections edits none. Details are in
[Messages and templates](https://muster-io.github.io/muster/latest/configure/messages-and-templates.md).

### By a token sent to the bot

1. In your profile, open **Messenger accounts** and select **Link through {Connection}** of the Bridge Connection.
2. On the tab **Token**, Muster shows a token of 43 characters, with **Copy**, and, when the bridge declares a link that
   opens a chat with its bot, that link as well. Within 10 minutes (`account_link.bridge_token_ttl`), send the token
   to the bot of that Connection in a direct message, or open the link, which hands the token to the bot. The token
   works once, and only with the bot of the Connection you chose.

    ![The dialog Link through Team chat on its tab Token: the token, Copy and the time it expires](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/account-links/05-bridge-token.png){ .screenshot }

3. The bot answers "Linked to Muster user {your name} ({your login})", and your profile shows the link with the name
   and the handle the bridge reported for your account.

If the bot answers "This link is invalid or expired. Start again from your Muster profile.", the token was used
already, expired, was started for another Connection — another bridge, or another bot of the same bridge — or was
never issued: start again from your profile. If it answers "This account is linked to another user. Its owner or an
admin can unlink it.", that account is linked to someone else; nothing changed.

### By a code by direct message

The code is offered only when the bridge declares how it finds people — its **lookup kind**, one of email address,
login, username or user id — and that its bot can start a direct chat. Your profile names the field after that kind:
**Email**, **Login**, **Username** or **User id**.

1. In your profile, select **Link through {Connection}** of the Bridge Connection and the tab **Code**. Enter your
   email address, login, username or user id in the messenger, as the field asks, and select **Send code**.
2. The bot sends you a direct message: "You requested a link to Muster. Do not share this code." with an 8-character
   code. If you did not ask for it, ignore it.
3. Type the code into your profile within 10 minutes (`account_link.bridge_code`); capital and small letters are the
   same. Select **Link**: the link is made at once, and the bot sends no confirmation.

    ![The tab Code of Link through Team chat after Send code: the login alice, the code entry and 5 attempts left](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/account-links/06-bridge-code.png){ .screenshot }


If the bridge finds no one, Muster answers "No account with this email was found." — or login, username or user id. If
the bot may not write to you, Muster answers "The bot cannot send you a direct message. Send it the token instead."
The limits are those of Mattermost: 5 attempts per code, a new request replaces your earlier one, 5 code requests an
hour for you and 3 an hour for you for one account, and at most 10 codes an hour to one account whoever asks, beyond
which a request is answered as if its code were sent and nothing is sent (`account_link.bridge_code_requests`). An
account that is linked to another User is refused.

## Several Connections of one messenger

An Organization may have several Connections of one messenger, such as two Mattermost bots on one server, two Slack apps
or a second Telegram bot. What a link covers differs by messenger:

- **Mattermost links are per Connection.** Each Mattermost Connection is its own Identity space, even when two
  Connections use bots on the same server: two bots on one server need two links, made one after the other from
  **Link Mattermost** with each Connection. Your profile lists one row per Connection.
- **Slack links are per Connection.** Each Slack Connection is its own Identity space, even when two Connections serve
  the same workspace with two apps: two Connections need two links, made one after the other from **Link Slack** with
  each Connection. Your profile lists one row per Connection.
- **Bridge links are per Connection.** Each Bridge Connection is its own Identity space, also when two Connections reach
  the same bridge with two bots: two Connections need two links, made one after the other, and a token started for one
  of them links nothing when you send it to the other's bot. Your profile lists one row per Connection.
- **A Telegram link is valid for all Telegram bots.** Telegram has one Identity space, so the link you make through any
  Telegram Connection lets you press buttons sent by every Telegram bot of Muster. Your profile shows it as "Telegram ·
  @<username> · for all Telegram bots", with "linked via <Connection>" below.

One chat reached through two Connections is two Destinations, and each posts its own message for every Alert Group. This
is allowed, but the Route editor warns when two or more of a Route's Destinations deliver to the same chat — one
Telegram chat, or one Mattermost server and channel — since their messages appear twice. The Destinations list, the
Route editor and the Alert Group page name each Destination's Connection and channel, so you can tell them apart.

## Unlink

Nothing can be unlinked from a chat. Removing a link, like making one, is recorded in the Audit log with who did it and
from where.

1. In your profile, open **Messenger accounts**. It lists each link with the messenger, the Connection, the account,
   when it was last used and when it was linked.

    ![Messenger accounts with four links: through the Bridge Team chat, Mattermost, Slack and Telegram for all Telegram bots](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/account-links/07-linked-accounts.png){ .screenshot }

2. Select **Unlink** on the row, and **Unlink** again in the dialog. Presses from that account no longer act as you.

    ![The dialog that confirms unlinking @oncall_admin](https://muster-io.github.io/muster/latest/assets/screenshots/messengers/account-links/08-unlink.png){ .screenshot }


## What Admins can do

Admins see the links of every User on the user page, under **Account links**, and can remove any of them — their own
from the web session only, as above. They cannot create a link for someone else. Deleting a User removes their links and voids the links they had started.

## What a press answers

| Who pressed | What happens | The private answer |
|---|---|---|
| An account without a link | Nothing changes | "Your Telegram account is not linked to Muster. Link it in your profile: {link}" — or the same for Mattermost or Slack, and "Your account is not linked to Muster. Link it in your profile: {link}" through a Bridge; the link goes to your profile and carries no secret |
| A linked Viewer | Nothing changes | "You are not permitted to do this" |
| A linked User who is disabled | Nothing changes | "Your Muster account is disabled" |
| A linked Responder or Admin | The Command runs as that User | "Done: {command}", or why it was refused |

The Audit log records `account_link.link`, `account_link.unlink` and `account_link.link_rejected` with the User, the
messenger, the account's id and username, and the Connection; a rejection says why: `token_unknown`, `token_used`,
`token_expired`, `wrong_connection`, `wrong_code` or `conflict`.
