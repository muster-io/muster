# 0010. Configuration only through the API

- Status: Accepted
- Date: 2026-10-02

## Context

Muster has a lot of configuration: Integrations, Routes and their policies, Connections and Destinations, Users and
Roles, OIDC sign-in, Link rules and Organization settings. Two models are common: configuration in files that the service
reads, or configuration in a database edited through an API and a UI. Some tools combine them with "provisioning" —
files that create or overwrite database objects at startup — which creates two sources of truth that drift apart.

Some things must exist before the database can be used at all: where the database is, the keys that protect the
secrets stored in it, the public addresses, and the first user who can sign in.

## Decision

**The database is the single source of truth for configuration, and the API is the only way to change it.** The UI is
a client of the API like any other, and a Terraform provider in a later layer (L2) will be one too. Every change goes
through the same validation, the same permissions and the same Audit log, with a before/after diff.

**No declarative provisioning in the first release (L1).** Apart from the first admin, nothing is created automatically
at startup: only the user knows which Integrations, Routes and Destinations they need, and creates them in the UI or
through the API. "Configuration as code" arrives with the Terraform provider. The demo configuration of `muster dev` is
an internal property of the development mode, which runs against fake servers; it is not a provisioning feature.

**The environment holds only bootstrap and infrastructure settings,** every variable named with the prefix `MUSTER_`:

- the database, either as one URL, `MUSTER_DATABASE_URL`, or as fields: `MUSTER_DATABASE_HOST`,
  `MUSTER_DATABASE_PORT`, `MUSTER_DATABASE_NAME`, `MUSTER_DATABASE_USER`, `MUSTER_DATABASE_PASSWORD` (or
  `MUSTER_DATABASE_PASSWORD_FILE`) and `MUSTER_DATABASE_SSLMODE`. If both forms are set, the URL wins and a warning is
  logged;
- the session-capable connection for the Leader lock, notifications and migrations (ADR-0007), either as
  `MUSTER_DATABASE_SESSION_URL` or as `MUSTER_DATABASE_SESSION_HOST` and `MUSTER_DATABASE_SESSION_PORT`, with every
  other field taken from the main connection. Without either, the main connection is used; a startup check stops
  Muster if that connection goes through a transaction pooler;
- the master keys, as the list `MUSTER_SECRET_KEYS` or `MUSTER_SECRET_KEYS_FILE` (ADR-0011);
- `MUSTER_PUBLIC_URL`, the address for people: links in messages, links in the profile, the OIDC redirect; and
  `MUSTER_INGEST_URL`, the address for machines: Mattermost button callbacks, Alertmanager receiver snippets, Heartbeat
  URLs and the Telegram webhook. The second defaults to the first. The public address is always set explicitly, never
  derived from an ingress;
- the listener addresses `MUSTER_LISTEN_INGEST`, `MUSTER_LISTEN_APP` and `MUSTER_LISTEN_INTERNAL` (ingest and app share
  one port when they are given the same address), `MUSTER_LOG_LEVEL` and `MUSTER_MIGRATE_ON_START`;
- the bootstrap admin, `MUSTER_BOOTSTRAP_ADMIN_EMAIL` with `MUSTER_BOOTSTRAP_ADMIN_PASSWORD` or
  `MUSTER_BOOTSTRAP_ADMIN_PASSWORD_FILE`.

Everything else lives in the database, including OIDC settings and bot tokens. All Destination adapters are compiled in
and always available; "enabling" one means creating a Destination of its type. The bootstrap environment is parsed with
`caarlos0/env` and validated with `go-playground/validator`; an invalid value stops startup with an error that names the
variable, instead of falling back to a default. Secret values come from an existing Kubernetes Secret or from `*_FILE`
variables and are never copied into Helm values. The process-wide proxy variables `HTTP_PROXY`, `HTTPS_PROXY` and
`NO_PROXY` are ignored; proxies are configured per client (ADR-0015).

**A master key is mandatory and never generated by Muster or the chart.** Without one the Helm chart refuses to install
with a clear message, and the docker-compose example ships a placeholder on which Muster refuses to start until it is
replaced. The documentation shows `openssl rand -base64 32` and advises keeping the keys in a secret manager and backing
them up separately from the database. Muster never writes keys anywhere; adding a key for rotation is a change to the
environment made by the operator (ADR-0011).

**First admin.** `MUSTER_BOOTSTRAP_ADMIN_EMAIL`, plus `MUSTER_BOOTSTRAP_ADMIN_PASSWORD` from a Secret or its `*_FILE`
variant. At startup, if the Organization has no Admin, Muster creates a local admin and records it in the Audit log as
done by "bootstrap". If an Admin exists, the variables are ignored and a warning says they can be removed. Emergency
recovery uses the CLI (`muster admin reset-password`, and `muster admin reset-totp` for a lost second factor).

**CLI subcommands are for emergencies, bootstrap and diagnostics only** — `muster migrate`, `muster ingest replay`,
`muster admin reset-password`, `muster admin reset-totp`, `muster secrets rotate-key --activate <id>`, `muster doctor`.
They work on the database directly. Subcommands that a person runs to change Muster's data — `ingest replay`,
`admin reset-password`, `admin reset-totp`, which removes a User's second factor, and `secrets rotate-key` — require
`--actor` and write it to the Audit log. `migrate` runs unattended (in an init container or through
`MUSTER_MIGRATE_ON_START`) and is recorded in the logs with the schema versions it applied; `doctor` only reads. Neither
takes `--actor`. Routine work goes through the API with a Personal access token.

## Consequences

- One source of truth: nothing drifts between files and database, and every change is audited the same way.
- Users who manage everything as code must script the API or wait for the Terraform provider.
- A fresh installation is empty apart from the first admin, so the UI must make the first steps easy (Alertmanager
  receiver snippets, suggested Routes).
- A broken OIDC configuration cannot lock everyone out: the bootstrap admin is local, and the CLI can reset passwords
  and second factors.
- Losing the master keys makes stored secrets unreadable; the startup check (ADR-0011) detects a wrong or missing key
  at once.

## Alternatives considered

- **Configuration files as the source of truth.** Changes would bypass the UI's validation and the Audit log, and
  editing in the UI would become impossible or confusing.
- **Continuous provisioning from files, as in Grafana.** Two sources of truth; objects edited in the UI are overwritten
  on the next restart.
- **One-time seeding of an empty database from a file.** Little value before the Terraform provider exists, and a second
  path to maintain.
- **Generating the master key in the chart** (`randAlphaNum` with `lookup`). `lookup` does not work under GitOps tools
  such as Argo CD and Flux, so the key would change on every sync and the database would become unreadable.
- **Muster generating the key and writing it to a Secret.** Requires write access to Secrets, and docker-compose would
  need a different path.
- **A mandatory `--actor` on every subcommand.** `migrate` runs in an init container with nobody to name, and `doctor`
  changes nothing; requiring a name there adds ceremony without accountability.
- **The database only as one URL.** A password with special characters must be URL-encoded, and a chart that takes the
  host from one place and the password from a Secret key would have to assemble a URL; fields avoid both, and the URL
  stays for those who already have one.
- **A mandatory separate session connection.** Most installations connect to PostgreSQL directly or through session
  pooling and would set the same value twice; defaulting to the main connection and checking it at startup catches the
  installations that need a second one.
- **A generated admin password.** It cannot be logged, because secrets never reach logs, and writing it to a Secret
  again requires write access.
- **Creating the first admin only through the CLI.** A manual step after every installation, at odds with GitOps.
