# Muster L4 — AI-assisted investigation

- Status: Draft — scope and kept designs only
- Date: 2026-10-02

L4 adds an optional AI module that explains an Alert Group and, step by step, investigates it. It brings your own model
— hosted or local — and never stands between an alert and the people who must see it. Detailed requirements are written
when work on the layer starts; this file fixes its scope and the decisions already taken. KeepHQ's approach — collect
data deterministically, then let a model summarize it — is the starting point. Terms follow
[`CONTEXT.md`](../../CONTEXT.md).

## Principles

- **The alert goes out first.** The Root message is published as in L1; AI results are added later, by editing the Root
  message and/or as a Quiet Thread reply. A slow, failing or disabled model never delays a notification.
- **Optional.** With the module off, nothing of it exists: no settings, no calls, no data leaves Muster.
- **Bring your own model, provider-neutral.** Each model connection has a base URL, a key, a model name and a prompt.
- **Read-only.** The model proposes; a person acts. Data sources have no write access, and no AI result runs a command.
- **Untrusted input.** Labels, annotations, logs, events and tool descriptions are data, never instructions.

## Tiers

| Tier | Sub-layer | What happens | Model requirements |
|---|---|---|---|
| T0 — summarizer | L4.0 | Built-in enrichers collect data deterministically; one model call turns it into a structured summary; no tools | any model with some path to JSON; context of at least 16k tokens |
| T1 — plan selector | L4.0b | A first call chooses, through structured output, which of a fixed set of queries to run; Muster runs them; a second call summarizes; no tools | reliable JSON schema with enumerations; at least 16k tokens |
| T2 — agent | L4.1 | An agent loop with native tool calling over read-only tools, bounded by steps, time and tokens | native tool calling and forced tool choice; at least 32k tokens |

The documentation states these minimums and warns that some local servers default to a small context window (for
example Ollama's `OLLAMA_CONTEXT_LENGTH`). Exact numbers are confirmed on a prototype.

**Result.** One structured result for every tier, with the reasoning fields before the conclusions so that models reason
before they answer: `evidence[]` (claim, query, link), `analysis`, `probable_cause`, `confidence`, `next_steps`,
`unknowns`, and `summary` last. A claim without a link Muster built is not shown in the Root message; `unknowns` is
shown when tools failed or a budget ran out. Refusals and truncated answers are explicit outcomes, not empty analyses.

## Protocols and adapters

- First release of L4: OpenAI Chat Completions and Anthropic Messages. The OpenAI Responses API is added with T2.
- Muster uses its own thin adapters on the standard HTTP client, through the outbound HTTP package (ADR-0015); official
  SDKs serve only as references in tests, because they read the environment and retry on their own.
- Connection capabilities (structured output, tool calling, context size) are probed by the connection check and can be
  overridden by hand.
- Structured output follows a ladder: JSON schema → a forced tool call → JSON mode → instructions in the prompt; the
  answer is always validated by Muster; one repair attempt follows a failure, and after that the free-text answer is
  shown, marked as unstructured.
- Adapters stream internally and return the complete answer (to be confirmed on a prototype). The agent loop is Muster's
  own code, without a framework.

## Data sources

Configured per Integration — per cluster — and all optional:

- **Metrics**: the URL of a VictoriaMetrics or Prometheus endpoint, with tenant headers where needed.
- **Logs**: the URL of a VictoriaLogs or Loki endpoint, with tenant headers where needed.
- **Kubernetes API, read-only**: an API address with a ServiceAccount token, or the in-cluster ServiceAccount when
  Muster runs in that cluster; a CA certificate instead of skipping TLS verification. The chart ships a `ClusterRole`
  `muster-reader` with get, list and watch on pods, `pods/log`, events, deployments, replicasets and nodes — never
  secrets. The connection check reviews the effective permissions and warns if secrets or any write access are
  available.
- **No network path to a cluster**: the L2 `muster agent` reads locally inside the cluster and sends results out;
  cluster credentials never leave it.
- Remediation, if it ever comes, is a separate feature with its own credentials and human confirmation; data sources
  never gain write access.

## Built-in enrichers

Deterministic enrichers are chosen by `alertname`. Starting candidates:

| Alerts | Enrichment |
|---|---|
| `KubePodCrashLooping`, `KubePodNotReady`, `KubeContainerWaiting` | reason and exit code of the last termination; the pod's events; the log tail of the previous (crashed) container; whether the image changed or a rollout happened in the last 30 minutes; past Alert Groups for the same workload |
| `KubeJobFailed` | job status, events, logs of the failed pod |
| `KubeNodeNotReady`, node filesystem and host alerts | node conditions and pressure, top pods by the resource, a one-hour graph |
| `CPUThrottlingHigh` | limits and requests, throttling ratio, neighbours on the node |
| `TargetDown` | DNS and endpoint state |
| any alert with `runbook_url` | the runbook's title and a short excerpt |
| any alert | similar Alert Groups of the last 30 days and how they ended |

Later, in T1, the model chooses among such queries instead of a fixed list per `alertname`.

## MCP client (T2)

- Added after the built-in tools, for capabilities Muster does not have itself.
- The official Go SDK; Streamable HTTP only — Muster never starts local processes from configuration (no stdio).
- Each MCP connection has an allowlist of tools; tool definitions are pinned by hash, and a changed definition disables
  the tool until an Admin confirms it.
- Each MCP server has its own secret; a User's token is never passed through.

## Safety and cost controls

- **Credentials.** Static keys only (Bearer, `x-api-key`, `api-key` or a custom header), stored encrypted and
  write-only; short-lived cloud credentials go through a gateway. Redirects are never followed. OpenAI-style requests
  set `store: false`.
- **Redaction.** Before anything is sent or cached, secrets are removed: built-in rules derived from gitleaks (MIT, with
  attribution), the Organization's own regular expressions and a list of labels never to send. Redactions are counted.
- **Where data goes.** Each model connection is marked local or external; a Route can require local-only processing; an
  external fallback for such a Route needs explicit consent from an Admin. The UI shows where an Alert Group's data is
  sent.
- **Money and load.** Admins enter prices per million input and output tokens; a daily cap per Organization stops new
  runs with "AI skipped: limit reached". Each run has token, time and (for T2) step budgets. Concurrency per connection
  defaults to 1 for local and 4 for external models.
- **Output.** No Mentions; only links Muster built from the queries it ran; escaped like any message; labelled "AI,
  confidence: …".
- **Prompts.** System prompts are in English; the answer language follows the Organization; untrusted data is placed
  only in user turns, clearly delimited, never in the system prompt.
- **Records.** Every run records who or what started it, the connection, model, prompt version, input hash, number of
  redactions, token counts, estimated cost, duration and outcome; T2 also records each tool call. Conversations with the
  model are kept 30 days, after redaction.

## Candidates, not yet decided

- When not to run: on resolved Alert Groups, on a Reopen within the Reopen window, on repeats without changes, on
  snoozed Alert Groups.
- Caching T0 results by input hash for 30–60 minutes; stable prompt prefixes for provider-side caching.
- Feedback buttons ("useful" / "wrong") feeding an evaluation set, and an evaluation command against a fake and a real
  model.
- Later sub-layers: questions in the Thread ("why?"), summaries and post-incident review drafts (with L3), and
  suggestions to merge related Alert Groups, decided by a person.
- Thread mirroring (L2) as context for investigations.
