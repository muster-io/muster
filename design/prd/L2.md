# Muster L2 — On-call parity

- Status: Draft — scope and kept designs only
- Date: 2026-10-02

L2 brings Muster to parity with a self-hosted on-call tool: who is on call and when, what happens when nobody reacts,
more ways to learn about alerts, and configuration as code. Detailed requirements are written when work on the layer
starts; this file fixes its scope and the designs already worked out while L1 was specified, so they are not lost or
reinvented. Terms follow [`CONTEXT.md`](../../CONTEXT.md); L1 behaviour is in [L1.md](L1.md).

## Scope

- **Schedules, rotations and Teams.** Who is on call and when; Teams arrive together with schedules. An **Assignee** is
  a person put on an Alert Group by a schedule or an escalation before anyone has acknowledged it.
- **Escalations and paging.** Sequences of steps that call more people when an Alert Group stays Firing, beyond the L1
  ack timeout; ack timeout notices start mentioning the person on call.
- **Data-driven Mentions** (`team="payments"` → `@payments-oncall`), together with schedules.
- **Connection modes `pull` and `agent`**, delivered as one module, including the "silenced in Alertmanager" indication.
- **A generic inbound webhook** for sources other than Alertmanager.
- **Backup Destinations** on a Route.
- **Alertmanager silence sync.**
- **Telegram forum topics and plain group chats** as further Telegram Destination modes.
- **A Terraform provider and an MCP server**, both clients of the API.
- **Maintenance mode.**
- **A per-Route Loud/Quiet matrix**, including whether new Alerts take the acknowledgement away.
- **Mirroring messenger Threads into the Timeline**, designed together with L4.
- **A step-by-step Destination test.**
- **Opt-in telemetry.**
- **Hold hints**, if hold returns (see [Waiting for operating experience](#waiting-for-operating-experience)).
- **Merging Alert Groups by hand**: attaching an Alert Group to another one that stands for the same problem.
- **Exporting the Alert Group list as CSV**, with the filters of the current view.

## Deferred designs

### Schedules, escalations and paging

- L1 ack timeout notices mention nobody unless a Destination is configured to; with schedules, they mention the person
  on call.
- Escalation is a separate concept from the ack timeout and from Reminders: an ordered list of steps (notify, wait,
  notify someone else) attached to a Route.
- A flow to support from the start: a `MusterHeartbeatLost` Internal alert goes to the operations Destination and, if
  nobody acknowledges it within 15 minutes, pages whoever is on call. In L1 the same Route can also deliver it to an
  outgoing webhook.
- Phone calls, SMS and mobile push are not part of the start; paging happens through messenger Mentions and outgoing
  webhooks, and those channels may come later as separate modules (see the mobile companion app under
  [Later, outside the layers](#later-outside-the-layers)).

### Connection modes `pull` and `agent`

- **pull** — Muster polls Alertmanager's API every 60 seconds with `GET /api/v2/alerts?receiver=<the Muster receiver>`.
  An alert missing from the API without a `resolved` webhook is resolved by the system only if it is missing from two
  consecutive polls **and** Alertmanager has been up for more than 5 minutes (from `/api/v2/status`); otherwise an
  Alertmanager restart would resolve everything at once. For an HA pair the Integration holds a list of Alertmanager
  URLs; Muster polls the first live one and fails over; "missing" means missing from every live instance. The reason
  appears in the Timeline.
- **agent** — a small `muster agent` runs next to Alertmanager, polls it locally and pushes Snapshots to Muster over
  outbound HTTPS with an Integration token, for networks that allow only outbound connections. The same agent is the
  transport for L4 data sources in such networks.
- Both modes show Alertmanager silences: "🔕 silenced in Alertmanager until …", from the alert's `suppressed` state.
- Polling is a Leader task. Ingestion stays idempotent on `fingerprint + status + startsAt`. The UI already shows each
  Integration's Connection mode and the precision it gives.

### Generic inbound webhook

- Accepts any JSON body and turns it into a title, labels, a status and a fingerprint through templates in the L1
  template sandbox; presets for common senders (for example Grafana Alerting, Zabbix, Uptime Kuma, scripts).
- A body that fails to parse is stored with its error, shown in the UI, and replayed after the template is fixed; the
  UI previews parsing on stored bodies.
- Needs its own automatic resolution: event streams have no Snapshots, so Gone and Stale do not apply.

### Backup Destination

A Route may name a backup Destination that receives its Alert Groups while the main Destination is Broken.

### Alertmanager silence sync

Optional per Integration, off by default, and always explicit: a separate "Create Alertmanager silence" action, distinct
from Snooze. Muster never creates an Alertmanager silence on its own.

### Telegram forum topics and group chats

Two more Telegram Destination modes, as alternatives to the L1 channel with a discussion group: a forum supergroup in
which each Alert Group gets its own topic, and a plain group chat in which the Root message is a message of the group
and its Thread is the replies to it.

### Terraform provider and MCP server

- **Terraform provider** — configuration as code through the API with the generated Go client; optimistic locking
  (`ETag` / `If-Match`) prevents silent overwrites; authenticates with a Service account token.
- **MCP server** — stateless, over Streamable HTTP, so several replicas need no session affinity; authenticates with a
  Personal access token; commands go through the same dispatcher, and the Audit log shows "{user} via token {name}".

### Maintenance mode (draft)

- "Maintenance until T" on an Integration or a Route.
- Ingestion and grouping continue; notifications and timers stop; the UI shows a banner and a counter of what was held.
- When maintenance ends, Alert Groups still firing are published with a mark — the same mechanism as the end of a Storm
  — and those already resolved are not.
- Whether Urgent Alert Groups break through is a setting of the maintenance window.
- Turning maintenance on and off is recorded in the Audit log.

### Per-Route Loud/Quiet matrix

The fixed L1 table becomes configurable per Route (for example, new Alerts in a firing informational Alert Group stay
Quiet). Because only a new message can ring, changing the matrix means adding or removing Thread replies, never making
edits Loud. The same place decides whether new Alerts in an acknowledged Alert Group take the acknowledgement away —
the Alert Group becomes firing, Loudly — which L1 never does: there the acknowledgement always stays and new Alerts are
Quiet.

### Data-driven Mentions

Rules that choose whom to mention from Alert labels, such as `team="payments"` → `@payments-oncall`, evaluated together
with schedules.

### Mirroring Threads into the Timeline

Replies people write in a Root message's Thread are copied into the Alert Group's Timeline. Designed together with L4,
which needs that discussion most.

### Step-by-step Destination test

A test message that goes through the whole lifecycle — creation, a new Alert, Acknowledge, Takeover, Snooze, Resolve,
Unresolve, a Reminder — so that an outgoing webhook's update and Thread requests can be verified without a real alert.
Until then, Unresolve in the UI lets people walk a real Alert Group through its statuses.

### Merging Alert Groups by hand

A person attaches an Alert Group to another one that stands for the same problem — for example two Routes that caught
two sides of one outage — and can detach it again. To be settled when L2 starts: whether the attached Alert Group
follows the status of the main one, what its Root messages show, how commands and timers treat it, and how attaching
relates to Incidents (L3), which span several Alert Groups without merging them. Suggestions to merge related Alert
Groups, decided by a person, come with L4.

### Exporting the Alert Group list

The Alert Group list (L1) can be exported as CSV with the filters, time range and columns of the current view. In L1
the same data is available through the paginated API.

### Opt-in telemetry

Off by default; when turned on, a daily anonymous report (version, orders of magnitude, Destination types), with the
exact content shown in the UI. Muster never enables telemetry by default.

## Waiting for operating experience

These mechanisms are left out of L1 on purpose and come back only if operating Muster shows they are needed. What L1
does instead is noted with each.

- **Flapping detection.** In L1 a flapping alert produces Reopens of one Root message and Thread replies, as long as
  each gap is shorter than the Reopen window.
- **Resolve delay.** In L1 the Reopen window already keeps one message per problem; revisit together with flapping.
- **Hold** (delaying publication). Design kept:
  - an attribute `publish_after`, not a status; a Route setting, off by default; never for Urgent Alert Groups;
  - presets 1, 2, 5, 10 and 15 minutes; 15 minutes is the maximum, and the UI explains that longer delays belong in the
    rule's `for:`;
  - a rise to Urgent during hold publishes at once;
  - an Alert Group that resolves during hold is never sent; its Timeline says "resolved by itself after N min", and the
    Route shows how many Alert Groups were held and resolved on their own in the last 24 hours;
  - Acknowledge or Snooze during hold publishes at once, Quietly, in the resulting status; Resolve during hold closes
    the Alert Group without publishing it, keeping its Timeline;
  - the ack timeout counts from publication;
  - hold hints (L2) suggest values from statistics such as time to resolve, without AI.
- **Adaptive Thread batching window.** Stretch the window when limiters are under pressure.
- **CEL expressions for Matchers**, as an advanced mode with OR.
- **Maximum Alert Group age.** Options kept: a maximum age on the Route that re-issues a new Alert Group, or reposting
  the Root message without closing the Alert Group. In L1 an Alert Group lives as long as any of its Alerts fires, and
  Reminders keep its Owner aware.
- **A Note required on resolve.** A Route setting that makes Resolve require a Note. In L1 Resolve is one action
  everywhere and Notes are optional, from the UI and the API. If the setting returns, messengers need a rule for it:
  refuse the press privately with a link to the Alert Group in Muster, or hide the Resolve button on such Routes.

## Later, outside the layers

Row-level security as a second line of Organization isolation; a schema management tool for migrations; external key
providers (Vault transit, cloud KMS) behind the key provider interface; SCIM; custom Roles built from existing
Permissions; an external ingestion queue for very large installations; reading a repeat-interval hint from the
`routeLabels` that newer Alertmanager versions send; a Telegram Bot API server kind and a wizard that moves a bot
between Bot API servers, if asked for.

**Mobile companion app.** A phone app with push notifications about Alert Groups and their commands, like the Grafana
IRM mobile app, as a client of the API. Which layer it belongs to is decided when L2 and the later layers are designed;
until then, people act from messengers and from the web UI, which works at phone width in L1.

Not at the start: digests; phone calls, SMS and mobile push — the companion app above is the planned way to push.
Never: an importer from Grafana OnCall.
