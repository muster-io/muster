# Muster L1 — Product requirements

- Status: Draft
- Date: 2026-10-02

L1 is Muster's first release: Alertmanager notifications become Alert Groups that people acknowledge, resolve and snooze
in Mattermost, Telegram or the web UI, with one editable message per Alert Group and Destination. This document is the
index of L1: its scope, rollout stages, the map of capabilities `C-01`…`C-21` — each specified in its own file under
[`l1/`](l1/) — the conventions those files follow, the non-functional requirements, what is out of scope and what is
still open. Terms follow [`CONTEXT.md`](../../CONTEXT.md); the reasons behind architectural choices are in the
[ADRs](../adr/README.md).

## 1. Scope

### 1.1 What L1 delivers

- **Input.** Alertmanager webhooks only, read as Snapshots: an Alert resolves when Alertmanager says so, for the Alert
  or for its whole Alertmanager group, when it is Gone from two consecutive Snapshots for at least a few minutes, or
  when it goes Stale while the Integration's Heartbeat is live. One Integration per Alertmanager cluster, with
  Integration tokens, optional Static labels and a Heartbeat. Webhooks are stored before they are processed and can be
  replayed.
- **Routing and grouping.** User-built Routes with Alertmanager-style Matchers, first match wins, a Default route that
  always exists, and a Group key that is a list of labels with a preview. Urgency from the Route or the Severity level;
  Severity levels critical, warning and info, with unfamiliar values counted as warning.
- **Alert Group lifecycle.** Four statuses — Firing, Acknowledged, Resolved, Snoozed — with Reopen that restores the
  previous status, a Grace period after a manual resolve, Replacements, Continuations, a rise to Urgent, visible
  reasons and a Timeline in which every change is a lifecycle event with its loudness and Mentions; a full web UI to
  manage them: a live list with status tabs, filters and search, a detail page, past Alert Groups and statistics, with
  the list and the detail page usable on a phone.
- **Commands.** Acknowledge / Unacknowledge, Resolve / Unresolve, Snooze / Unsnooze and Notes, through one dispatcher,
  from the UI (one at a time or in bulk), the API, Mattermost and Telegram, with Takeover and an Audit log entry for
  every action of a person or automation.
- **Delivery.** One Root message per Alert Group and Destination, reconciled to its Desired state; Threads with
  batching; limiters per Destination and Connection; Storm summaries per Route; a fixed Loud/Quiet table; error
  classes; Broken Destinations — after a fatal error or exhausted retries — that are probed, through a Destination check
  when nothing waits, and recover to the current state; Not delivered only for unknown responses and failed templates;
  safe output; Mattermost, Telegram (through a proxy or another Bot API address where needed) and outgoing webhook
  Destinations, the last with ordered, at-least-once events — one per lifecycle event — or templated requests and
  Secrets; a Destination test.
- **Timers.** Ack timeout notices that end in Unclaimed; Reminders to the Owner; optional auto-unacknowledge after two
  unanswered Reminders.
- **Access.** Local users and OIDC with group-to-Role mapping, three Roles, TOTP, sessions, Personal access tokens,
  Service accounts, Account links started only from the web session, an Audit log, encrypted write-only secrets with a
  rotatable Keyring, an outbound address policy and per-client proxies.
- **Operations.** Muster's own metrics, chart alert rules, a dashboard, Internal alerts, an outgoing heartbeat and a
  read-only System status page; a Helm chart and a docker-compose example; migrations, releases, `muster doctor`; a
  versioned documentation site with a runbook for every alert Muster can raise.

### 1.2 Rollout stages

Muster is introduced next to an existing alerting path in three stages, then takes over. Each stage is done when the
sentence in the last column is observably true. The capabilities are grouped by the first stage that needs them.

| Stage | What runs | Capabilities | Done when |
|---|---|---|---|
| Foundation | Process, sign-in, tokens | C-01 – C-04 | An Admin installs Muster from the chart or compose example and signs in. |
| 1. Observe | Webhooks are received, grouped and handled in the web UI; nothing is sent to messengers | C-05 – C-10 | For every Integration, the number of webhooks Muster accepted matches Alertmanager's `alertmanager_notifications_total` for the Muster Alertmanager receiver, and the Alert Groups in the UI open and resolve together with their alerts. |
| 2. Shadow | Messages go to a test Destination, in parallel with the existing messenger receiver of Alertmanager, for 1–2 weeks | C-11 – C-16 | Over the shadow period, every notification of the existing receiver has a matching Alert Group in the test Destination and no Root message is missing, duplicated without a Timeline entry, or left in an outdated state. |
| 3. Act | Buttons, ack timeouts and Reminders are used by the team | C-17, C-18 | The team acknowledges and resolves from the messenger, ack timeout notices and Reminders arrive on schedule, and the Audit log attributes every press to a User. |
| Cut-over | The previous messenger receiver is removed from Alertmanager once the shadow comparison is clean | — | Alertmanager sends alerts to Muster instead of the previous receiver; only Muster's own critical rules take the route that bypasses Muster (C-19). |
| Operations | Needed before cut-over | C-19 – C-21 | Every chart rule and Internal alert links to a published runbook, and a stopped Muster is noticed outside Muster. |

## 2. Conventions

**Files.** Each capability has one file `l1/C-NN-<slug>.md` with the sections Goal, Scenarios, Functional
requirements, UI, API surface, Acceptance, Related ADRs, Depends on and Suggested story split. Tables that several
capabilities share live in [`l1/reference.md`](l1/reference.md); every configurable value and built-in limit lives in
[`l1/defaults.md`](l1/defaults.md).

**IDs.** Functional requirements are `C-NN.FR-n`, acceptance statements `C-NN.AC-n`, provisional items `P-NN`. IDs are
stable and never reused: when a requirement moves to another capability or is removed, its ID is retired, the file
skips that number, and [section 6](#6-retired-and-moved-ids) records where it went. New requirements take the
next free number of their capability, so numbers inside a file are not always in order.

**Stories.** Stories are contract files `design/stories/S-NNN-<slug>.md`, grouped under one issue per capability
(`C-NN`). A capability without a UI is one backend story, or several when its "Suggested story split" says so; a
capability with a UI is a backend story first and then a frontend story built on the merged API. Each story lists the
IDs it covers (for example `covers: [C-05.FR-1, C-05.FR-3, C-05.AC-1]`) and the default names it uses. An acceptance
statement belongs to the story whose merge makes it checkable — a statement about a page belongs to the frontend
story. A capability is done when its stories together cover every FR and AC of its file.

**Defaults.** A name of the form `area.setting` — or an environment variable `MUSTER_*` — refers to a row of
defaults.md. Requirements cite the name instead of repeating the number; a story that changes a value changes it in
defaults.md.

**Provisional.** _Provisional_ marks a value or behaviour that was inferred while writing this PRD rather than decided.
Each one has an item `P-NN` in [section 5.3](#53-provisional-values-and-behaviours) and is marked in defaults.md or in
its requirement. A story or a test-environment measurement may change it; the change updates the requirement or
defaults.md and closes the item in the same pull request.

**Facts.** An id of the form `F-NNN` refers to an entry of [verified facts](../facts.md): behaviour of Telegram,
Mattermost or Alertmanager checked on the real system, with the date and the method. A requirement that relies on such
behaviour cites the fact.

**Acceptance at merge.** Every acceptance statement can be checked when its capability merges, using only that
capability and the ones it depends on — with the fake servers of `muster dev`, the recording test adapter of C-11 and a
virtual clock where the statement says so. A requirement may mention what a later capability adds ("from C-11 on");
such a part is checked by that later capability. An acceptance statement that cannot be checked when its capability
merges is verified by the story in which its dependency appears, and the [coverage table](../stories/coverage.md)
names that story.

**Events and loudness.** Every change of an Alert Group records a lifecycle event — a row of the lifecycle event tables
of C-09.FR-22, C-10.FR-15 and C-17.FR-11 — as a Timeline entry that carries the event name, its loudness and its
Mentions, readable through the API. Destinations receive these events from C-11 on: messengers as the tables' last
column says, outgoing webhooks one to one (C-15.FR-2); what delivery adds for one Destination is in the
[Loud/Quiet table](l1/reference.md#loud-and-quiet). Where an earlier capability says "a Loud event", its acceptance
checks the `loudness` and `mentions` of the Timeline entry, not a message.

**UI.** Every page is in English and Russian, shows times in the user's time zone, and shows and enables only what the
user's Permissions allow ([Roles and Permissions](l1/reference.md#roles-and-permissions)). Texts quoted in requirements
are the English originals.

## 3. Non-functional requirements

- **NFR-1 Throughput and scale.** For one Organization, Muster accepts a burst of 50 webhooks per second for one minute
  without errors or loss, and holds 10,000 active Alerts (fingerprints) in 1,000 open Alert Groups. A nightly load test
  on `muster dev` with the fake servers checks these figures.
- **NFR-2 Latency.** The 95th percentile from receiving a webhook to handing the resulting message to the messenger's
  API is at most 5 seconds when the limiters have room (`muster_delivery_latency_seconds`; chart rule
  `MusterDeliverySlow`). Under the NFR-1 load, ingestion answers within 1 second at the 99th percentile
  (`muster_ingest_request_duration_seconds`), far inside Alertmanager's 15-second peer timeout, beyond which the second
  instance of an HA pair sends its copy ([F-038](../facts.md#ha-pairs)) (_provisional_, P-44).
- **NFR-3 Footprint.** The minimal installation — one Muster replica and PostgreSQL — runs within 256 MB of RAM at the
  NFR-1 figures, measured as the sum of the peak memory working sets of the Muster and PostgreSQL containers of the
  compose example, whose PostgreSQL memory is capped (C-01.FR-15), during the nightly load test (_provisional_
  measurement, P-43).
- **NFR-4 Availability.** Every replica serves traffic and runs ingestion, delivery and timers; a lost Leader is
  replaced within one minute and its absence never stops ack timeouts, Reminders, ingestion or delivery. A webhook
  answered with `202` is never lost; webhooks sent while Muster is down are covered by Alertmanager's retries and
  repeats, and the UI says when data may be incomplete after downtime. A messenger outage longer than the retry budget
  loses nothing still open: the Destination turns Broken and recovers to the current state. Readiness depends only on
  the database. A nightly end-to-end run uses two replicas.
- **NFR-5 Durability and backup.** PostgreSQL holds all state. Backups of the database and of the master keys are taken
  separately; the documentation gives the restore order, and `muster doctor` verifies a restore, including the key
  canary.
- **NFR-6 Security.** Secrets are encrypted with AES-256-GCM under a rotatable Keyring; tokens Muster issues are hashed;
  secret fields are write-only for everyone and masked wherever requests are shown; outgoing webhook credentials are
  Secrets; no secret reaches a log line or an error, including tokens inside request URLs (checked in CI). Sessions use
  secure cookies with CSRF protection; the SPA has a Content Security Policy; passwords use argon2id with sign-in
  throttling; TOTP is available to everyone. Messenger buttons are signed. Outbound requests follow the outbound address
  policy, never follow redirects and go through per-client proxies only. A Telegram bot token is sent only to the saved
  Bot API address. OIDC refuses users without a mapped group by default. Alert data is escaped and cannot mention
  anyone. Dependencies are scanned, images are signed and come with an SBOM.
- **NFR-7 Privacy.** L1 sends no telemetry. Deleting a user pseudonymizes them. Metrics never carry alert labels, users
  or Alert Group numbers. Muster sends no email.
- **NFR-8 Internationalization.** The UI is in English and Russian from the first release; CI fails on a missing
  translation; Russian plural forms are handled. Built-in message texts exist in both languages, chosen per Route. The
  documentation is in English.
- **NFR-9 Time.** Messages show absolute times in the Organization's time zone; the UI shows the user's time zone
  (browser, overridable in the profile); the API uses UTC in RFC 3339. All windows and timers run on Muster's clock; a
  clock skew above `process.clock_skew_warning` is reported. The documentation requires NTP on the nodes.
- **NFR-10 Retention.** Retention periods are those of defaults.md (`retention.*`), editable in the UI; high-volume data
  lives in time partitions and is removed by dropping whole partitions, so the promise for Stored Snapshots holds with
  daily partitions.
- **NFR-11 Upgrades.** Versions follow semantic versioning; during 0.x breaking changes are allowed; from 1.0 `/api/v1`
  is stable and removals are announced one minor release ahead. Rolling updates are supported only between adjacent
  minor versions; skipping versions requires stopping Muster; downgrades are not supported and the documentation says to
  back up before upgrading. Migrations are expand/contract and compatible with the previous release; a binary refuses a
  newer schema.
- **NFR-12 Compatibility.** PostgreSQL 14 or newer, directly or through a session-capable pooler for the session
  connection. Alertmanager webhooks; repeat learning uses `notification_reason` when present and falls back to
  identical Snapshots. Mattermost through its REST API v4 with a bot account; Telegram through the Bot API at
  `api.telegram.org` or a compatible base URL. Binaries for linux and darwin on amd64 and arm64. Kubernetes through the
  Helm chart, with optional Ingress and Gateway API routes.
- **NFR-13 API.** Spec-first OpenAPI; cursor pagination (`api.page_size`); RFC 9457 errors with field pointers;
  optimistic locking on configuration; UTC times; `public_id` in URLs (ADR-0008).
- **NFR-14 Quality.** Coverage of at least 95 % for the core and 80 % elsewhere; mutation testing reported nightly;
  end-to-end tests with fake servers and a real browser; every capability's acceptance statements are covered by tests
  or recorded evidence in the pull request.
- **NFR-15 Phone width.** Responders open links from messages at night on a phone, so the Alert Group list and the
  Alert Group page, with their commands, work in a phone browser from a viewport 360 CSS pixels wide without horizontal
  scrolling of the page (C-09.FR-24); end-to-end tests run them at that width. Other pages only need to stay usable
  there.

## 4. Out of scope for L1

Planned for **L2** ([L2.md](L2.md)): schedules, rotations, teams, Assignees, escalations beyond the ack timeout and
paging the person on call; the `pull` and `agent` Connection modes, with polling rules and the "silenced in
Alertmanager" indication; a generic inbound webhook; backup Destinations; Alertmanager silence sync; Telegram forum
topics and plain Telegram group chats as Destinations; the Terraform provider and the MCP server; maintenance mode; a
per-Route Loud/Quiet matrix, together with a Route setting that removes the acknowledgement when new Alerts arrive;
data-driven Mentions; mirroring messenger threads into the Timeline; a step-by-step Destination test; opt-in telemetry;
hints for hold; merging Alert Groups by hand (attaching one to another); exporting the Alert Group list as CSV.

Planned for **L3** ([L3.md](L3.md)): Incidents. Planned for **L4** ([L4.md](L4.md)): AI-assisted investigation.

**Waiting for operating experience:** flapping detection, a resolve delay, holding publication back ("hold"), an
adaptive Thread batching window, CEL expressions for Matchers, a maximum Alert Group age, a Route setting that requires
a Note to resolve.

**Later, outside the layers:** row-level security, a schema management tool, external key providers (Vault, cloud KMS),
SCIM, custom Roles, an external ingestion queue, reading a repeat-interval hint from Alertmanager's `routeLabels`; a
Telegram Bot API server kind and a wizard that moves a bot between Bot API servers, if asked for.

**Not at the start:** digests; phone calls, SMS and mobile push — a mobile companion app with push notifications is
noted in [L2](L2.md#later-outside-the-layers), its layer still open. **Never:** an importer from Grafana OnCall.

**Also not in L1:** declarative provisioning (configuration only through the API); OR in Matchers; Mattermost OAuth or
Telegram Login for Account links; automatic linking by email; a public demo installation.

## 5. Open questions

### 5.1 Test-environment facts

Short experiments confirm these before the affected stories are finalized; the design works either way unless noted.
Answers are recorded in [verified facts](../facts.md), and the requirements cite them.

1. Whether a Telegram bot receives the automatic copy of its own channel post (C-14.FR-3). _Answered:_ it does as an
   admin of the discussion group, not as an ordinary member (F-003, F-005).
2. Telegram's real limits for channel posts, edits and discussion groups, and whether edits count (C-14 limiters,
   P-28, P-29). _Answered for one chat:_ sends and edits share a budget of about 20 per minute (F-016, F-017); the
   Connection's limit (P-28) is still open.
3. Whether Telegram limits how long a bot can edit a channel post; if it does, long-lived Root messages need
   republishing. _Under test_ (see [Pending](../facts.md#pending)). Mattermost allows edits at any age by default
   (F-032); a limit set by its admin is question 12.
4. How phones notify for `disable_notification`, edits and Thread replies in Telegram and Mattermost. _Answered for
   Telegram_ (F-012 to F-015). _Answered for Mattermost, except phone push:_ an edit notifies nobody, even one that adds
   a Mention, while a new post with a Mention does (F-029), a Mention makes the person a follower of the Thread
   (F-027), and a Mention inside an attachment notifies with an empty notification unless the post's own text is set
   (F-056); the test server had push notifications off, so push on phones is still open.
5. Mattermost buttons, ephemeral replies and direct messages through a bot (C-13, C-18). _Answered:_ buttons work once
   an internal callback address is allowed in Mattermost (F-022, F-023); an answer to a press cannot open a URL (F-024);
   `ephemeral_text` in the answer lands in the Thread, so Muster sends a separate ephemeral post (F-025, F-026); a bot
   can message a user directly by id (F-028); and a bot can press its own button through the API (F-054), so a test
   message of a Mattermost Destination proves that presses reach Muster (C-16.FR-3).
6. Whether buttons work on Thread replies — "Still on it" and "Unack" on Reminders — in Mattermost replies and in
   comments of a Telegram discussion group (C-17.FR-4). _Answered for Telegram:_ they do (F-009). _Answered for the
   Mattermost server:_ it accepts a press on a Thread reply (F-055); how the client shows those buttons is still to be
   checked by eye.
7. How often an Alertmanager HA pair sends duplicate or partial Snapshots, how quickly a restarted instance catches up,
   and the observed gaps between repeats (C-06). _Answered:_ repeat gaps (F-033 to F-035), when and how an HA pair
   duplicates (F-037 to F-040), partial Snapshots after restarts and how fast they fill (F-041 to F-044); the
   requirements changed accordingly (C-06.FR-5, C-06.FR-21, C-05.FR-11). Still open: how often tick races of an HA pair
   cause duplicates over hours of operation, and the cases listed under [Pending](../facts.md#pending).
8. The Telegram dry probe and long polling through HTTP, HTTPS and SOCKS5 proxies and through an nginx reverse proxy
   with a path prefix (C-14.FR-10, C-14.FR-11).
9. What happens to messages sent before a bot moves between Bot API servers, and Telegram's answers in the 10 minutes
   after `logOut` (for the documentation of C-21.FR-7).

### 5.2 Other questions

12. **Edits refused by Mattermost's edit time limit.** An admin can limit how long posts can be edited
    (`PostEditTimeLimit`, unlimited by default, F-032), and what Mattermost then answers to the bot's edit of an older
    Root message was not checked. Under C-13.FR-5 that answer decides the outcome: an unknown answer ends the edit as
    Not delivered, so the Root message stops showing the current state, and a `403` would make the Destination Broken.
    Whether Muster should instead republish the Root message — the same question as question 3 for Telegram — is open;
    until it is decided, the documentation asks admins to keep the default (C-13.FR-7).

Answered since they were first listed — their numbers are not reused: question 10 (the OpenAPI 3.1 subset works through
the generators, so the specification stays on 3.1; the spike is recorded in [`api/README.md`](../../api/README.md)) and
question 11 (the documentation site is generated with Zensical; Material for MkDocs with the same configuration is the
fallback only if Zensical cannot build it, C-21.FR-1).
